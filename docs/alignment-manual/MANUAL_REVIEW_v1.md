# Review of the project-management manual

Review 1 · 22 September 2026 · Chirality basis `9b7ac5fb3c7f06cec35f24de8ebba8331bb95ac8`

The [original manual](Project_Management_for_Human_Agent_Teams_Consolidated_v1.md) is a coherent and unusually careful account of managing delegated work. Its strongest contribution is the connection it makes between purpose, authority, production, evidence, and continued human responsibility. It treats an agent's apparent completion as something to examine in relation to the intended result. That makes it useful both to programmers learning to manage substantial agent work and to engineering managers learning what changes when an artificial contributor enters the team.

Most of the manuscript should remain. The principal weakness for use in this repository is the reader's route from its supplied sources to current operating practice. The manuscript accurately preserves many distinctions, but its source apparatus still describes the latest App/Piping loop as a proposal; the repository now contains the adopted successor. Conversely, that adoption does not replace Runtime or PEC's procedures, change the method of an existing concordance run, or qualify a described host capability. A reader needs those differences before choosing what to do.

The [incremented Edition 2](Project_Management_for_Human_Agent_Teams_Consolidated_v2.md) therefore makes targeted corrections and adds a dated application note. It retains all seven chapters, their examples, the author's phase model, the philosophical framing, and every original section anchor. The separate [agent user manual](CHIRALITY_AGENT_USER_MANUAL_v1.md) supplies an operational reading of the repository. That guide is derivative documentation; the identified live instructions and accepted project instruments govern actual work.

## What the manual does well

The recurring editor example is effective because each return to it asks a different management question. Preserving document state begins as an intention, becomes a commitment in the PRD, appears in decomposition and interfaces, and later requires candidate-specific evidence. The reader can see why fluent prose, a plausible design, and a passing test answer different questions. Broadly compressing this example would weaken that progression.

The distinction between human judgment and artificial reckoning gives the book a clear position without requiring the agent to be passive. Agents can investigate, interpret, select within a brief, prepare consequential proposals, and carry authorized work far enough for a human to decide something concrete. The manual repeatedly protects this useful initiative. Its method should not be translated into a demand for permission before each routine choice.

Its graph treatment is also sound. Composition, production dependency, the local execution route, and the delegation arrangement are different views of work. An acyclic picture does not prove that prerequisite outputs exist, a completed node does not close a Deliverable, and a graph state must be compared with actual code, unmerged work, and evidence. The discussion of strongly coupled work gives concrete responses while retaining the need for the relevant decisions.

The treatment of examination deserves to remain central. The manual distinguishes verification from validation, requires a reviewer to inspect the actual changed candidate, protects test criteria during repair, and rejects the inference that a passing rerun proves a known defect was repaired. Its requirement to trace both from obligations into implementation and from implementation back into the records is particularly useful for a repository that has accumulated many decisions and representations.

Finally, Chapters 5–7 resist two tempting overclaims. Record maintenance is not itself product progress, and the proposed management benefits are not measured universal productivity gains. Completion, professional reliance, lifecycle acceptance, Git integration, and delivery retain different meanings. The brief delivery chapter is appropriate: an explanatory manual should connect to a product's real delivery arrangements, not invent one pipeline for every domain.

## Suggestions retained for later editorial development

These are optional improvements to the book's presentation, not missing prerequisites for this revision:

- Add a short reading route for each principal audience. An engineering manager may need the software/harness vocabulary first; a programmer may benefit most from the basis, scope, and evaluation chapters before the concurrency discussion.
- Carry one small undertaking through a compact end-to-end record set. The editor example already supplies the narrative; a small collection showing the PRD commitment, Deliverable claim, graph node, return, reconciliation, and completion position would make the relationships easier to rehearse.
- Use a compact source-status key in a future edition. It could reduce repeated caveats while preserving the important distinction among a current instruction, adopted decision, proposal, historical artifact, illustrative example, and unverified claim.
- Trim repeated general warnings only where a cross-reference preserves the local lesson. PRD maturity and record/evidence distinctions recur for sound teaching reasons. A broad shortening pass was not needed for the current corrections.
- If empirical claims are later desired, commission a separate study with defined cases, costs, independence, comparison conditions, and failure reporting. The supplied retrospective accounts support useful questions and design mechanisms; they do not establish a universal staffing ratio or productivity gain.

The operational guide carries the detailed entry recipes, standing Git procedure, current Codex MVP boundary, commands, and project-specific checks. Repeating all of these inside the general manual would make the manuscript harder to maintain and would turn its conclusion into another operating checklist. The revision therefore keeps those details in their appropriate companion while retaining the existing correct discussion of integration and release.

Current counterparts are identified as counterparts, not claimed to be byte-identical to supplied archives. The original APEGA, Alberta terminology, philosophical, and vendor references remain attributed manuscript sources; this editorial task did not independently renew their regulatory interpretation, date of consultation, or capability qualification. The manuscript's professional-practice and validation qualifications were preserved.

The assessment covers every chapter but is not a complete audit of every referenced tool implementation, every project's current state, or the empirical effectiveness of the method. The current graphs themselves contain dated recovery descriptions, reinforcing the book's instruction to compare recorded state with actual work. No graph state was repaired or promoted as part of this documentation task.

The source manifests, edit manifest, and original figure extraction make the comparison recoverable. They are evidence of reading and authoring, not human acceptance of the revised manual. The larger documentation undertaking owns final combined-candidate review, link/rendering checks, required repository validation, and Git closeout.
