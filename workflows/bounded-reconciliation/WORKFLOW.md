# Bounded reconciliation

Use this method for bounded comparisons within one planned closeout stage of a
development undertaking. The stage follows integration of the intended
implementation and evidence work—normally the penultimate merge—and precedes
the final PR. Reconcile actual deliverable documents and governing records with
that result. The manager may divide the affected deliverables into bounded
assignments; this does not introduce recurring passes during graph traversal or
activate whole-corpus concordance. Substantive PRs already carry the document,
reconciliation and conditional Task Management work their slices need. Those
consequences do not require a formal pass after each node. The final stage
checks the combined result and completes the documentary/governance closeout.

TASK can perform one deliverable or a small connected comparison without
further delegation. Its parent integrates the return and any resulting work
into the graph. A report alone does not complete authorized document edits.

## 1. Identify the work and affected deliverables

Use the work graph, actual changes and relevant decisions to identify the
capability, repair, investigation or design result being reconciled. Establish
the affected deliverable IDs/folders, stable code or artifact revision, evidence,
permitted writes and completion conditions. Inspect consequential consumers when
the original mapping is incomplete. Return a mapping question rather than force
new scope into an unrelated deliverable.

The intended implementation and evidence work must be complete enough to support
closeout. Identify the integrated candidate and any unmerged work accurately. A
claim that requires a merged or accepted basis cannot be established from a lesser
one. Missing required evidence returns to production; it is not a documentation
qualification that makes the undertaking complete.

## 2. Read and compare the substantive records

Read current controlling decisions and the affected contents of these files:

| File | Subject |
|---|---|
| `ScopeOfWork.md` or another accepted production form | Purpose, outputs, requirements, criteria, methods, interfaces and the output/evaluation relationships. |
| `Dependencies.csv` / `_DEPENDENCIES.md` | Required inputs, target identities, satisfaction evidence and affected consumers. |
| `MEMORY.md` | Prior run index and pointers to central evidence/decisions; no independent decision authority. |
| `_REFERENCES.md` / `_CONTEXT.md` | Supporting sources, identity and scope; changes to a pinned basis or identity retain their authority requirements. |
| `_STATUS.md` | The deliverable's lifecycle and history, not a mandatory execution backlog. |

Follow document statements into the actual work and evidence; then follow the
work back into the documents to find resolved questions, omitted consequences
or unsupported descriptions. Distinguish missing implementation from missing
verification. Preserve failures and limits. A later passing check alone does
not demonstrate that a known defect was repaired.

Keep claims at the level of commitments, relied-on interfaces and meaningful
verification. Apply the owning claim-granularity rules: incidental mechanism
detail belongs in code, tests or technical evidence; a decision-bound mechanism
retains its force. Prefer lifting stale incidental wording to its stable claim
rather than repeatedly rewriting the mechanism. Borderline cases go to the
owning decision. This test does not authorize changing a requirement.

## 3. Make the warranted changes

Correct outdated descriptions, resolved details, evidence references and
permitted dependency statements. Apply accepted design decisions within their
actual scope. Keep documents consistent and preserve identities. Future
requirements remain requirements when implementation falls short; record the
necessary implementation/check/decision work in the graph, not in a second
local task list or in MEMORY as future instructions.

Changes to accepted scope, lifecycle, protected criteria or a pinned authority
basis follow their owning decision path. When direct edits are not authorized,
return precise proposed changes and leave application outstanding. Ordinary
factual corrections already within the assignment need no new human prompt.
Code repair remains separate unless included in the assignment.

A useful current document must say what it means. Adding a memory entry or a
link to a central run folder does not discharge a warranted substantive edit.
Conversely, a supported no-change result is sufficient when the affected record
already represents the result accurately.

## 4. Account for unresolved consequences

First handle a consequence through the authorized graph, a warranted amendment,
or the actual owning decision/scope-change route. Preserve ordinary future
requirements in their governing scope. A material evidenced concern with no
current or identified successor home may enter Task Management through a
WORKING_ITEMS undertaking when the calling loop permits it. Supply the concrete
concern and its grounds; the selected workflow performs federation and retains
actual human promotion/disposition requirements. Return the linked outcome or
pending intake. A transfer never fulfills required production or authorizes a
foreign assignment.

Central decision and scope-change records retain the ruling and its grounds.
Do not introduce a deliverable-local decision record while reconciling the
result. Preserve the evidence at its actual source; unresolved proposals remain
proposals. MEMORY will receive a terse run entry during final PR preparation,
linking this closeout and any relevant decision, transfer or completion result.

## 5. Check and return

Compare live target bytes with those inspected before saving; preserve others'
edits. If inputs changed, recheck the affected comparison or report stale
claims. Read the changed documents together, verify source/evidence links and
applicable formats, and obtain required independent checking.

Return the deliverables and sections changed, the result/evidence they reflect,
the central decisions or transfers applied and any unresolved consequence for
the graph. Supply the pointers needed for the subsequent MEMORY run entries. Use a
small table only when it helps. Detailed evidence can remain at its appropriate
source; no duplicate central run narrative or separate claim ledger is required.

The node completes when its bounded comparison and permitted edits are checked,
or no change is warranted, and residuals have an explicit disposition. A proposed
edit remains unapplied; missing inputs leave affected comparison incomplete.
If missing implementation or evidence is found, repair that graph work and
recheck only the affected comparisons before completing this closeout. This does
not declare the entire deliverable complete. After interruption,
inspect partial edits and the actual evidence basis before continuing. Return
execution state to the graph maintainer; do not turn it into memory instructions.
