## Findings applicable now

**The Pi foundation already has the useful lifecycle primitives.** The installed `pi-agent-core/dist/agent.js:134-146,195-209,366-409` provides an active abort signal, ordered awaited listeners, and a wait-for-idle promise that settles after final event listeners. `agent-loop.js:393-433,449-470` supplies the signal to the pre-tool hook and execution, blocks execution after abort, preserves tool-call identity on updates, and waits for emitted updates. `pi-coding-agent/dist/core/agent-session.js:1162-1175` aborts retry and the agent, then awaits idle. These primitives support cancellation-aware tools and deterministic final event settlement without replacing the SDK loop.

Current Runtime `packages/engine-pi-omlx/src/pi-turn-runtime.ts:109-114,188-202` already calls SDK abort/waitForIdle and disposes after cleanup. Its `session.subscribe` callback projects SDK events using Runtime session/turn identity. This is existing reuse, not a recommendation for migration. SDK abort is cooperative: an arbitrary tool or awaited listener that ignores its signal can still delay settlement. Pi alone does not establish process-group extinction, account continuity, approved supplier identity, or Chirality durable approval authorization.

**t3code separates live approval waiters from correlation retained for later resolution.** In [CodexSessionRuntime.ts:271-285](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L271), the pending record carries its Deferred decision and request/turn/item identity; another correlation record can survive removal of that waiter. [Registration and cleanup at lines1919-1971](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1919) install both maps and remove pending state in an ensuring block. [Resolution at lines1817-1846](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1817) consumes the retained correlation before emitting its normalized event. This is a useful lifetime separation, not proof that t3code's particular request-key fallback matches Chirality's pinned supplier.

**Cancellation request, process termination, provider acknowledgement, and durable projection are different facts.** t3code [close at lines2273-2289](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2273) settles approval waiters as cancel before scope shutdown. Its [interrupt path at lines2358-2389](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L2358) sends bounded best-effort interrupts to live child turns before interrupting the parent. Close and interrupt do not have identical bookkeeping. Its durable [approval projection at lines1633-1683](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/orchestration/Layers/ProjectionPipeline.ts#L1633) consumes attributed activity and permits a resolved row with an unknown/null decision. It separately handles optimistic response display and reply failure. Therefore these are source patterns to compare, not evidence that every external interruption has a successful durable resolution.

Current Chirality `packages/core/src/delegated-runtime.ts:197-213` reconciles missing unsent prompts into `store.resolve` only while the worker binding is live. `executeInterrupt:230-238` marks interruption and retires the worker. `approval-store.ts:35-45,100-104` requires live binding even for read/resolve. Consequently post-retirement public read403 is consistent with the present authorization contract and does **not** by itself prove a missing durable record. Use the owner-approved fixture-only private artifact inspection to distinguish the two. Do not relax `isLive`, fabricate a user deny decision, or label a Runtime retirement as a provider acknowledgement. A later change to lifecycle settlement semantics would need its own bounded diagnosis and grant.

## Native attribution: reference option, not implementation authority

Native children have their own provider thread and turn IDs. t3code [registers explicit child source information and immutable spawn attribution](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1417) and [maps collab receiver threads to their parent turn](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L977). Its source explicitly calls this feature work in progress and probe-gated at lines884-898. [Routing at lines1032-1084](https://github.com/pingdotgg/t3code/blob/95d99373b74edfb3bfd092c61a15999a95727423/apps/server/src/provider/Layers/CodexSessionRuntime.ts#L1032) avoids dropping child request-resolution traffic as ordinary child chatter. The adjacent `CodexCollabWire.test.ts:176-180` pins that distinction; these tests were read, not executed here.

Chirality `packages/daemon/src/codex-session.ts:216-217,240-248` currently accepts, lists, and replies to network prompts only when thread/turn equal the active primary. It already holds `childAssociations` and exposes them at line270, populated from primary collab events at lines340-349. A genuine child's callback can therefore require handling distinct provider identity even though the Runtime's authorization binding remains the root worker generation. This is a source-level likely failure boundary; it does not prove that a particular live failure arose here without its captured callback.

A **design option** is to preserve two separate identity sets: (1) the existing root Runtime authorization binding, including root/account/epoch/policy/worker generation; and (2) validated provider thread/turn/request/item attribution, linked through observed child parentage. This option must not grant child capabilities from arbitrary foreign traffic, assign a role from native descent, accept an unadvertised approval choice, substitute a child ID for a root authorization identity, or persist raw provider payloads.

The smallest potential repair would reuse existing validated association data inside the private adapter and retain the existing public projection, if exact supplier evidence proves the association is sufficient and ordered. That is an option for manager analysis, not a finding that such a change is safe. If proving descendant parentage requires a new registry, public schema, durable child model, transitive association protocol, or changed approval/lifecycle contract, that is a significant design decision to discuss with the owner **before implementation**. t3code's default forwarding of unknown notifications and broad runtime modes must not be copied into Chirality's closed projection and containment boundary.
