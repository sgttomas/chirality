# Hosted status/config implementation handoff

The Runtime v2 route paths remain unchanged. HostedLoginStatus changes from unversioned `{state,loginId?,hasAccount?,authBindingSha256?,evidenceClass}` to the accepted schema chirality-hosted-login-status/v2 with required unavailable binding chirality-hosted-account-binding/v1, reason canonical-identity-producer-unavailable, and hostedReady:false. authBindingSha256 is rejected. Public loginId remains a string of at most512 characters; the supplier actor's existing128-character identifier grammar remains distinct and unchanged. Ceremony state and hasAccount are not verified identity/readiness.

Runtime client now validates the response. Updatedclient/updateddaemon accepts exact unavailable status; updatedclient/olddaemon rejects old status with INVALID_REQUEST; oldclient/newdaemon can silently accept it through its unchecked JSON cast. The latter is tested faithfully as an unsupported pair, not falsely rejected. No version handshake or endpoint is introduced. Paired rollout and exact artifact identities remain acceptance conditions; LOCAL_ARTIFACT_IDENTITIES records local built client/contracts/daemon bytes, not an App rebuild or released binary.

Hosted standalone config uses chirality-standalone-hosted/v2 and keyring/unavailable managedAuth, rejecting legacyhostedv1/hash/mixed/file/auto forms. Controlled-worker and local-engine-only retain v1 and pass selected config regressions. Changed source/config cannot inherit old conformance: configDigest replacement is directly tested; no unavailable sentinel becomes accountDigest. Production conformance/auth-file launch path is removed because its identity basis is unsupported. This is not permanent removal of the conformance obligation: any future enablement must supply separately qualified identity, exact source/config/supplier/owner acceptance and full conformance before executable admission. Current production guards unconditionally refuse before effects; fixtures remain explicit.

Trusted login config declares built-in keyring and narrow auth-purpose securityd exception. Default/offline worker denial is preserved; native hosted policy denies broker/private subtrees and rejects a login-purpose override. These are source/mock assertions, not OS isolation or keyring ACL qualification. No production keyring login is enabled. No bootstrap or global hosted lifecycle state is implemented.

Failure-code limit: direct CodexLogin.startLogin and supervisor admission guards produce ENGINE_UNAVAILABLE. The existing private supervisor transport collapses operation failures; a remote start rejection can remain a generic error projected as INTERNAL_FAILURE. This preexisting limitation was preserved rather than relabelling every authentication/transport error ENGINE_UNAVAILABLE. New malformed status projection uses INTERNAL_FAILURE internally and INVALID_REQUEST in the public client. Review must not claim exact direct error-code preservation across that old remote transport; a future typed propagation change needs an exact scoped contract.

App PKG09's reported absent current live caller means D122 presentation remains independent. Future App port acceptance must represent ceremony versus unavailable execution explicitly; binary loggedOut/loggedIn plus identity cannot losslessly carry the new condition. No sentinel principal/digest or completion-to-loggedIn shortcut. App owns rebuilt artifact identity and consumer review before reliance; no App/CLI product source or presentation was changed here. Existing supplier stableidentity, actual multi-rootUX, storage/process qualification, childapproval gaps, holds/lifecycle/cutover/release remain.
