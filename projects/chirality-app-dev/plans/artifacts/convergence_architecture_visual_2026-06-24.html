How chirality-app-dev and chirality-piping converge

So the agent harness can run inside piping — a plain-language visual walkthrough.

The one idea behind everything: the two projects do not merge, and piping does not rebuild the harness. Instead piping borrows the harness as version-pinned packages and runs it as a side module. A third thing — the chirality bridge — writes the rules but builds nothing. Think of it as federation through a shared contract, refereed by the bridge.

1The three players

Before any wiring, know who does what. Two builders and one referee. The harness only ever flows one way — app-dev makes it, piping uses it.

app-dev (builds the harness) piping (the domain engine) the bridge / tier-0 (rules only)
  • Aapp-dev owns the harness — the generic machinery that runs an AI agent. It is deliberately not piping-specific, so it can serve other domains later.
  • Bpiping is the specialist: a deterministic piping-stress solver. It wants an embedded agent but will not build a harness itself.
  • Athe bridge is pure governance. It never ships code; it rules what the contract is, which version is in force, and in what order capabilities may switch on.
  • BDirection matters: the harness only flows app-dev → piping. Domain truth (the models, the math) always stays inside piping.

2The end-state: how the harness lives inside piping

This is the picture of "done." Piping imports two app-dev packages and launches the agent runtime as a sidecar (a helper process). The agent can read and propose, but a human signs off and piping's own code makes the change. Follow the numbers ①–⑥.

app-dev code (the harness) piping code shared contract package human decision point
  • ①Piping's app starts the harness as a sidecar — a separate process running app-dev's Node + Agent SDK. The SDK stays whole, never rewritten in Rust.
  • ②The agent reads piping's allowed artifacts (existing models, run results) through read-only domain tools.
  • ③To compute, the agent asks piping's headless CLI to run the real deterministic kernel — same math as the GUI, no GUI needed.
  • ④When it has a suggestion, the agent writes an OperationProposal into the one folder it is allowed to write. It cannot touch protected truth.
  • ⑤A human reviews that proposal in the agent panel and accepts or rejects it. Nothing happens to the model without this.
  • ⑥On accept, piping's own code applies the change. The agent never mutates anything directly — that asymmetry is the safety guarantee.
Why a sidecar and packages (not a merge)? Piping keeps its own stack; app-dev keeps one generic harness. Piping pins a version of the harness packages and bolts the runtime in as a helper. Decided in DEC-041: "harness-as-versioned-packages — not a refactor, not a re-implementation."

3The convergence path: a 4-rung ladder

The bridge forbids "jumping levels." Capability switches on one safe rung at a time. Each rung adds power and unlocks the next gate. Today the projects sit on the bottom rung.

read-only / safe needs a gate or fence to open live mutation (most guarded)
  • L0Manual bridge (now). The agreement exists on paper: piping's profile is adopted, the contract is mapped. No automated contact yet.
  • L1Read. The agent can find and read piping's data through read-only tools. Needs only app-dev's contract package extracted and imported. No fence.
  • L2Run. The agent can run the real solver via the headless CLI and get validated results — but still changes nothing. This rung is the linchpin.
  • L3Propose → apply. The live loop from diagram 2. Only reachable after L2 is proven and the guarded fences open in order.
Why L2 is the linchpin: the bridge rule D-T0-08 says fence F3 (the domain machinery for L3) may only open after a proven L2. And L2 needs the headless CLI. So the entire path hinges on one buildable-today piece of code — see diagram 5.

4The safety workflow: who may do what

The reason this is safe to switch on is a strict division of labor. The agent suggests; a human decides; the engine acts. No single party can both decide and mutate.

  • 1Agent proposes. It writes a structured OperationProposal — what it wants changed and why — into its writable folder. It cannot apply it.
  • 2Human gates. Every proposal is reviewed and explicitly accepted or rejected. This is the non-negotiable checkpoint (K-DOMAIN-3).
  • 3Engine applies. Only piping's own deterministic code performs the mutation, so domain truth is always produced by the validated engine — never by the LLM.
  • 4Loop. The new state becomes readable, and the agent works from it next turn. Continuous, but human-paced.

5The critical path: what unblocks what

Two teams work in parallel and rendezvous at "a proven L2." The two starting pieces (in green) need no permission — they can be built today. Everything after the rendezvous is gated.

buildable today (no fence) needs a ruling / fence live binding
  • 1Start now, no permission needed: app-dev extracts the contract package (proposal D-APP-46) and piping builds the headless CLI (DEC-042). These are the green boxes.
  • 2They meet at a proven L2 — the agent reading and running piping's validated kernel. This is the single milestone everything else waits on.
  • 3Then the gated steps open in order: pin the contract version, rule piping's scope (D-21), open fence F3, then F1 for live binding.
  • 4Result: L3 — the harness runs live inside piping. Nothing irreversible happens until these gates are deliberately opened.
