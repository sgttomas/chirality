## 2. Decisions

- `chirality-standalone/v1` controlled-worker and local-engine modes and the `supervisor` role are retired with their tests. Both depended on the private supervisor server and the pi/oMLX manager path, which the design retires; keeping them without the supervisor server was not possible. The `engine-pi-omlx` package and its own tests stay untouched.
- `codex-manager.ts` (Agent 1 manager over the retired Codex session) is deleted along with `agent1-run-coordinator.test.ts`; the core `GovernedAgent1RunCoordinator` remains and is still covered by `agent1-run.test.ts`.
- `residency-coordinator.ts` stays because `RuntimeService`, `TurnCoordinator` and the Agent 1 coordinator still take it; the composition installs an offline control port.
- The retirement journal still requires a `WorkerContinuity`; the composition derives `{canonicalRoot, cwd: canonicalRoot, accountId: "chirality-app", accountEpoch: 0, policyDigest: "stock-codex"}` per project. It is root continuity for the journal, never an account claim.
- A role policy change between turns starts a fresh thread (existing `WorkerRetirementCoordinator.restart` rule); the same policy resumes the durable thread. The tests exercise both.
- `DelegatedRuntime` accepts `DelegatedTurnInput` (the contract request minus `compatibility` and `preflight`, plus `developerInstructions` and `contextUpdate`) because the contract seam still requires the retired fields; see section 5.
- The composition issues the App-host client with every runtime scope so the App can register projects, read status and drive sign-in from one token; per-project session tokens continue to be minted by the daemon's hosted registration route (`hosted-project-<id>`), which W3 and W4 read from `resolveHostedProjectTokenFile`.
- The native Plan trial admission is a fixed spike constant (`D-GOV-43:app-owned-codex-spike:local-human-trial`); it is evidence of a local human trial, not qualification.
- `pendingRequests` treats a worker that retired between the live-turn lookup and the read as an empty list rather than a 503; the composition test exposed that race.
- The supervisor registers the turn entry before sending `turn/start` and defers whatever the stream delivers ahead of the response behind the `started` event. Without that, the app-server's first notifications and the first approval request (which the stock server streams immediately behind its response) were routed to no live turn.
- Legacy approval denial is sent as `{denied:{rejection:"..."}}` (the object form in the pinned bindings), not the plain string the design text mentions.

## 3. Protocol facts verified by probe (scratch CODEX_HOME only)

Verified against the scratch install of `@openai/codex@0.154.0` and its generated bindings before this write-up: `initialize` accepts `capabilities {experimentalApi:true}` alone; `thread/start` takes `cwd`, `developerInstructions`, `approvalPolicy`, `sandbox` (string), `model`, `ephemeral`, `serviceName` and answers with `thread.id` and the effective `model`; `thread/settings/update {threadId, collaborationMode:{mode, settings:{model, reasoning_effort, developer_instructions}}}` and `collaborationMode/list` work although the generated `ClientRequest` union omits them; `turn/start` has no collaboration-mode parameter and takes `sandboxPolicy` as an object; a text `UserInput` works with `{type:"text", text}`; `turn/interrupt {threadId, turnId}` answers `{}` and the turn ends with `turn/completed` status `interrupted`; `account/read {refreshToken:false}` reports presence only; `model/list` entries carry `hidden`, `isDefault`, `defaultReasoningEffort` and `supportedReasoningEfforts` objects. No live probe pointed at the owner's real `~/.codex`, no credential file was read, no sign-in was attempted.

## 6. Open risks

- The composition and supervisor were exercised only against the scripted fake app-server and the earlier scratch probes; a live end-to-end turn through the App against the real binary is the next check (W3 reports the same for its host).
- `serverRequest/resolved` from the real server arrives with a request id; the fake sends `null`. The supervisor only acts on ids it still holds, so both are handled, but the real ordering of `serverRequest/resolved` relative to the client's own answer was not observed live.
- Model catalog freshness: `binding.catalog` is read from the last hosted-bootstrap status; a session created before any status read triggers one `model/list` through the default session policy, but a catalog change after sign-in is only seen on the next status read.
- The app-server restart path re-resumes threads on demand (`thread/resume` when the new child does not know the thread); a turn that was live during the crash is failed, not replayed, by design.
- `hostedBootstrap.grantProviderNetworkConsent` is a no-op that returns status; the App's consent step remains on the wire but grants nothing, which the App copy should reflect.
