# Runtime environment correction, version 2

Preparation only. This supplements the immutable initial protocol and supersedes its historical-driver environment recipe. No app, browser, server or build was launched. Candidate v2 remains unbound and execution held.

The current source has two distinct credential selectors. Electron main runtimeControlPaths reads CHIRALITY_RUNTIME_OPERATOR_TOKEN_FILE, falling back to app userData/runtime/auth/tokens/operator.token; it reads CHIRALITY_RUNTIME_SOCKET_PATH, falling back to app userData/runtime/control.sock. The GUI runtime control, connectivity supervisor and model status clients use these explicit options. CHIRALITY_USER_DATA must point to the owned absolute directory before main resolves paths.

The App HTTP harness port reads CHIRALITY_RUNTIME_TOKEN_FILE, CHIRALITY_RUNTIME_SOCKET_PATH, CHIRALITY_RUNTIME_PROJECT_ID and CHIRALITY_RUNTIME_PROJECT_ROOT. All four are required; the token basename must match project-[A-Za-z0-9_-]+.token and the ID must be chirality-app-dev. Missing binding fails ENGINE_UNAVAILABLE/503. It has no fallback to a user token. RuntimeClient itself requires explicit socketPath and tokenFile and reads only that token path.

Main prepareDesktopHarnessEnvironment deliberately deletes TOKEN_FILE and PROJECT_ROOT before attempting operator binding, sets the owned socket, and forces the fixed project ID. A failed offline binding therefore leaves TOKEN_FILE and PROJECT_ROOT absent in main: this is expected fail-closed behavior, not a reason to reinsert or fabricate a bound project. A successful binding would derive its token only from app userData/runtime/auth/tokens and validate its ownership, canonical containment and actual registered project. No successful binding is expected or permitted in this fixture. An unexpected connected state is a stop condition.

An independently launched owned Next server does not inherit later main process mutations. Give both processes the clean explicit launch environment in ISOLATED_ENVIRONMENT_v2.json, including both token selectors, an owned nonexistent socket, fixed project ID and inert fixture root. Keep both token files absent. The HTTP server may construct a client but attempts fail on the owned missing token/socket; fixture harness routes supply only synthetic session responses. Do not copy any real token or start a daemon. Inspect effective main and server environments separately after launch; do not assert that main retains the initial TOKEN_FILE after its deliberate clearing.

The CLI resolveCliRuntimePaths reads CHIRALITY_USER_DATA, SOCKET_PATH and TOKEN_FILE, with defaults inside userData; when userData is unset it defaults to the real home Application Support/Chirality directory. It also reads CHIRALITY_LAUNCH_AGENTS_DIRECTORY, otherwise the real home Library/LaunchAgents directory. Set the former to an owned path as defense in depth, although no CLI operation is needed. Critically, Electron createDesktopDaemonLifecycle does not consume that directory override: it uses app.getPath('home')/Library/LaunchAgents. Its target job is isolated by CHIRALITY_RUNTIME_LAUNCH_AGENT_LABEL, consumed by resolveDesktopDaemonPosture. Check the unique real-home label path is absent before and after; status only, no install/start/stop/uninstall. HOME remains unchanged. CHIRALITY_DAEMON_GUI_SPAWN=0 does not itself isolate credentials and is not a substitute for these gates.

Use a positive environment allowlist. Do not inherit provider keys, runtime bindings, probe switches, daemon activation switches or arbitrary CHIRALITY variables. Pin CHIRALITY_INSTRUCTION_ROOT to the verified checkout and ELECTRON_RENDERER_URL to the owned origin at release. Confirm app.isPackaged=false and absence of --runtime-daemon. No runtime host initialization is authorized.

Fallback assessment: the old recipe was incomplete for a separately launched HTTP server or CLI because it supplied only the operator selector. With a clean allowlist and owned CHIRALITY_USER_DATA, main's operator fallback was already owned; the HTTP adapter fails closed when incomplete rather than discovering a real token. This supplement explicitly fences both selectors and every relevant default. Runtime and token paths, the unique LaunchAgent target and effective environments remain to be verified during a separately released native attempt.
