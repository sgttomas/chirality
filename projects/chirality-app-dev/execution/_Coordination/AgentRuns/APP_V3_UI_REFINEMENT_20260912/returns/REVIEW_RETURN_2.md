### Findings, by severity

Finding 1 (Medium): opening a chat from another folder bypasses the chat binding lock, leaving the chat panel bound to the old folder under the new one.
- Location: `frontend/src/components/woven-dialogue/woven-dialogue-shell.tsx:421-422` (`openChatInFolder` guards only `streaming || folderSelectionPending`), `:446-447` (`locateFolder`, same guard), `:468-476` (`loadReplay` routes an unlisted indexed chat to `openChatInFolder`); `frontend/src/components/shell/chat-panel.tsx:478-489` (root-change effect nulls `activeSession` only), `:716-720` (`selectNativeFolder` refuses with "Start a new chat before opening another folder." when `conversationBinding` is set), `:784-785` (`createHarnessSession({ projectRoot: conversationBinding?.projectRoot ?? projectRoot })`), `:838-841` (`canonicalTransition` re-applies the session's root).
- Trigger: chat A is open and bound to folder F1 (`binding.locked` true, which the FolderSelect, ShellFrame `folderLocked` and `selectNativeFolder` paths all honour); the user clicks chat B under folder F2 in the navigator. `openChatInFolder` calls `workspace.applyProjectRoot(F2)` regardless of the lock. In ChatPanel the effect at 478-489 clears `activeSession` but leaves `conversationBinding {F1}`, A's messages and the composer enabled. The resume of B then depends on the pending-folder-chat effect: if B is not in F2's listing (index and listing disagree, listing error, replay isolation unavailable, or disclosure CONFLICTING/STALE/MALFORMED/BOUNDED so `canContinueRecordedConversation` is false), no resume happens and the stale state persists. Even in the happy path there is a window between `applyProjectRoot` resolving and `loadReplay` disabling the fieldset (the F2 listing must settle first) in which the composer is enabled.
- Impact: the UI shows A's transcript with "Working in F1" and the persistent right-panel folderMismatch alert ("The chat is bound to a different folder...") while the workspace, file tree and navigator show F2. Sending from that state calls `ensureSessionBooted`, which creates a new session in F1 (binding root wins), appends the exchange to A's displayed transcript under a new session id, and `canonicalTransition` flips the folder back to F1, undoing the user's selection. The recorded history is not corrupted (the new session is correctly bound to F1) but the displayed continuity is misattributed and the "explicitly re-selects that folder then resumes" behaviour of item 13 fails silently. Every other root-change path in the diff refuses this state; the new one does not.
- Evidence: `woven-dialogue-shell.tsx:728` and `:899` compute `folderLocked={binding.locked || streaming || folderSelectionPending}` for FolderSelect and RightPanel, while `openChatInFolder` omits `binding.locked`. `chat-panel.tsx:648` shows that only the new-chat path clears `conversationBinding` and `messages`. `woven-dialogue-shell.test.tsx` mocks ChatPanel without any binding, so no test exercises a cross-folder open with a bound panel; RUN_LOG 20:04Z records the happy path only.
- Remediation direction: either refuse the cross-folder open while `binding.locked` (consistent with `selectNativeFolder`, with a notice telling the user to start a new chat), or drive it through the new-chat request (bump `newChatRequest`, honouring the unsent-draft confirm) so `conversationBinding` and `messages` are cleared before `applyProjectRoot`; additionally have ChatPanel clear `conversationBinding` (and hide the stale transcript) when its root is left by the shell. Add a shell test with a binding-reporting ChatPanel mock covering both the happy path and the not-resumable path.

Finding 2 (Low): the F-2 remediation still records a document opened during "new chat" for the chat that is resumed next when that chat was also the previous one.
- Location: `frontend/src/components/woven-dialogue/woven-dialogue-shell.tsx:595-600` (`documentRecordSessionRef` is assigned only after the `!primarySessionId` early return).
- Trigger: chat A active (ref = A); New chat (primary undefined; effect returns before updating the ref); the user opens document X with no chat active; resume A (primary = A). `sessionChanged` is `A !== A` = false, so the effect records `chatDocuments[A] = X` although X was never opened while A was active.
- Impact: same inheritance class as the first reviewer's F-2 (A later restores X and forces the right panel to Files). Narrower trigger, same contradiction of "document context per chat".
- Evidence: the restore effect immediately above (`:582-586`) updates its ref before its own early return; the record effect does not. The regression test only covers A -> B (distinct sessions) and never passes through an undefined primary.
- Remediation direction: assign `documentRecordSessionRef.current = primarySessionId` before the early return (or reset it to undefined when `primarySessionId` is undefined), and add a test for A -> new chat -> open document -> resume A.
