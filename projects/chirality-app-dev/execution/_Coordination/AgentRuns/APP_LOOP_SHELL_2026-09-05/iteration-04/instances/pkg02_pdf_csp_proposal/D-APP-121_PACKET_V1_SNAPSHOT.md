## Evidence and the omitted seam

`frontend/electron/renderer-window-policy.ts` buildRendererContentSecurityPolicy emits `frame-src 'none'` (line 217) and `frame-ancestors 'none'` (221) in both modes. The first stops the parent loading a PDF frame; the second stops a served PDF being framed even if the first is changed.

Packaged `frontend/electron/main.ts` custom server (485–488) calls applyPackagedRendererRequestPolicy for every request before Next handles it. That helper (renderer-window-policy.ts 240–251) installs byte-identical request/response CSP with one fresh request nonce. Thus the PDF API response inherits the deny-ancestry policy too. The development window setup (main.ts 540–546) supplies a static policy to the response hook. applyContentSecurityPolicyHeader (264–284) adds it only to renderer-origin responses without an existing CSP; it leaves existing CSP untouched. An endpoint-supplied header could therefore avoid the dev fallback, but that is not authorization or a complete packaged fix. No response-hook/header bypass is proposed now.

The draft `frontend/src/app/api/working-root/file/route.ts` GET accepts `content=pdf`, classifies by `.pdf` extension, and streams an opened descriptor with application/pdf and inline disposition. That is not content authentication. Its normal route also serves metadata/text, so matching the URL pathname alone is insufficient. `file-policy.ts` validates Working Root, relative paths, canonical containment, instruction-root exclusion, regular files and descriptor identity. Those boundaries must remain intact. `document-view.tsx` currently gates inline PDF by desktop capability; `electron/preload.ts` exposes inlinePdfPreview false. These captured T3 bytes are evidence of partial work, not an accepted successor source baseline or native display proof. The author alone owns their freeze; manager must refresh identities against the final source freeze.

`frontend/src/__tests__/contract-pins.manifest.ts` renderer policy block pins both denial literals. `renderer-window-policy.test.ts` pins them in packaged and exact development policies, and checks one nonce. `scripts/run-packaged-security-proof.mjs` inspectPolicy (430–449) currently requires exact `frame-src 'none'`; its test rejects `frame-src 'self'`. The proof does not currently test PDF rendering or explicitly require frame-ancestors in that inspector. Pins/tests/proof must evolve together under a new accepted boundary; merely deleting denial assertions is not evidence.

### Proposed minimum policy semantics

1. Parent HTML: retain frame-ancestors 'none'. Permit a frame destination only at the actual renderer HTTP(S) origin with exact pathname `/api/working-root/file`; generate a CSP origin-and-path source, never wildcard host/port or `frame-src 'self'`. Ordinary non-shell/other responses remain closed. No redirect may widen the permitted destination; endpoint responses must not redirect, and navigation/redirect handling must enforce the same bounded destination for this subframe. Scheme/foreign-origin, arbitrary route and encoded-path negatives remain required.
2. Eligibility is enforced by the endpoint and descriptor checks, not CSP: a PDF frame response requires GET, exact path, exactly one `content=pdf`, one projectRoot, and exactly one relative target supplied through either path or target; reject duplicate/conflicting selectors and unknown keys for the PDF content request. Preserve metadata/text behavior outside that request. Validate approved accessible Working Root, no traversal, no symlink escape, no instruction-root or .git access, regular readable file and stable opened descriptor. Require `.pdf` extension plus descriptor-read PDF signature as a minimum eligibility screen; reject zero-length/obviously mislabeled data. A signature is not a full parser or guarantee of benign PDF. Malformed/polyglot behavior and changed-file/range handling remain explicit proof/design constraints; do not assert this screen proves safe parsing.
3. Only an eligible successful PDF stream may receive application/pdf, inline disposition, nosniff, no-store and a separate closed document policy permitting frame-ancestors 'self'. Its proposed default is `default-src 'none'; script-src 'none'; frame-src 'none'; object-src 'none'; base-uri 'none'; form-action 'none'; frame-ancestors 'self'`. Metadata, errors, failed validation, HTML and every other resource keep deny ancestry. No public request header/query value is trusted as a policy eligibility assertion. CSP cannot constrain query parameters, MIME or exact parent pathname: endpoint validation handles the first two; same-origin ancestry is the supported proposed trust granularity, not proof of a particular shell parent.
4. Central policy ownership is mandatory. The endpoint owns validated eligibility; renderer-window-policy owns policy bytes; main owns packaged installation. The implementation must carry trusted validation to one response finalizer before any bytes/headers commit, with deny-all defaults on failures. Keep one fresh nonce for each HTML request, byte-identical between Next input and the enforced HTML response. Do not append a contradictory second CSP header, fabricate a packaged fallback nonce, exempt `/api` wholesale, or let route code silently overwrite the security boundary. Development must apply the same eligible-response classification rather than trusting an arbitrary preexisting CSP as authorization.
5. Preserve contextIsolation true, sandbox true, nodeIntegration false, forbidden preferences, deny child BrowserWindows, authorized sender checks, existing navigation containment and egress allowlist. Keep packaged connect-src self and nonce-only inline scripts without unsafe-inline/unsafe-eval; retain only existing development allowances. Preserve object-src none. Whether Chromium's internal PDF viewer works with this closed PDF policy and existing internal-resource handling is TBD; do not add extension/blob/data/file/object exceptions merely to make a demo work. If these exact semantics cannot display the built-in viewer, return a new bounded candidate or choose defer.
