## Root cause and pin evidence

1. `projects/chirality-runtime/packages/core/src/delegated-engine-adapter.ts:285–287` converts both native item/started and item/completed for `subAgentActivity` into `subagent.progress`, with `taskId=item.id`, `agentThreadId`, `kind`, `agentPath`, and phase. It then continues, so there is no corresponding codex.notification row. This explains why the parent's Codex view cannot show the raw activity item, although the raw item remains nested under the projected event's `data.codex.params.item`.
2. `frontend/src/lib/shell/harness-event-views.ts:486–529` takes these events through its legacy pass: keys by taskId (activity item ID), assigns every subagent.progress event running status, ignores native agentThreadId/kind/agentPath, and falls back to an unavailable agent name. Its later native pass only accepts codex.notification, so it never corrects those rows. Item-start/item-complete pairs become one perpetual-running row with exactly two events. Two lifecycle items for one agent can consequently become two purported children. `activity-shelf.ts:103` counts the resulting rows, not unique native agents.
3. Exact [stock 0.154 SubAgentActivityKind](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/app-server-protocol/schema/typescript/v2/SubAgentActivityKind.ts) values are started, interacted, interrupted, completed. [ThreadItem](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/app-server-protocol/schema/typescript/v2/ThreadItem.ts) has `{type:'subAgentActivity',id,kind,agentThreadId,agentPath}`. These fields describe agent activity; item lifecycle phase is a separate fact.
4. [v2 activity emitter](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/multi_agents_v2.rs#L48) emits item/started and immediately item/completed for **every** activity item. The outer item/completed notification therefore does not mean that child work completed; `item.kind` carries the activity meaning.
5. [v2 spawn](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/multi_agents_v2/spawn.rs#L241) emits subAgentActivity with kind started and actual new child thread/path. Its collab spawn object at lines 69–86 is supplied to analytics, not emitted there as the UI lifecycle item. Consequently, no spawn collab row in Actions is compatible with this stock path.
6. [v2 wait](https://github.com/openai/codex/blob/rust-v0.154.0/codex-rs/core/src/tools/handlers/multi_agents_v2/wait.rs#L76) emits collabAgentToolCall wait started/completed, both with empty receiverThreadIds and empty agentsStates. Such wait completion cannot repair child status or establish any child result.

Existing `tests/native-event-adapter.test.ts` and App `__tests__/lib/native-progress.test.ts` cover a collab spawn with populated receiver states. They miss the stock v2 subAgentActivity path and its repeated lifecycle item pair.

## Separate Agents-tab limitation

`frontend/src/components/woven-dialogue/woven-dialogue-shell.ts:358–373` builds the recorded agent hierarchy only from `listHarnessSessions` records. `recorded-agent-hierarchy.ts` uses Runtime sessionId/parentSessionId. Native descendants seen in the primary's event stream are not materialized as Runtime sessions by this adapter. Refreshing this tab therefore cannot discover them merely because the Activity projection has native child evidence. This is a separate missing native-tree projection, not proof the child did not run. No fabricated Runtime child session or role should be created to make the tab agree.
