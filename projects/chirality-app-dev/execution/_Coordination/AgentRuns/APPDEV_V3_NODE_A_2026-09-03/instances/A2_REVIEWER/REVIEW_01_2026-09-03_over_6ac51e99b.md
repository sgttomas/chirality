### MAJOR-1 — Deny-all `setWindowOpenHandler` silently breaks two existing renderer features; the evidence claims "the app never opens windows from the renderer", which is false

- **Where:** `frontend/electron/renderer-window-policy.ts:12-13` (header comment), `:152` (`evaluateWindowOpen` comment "The renderer never opens windows"), `:241-246` (installer). Existing product call sites: `frontend/src/components/shell/chat-markdown.tsx:26` — every link in rendered chat markdown is `<a href={href} target="_blank" rel="noreferrer noopener">`; `frontend/src/components/woven-dialogue/navigator.tsx:321` — `<Link href={legacyHref} target="_blank">Open legacy interface in a new window</Link>`.
- **Evidence:** at basis no `setWindowOpenHandler` existed, so a `target="_blank"` click created a new `BrowserWindow` at the link's URL with the security web preferences inherited from the parent (Electron `electron.d.ts:21376`). After this diff every such click is denied and only a `renderer.window_open.denied` warn line is emitted; the user sees nothing happen. Neither RETURN.md §5 nor `EVIDENCE.md` discloses the behaviour change; both, and the source comments, assert the renderer never opens windows.
- **Impact:** user-visible functional regression on the chat surface (any model-authored link) and on the navigator's "open legacy interface" affordance, plus an inaccurate claim in the G-CSP evidence (UI/claims family). The denial itself is the right security posture — a foreign page in a child window inheriting the preload is exactly the sender-authorization threat this tranche closes — so the fix is a recorded decision, not a rollback.
- **Remediation (pick one, record it):** (a) keep `{ action: 'deny' }` and, for `http:`/`https:` targets only, call `shell.openExternal(url)` from the handler (system browser — not app egress, so not a K-NET-1/F-APP-1 change; keep the redacted log; add a unit case that `javascript:`/`file:`/`data:` are denied without `openExternal`); or (b) keep deny-all and record the regression as a named residual in the owning deliverable's `Remaining` at closeout. In either case correct the "never opens windows" statements in `renderer-window-policy.ts`, `EVIDENCE.md` §1, and RETURN.md §1. This is a product-behaviour choice for the coordinator/owner; the reviewer only requires that it be decided and disclosed.

## Ruling on the two implementer trade-offs

### 4(a) `connect-src https://api.anthropic.com:*` (port wildcard) vs exact host

**Ruling: not acceptable as the final form; acceptable as an interim only with a named residual (MINOR-2).**

- Posture: the wire posture is unchanged — `main.ts:246-259` still denies any non-`https:`, non-443 Anthropic request (`anthropic_port_not_allowlisted:8443` observed in bundle 2), and no non-loopback TCP was observed. K-NET-1 (deny-by-default, enumerated transports) and F-APP-1 (no provider/network expansion) are not breached: no new destination is reachable.
- But the renderer has **no** legitimate Anthropic call — the only references to `api.anthropic.com` under `src/` are server-side (`src/lib/harness/anthropic-agent-sdk-manager.ts`, used from `src/lib/harness/runtime.ts`), which run in the Next server process, not the page. The product-correct packaged CSP is therefore `connect-src 'self'`, stricter than the egress allowlist. The wildcard exists solely so a *page-originated* request can reach the egress layer for the proof: production policy shaped by the test, and a header any security reader will flag as inconsistent with REQ-NET-001's exact `https:443`.
- The "keep the egress layer observable" rationale is legitimate in aim but insufficient in means, because a different probe achieves it: Electron's `session.fetch`/`net.fetch` "will trigger webRequest handlers if present" (`electron.d.ts:12975-12976`), so a main-process probe (`window.webContents.session.fetch('https://api.anthropic.com:8443/…')` under the existing env gate) is cancelled by `onBeforeRequest` and yields the same `anthropic_port_not_allowlisted:8443` diagnostic independently of the CSP, while the in-page probe continues to evidence the CSP (`connect-src` violation for example.com).
- **Recommendation:** make the CSP exact (`connect-src 'self'` in packaged mode; if a future renderer call is intended, `'self' https://api.anthropic.com`, noting a host-source without a port matches only the scheme default 443), move the egress-layer observation to a main-process `session.fetch` probe, keep `egressLayerDiagnostics > 0` as a proof requirement, and drop the `:*` pin from `contract-pins.manifest.ts`. If deferred, record the residual in DEL-09-06 `Remaining` at closeout.

### 4(b) `script-src 'unsafe-inline'` for Next flight payloads

**Ruling: acceptable now; follow-on must be recorded in a deliverable `Remaining`, and the evidence should state the limitation plainly.**

- Verified independently on the frozen commit's build: Next 15.5.21 App Router emits inline `self.__next_f.push` scripts (6 per page) with no nonce; all external scripts are `/_next/…` (`'self'`); no inline event handlers. Without `'unsafe-inline'` the packaged page does not boot — `'unsafe-inline'` is genuinely required at this version with prerendered routes and no middleware.
- `'strict-dynamic'` is not feasible now: it requires a nonce or hash on every root script including Next's own `<script src>` tags. A nonce *is* feasible later without touching `next.config.mjs`: Next reads the nonce from the `Content-Security-Policy` **request** header (set by middleware, or — for the packaged custom server — set on `req.headers` before `handle(req, res)` in `startPackagedRendererServer`), but a nonce forces dynamic rendering of routes that are prerendered today, so it is a `src/app` change plus a decision on static prerender. Build-time hashes of the flight scripts are possible but fragile. The follow-on is recorded in RETURN §5.1 but in no deliverable `Remaining`; add it at closeout.
- With `'unsafe-inline'` in `script-src`, the CSP's XSS-mitigation value is limited to remote-script/eval/frame/object/base/form/connect containment; `EVIDENCE.md` should say so explicitly so G-CSP "CSP effective" is not over-read. `frame-src 'none'`, `object-src 'none'`, `base-uri 'self'`, `form-action 'self'`, `frame-ancestors 'none'`, `'unsafe-eval'` absent in packaged mode — all present and correct.
- Dev mode: `'unsafe-eval'` and the dev origin's `ws:`/`wss:` are added only in development; the dev-server CSP inside Electron is not empirically verified (disclosed) but nothing in the policy contradicts Next dev's needs (HMR websocket, eval, inline styles, `data:` assets). D-APP-36 render tests are unaffected (no CSP in the test environment); the full suite passes on my rerun.
