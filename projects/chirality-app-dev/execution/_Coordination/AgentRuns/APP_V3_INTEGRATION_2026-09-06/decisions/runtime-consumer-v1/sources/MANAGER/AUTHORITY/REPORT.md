## Decision A — Shared account presentation and per-root consent

**Recommendation A1:** retain one app-wide account presentation while the existing runtime contract remains root-private. Show account identity/readiness separately from the active canonical root's consent. Do not label a global sign-in as proof that all root-private login homes are ready. This enables coherent account navigation and truthful root switching; it prevents automatic consent inheritance, ambient-home reuse, and implicit credential copying. The App plan already says the display split leaves fake-port per-root login semantics unchanged (S15 §§8.1/8.1a, S16 account split).

Accepted constraints: S24 REQ-001 root-private app-owned CODEX_HOME and exclusion of ambient ~/.codex; REQ-002 no root/account/policy-digest consent crossover; REQ-004–006 off/ask/on with explicit-user-only acceptForSession and visible host/protocol/grouping caveat; S21 REQ-041 single-owner encrypted credential boundary. S12 `HostedConsentStore.ready` rejects cross-root homes; `sameContinuity` compares canonicalRoot/accountId/accountEpoch/policyDigest/cwd; `configuration` defaults to off. These source facts support the separation, not full production readiness.

**Alternative A2:** true shared login brokerage with per-root consent and isolated execution homes. This could remove repeated login ceremonies, but changes custody/continuity semantics and needs a concrete secure credential-broker contract, revocation/logout propagation, exact account epoch rules, and supplier proof. It cannot be implemented by pointing every root at one CODEX_HOME, copying tokens, or reading ambient ~/.codex. Runtime owner must select/amend DEL-02-09 scope/contract through its instrument; Root must accept any D-GOV-20 or custody-boundary amendment; App must accept consumer semantics. Defer live shared login until those acts exist. **Alternative A3:** explicitly present per-root account sessions, reducing ambiguity but abandoning the shared-account experience; App owner choice required.

Candidate App projection (new schema only if separately accepted): account `signedOut|signingIn|signedIn|expired|unavailable`; root consent `notGranted|granted|stale|revoked|needsSignIn`; separately `executionReadiness` and typed reason. Never serialize tokens. State carries canonical-root identity, account epoch, policy digest and consent generation so a delayed response for folder A cannot repaint folder B as granted. Exact enum/version acceptance belongs to Runtime/App; these names are not claims about the existing port.

**Owner slate A:** select A1 presentation-only now or authorize design of A2; decide sign-out scope (all broker sessions vs selected root), explicit reconsent after account/policy change, and required readiness wording. Required returns: exact HostedEngineConsentPort candidate, custody/continuity state table, affected-client compatibility determination under S21 REQ-004–008, Runtime own evidence and App-rendered acceptance.

## Decision B — No-folder chat still needs an execution boundary

**Recommendation B1:** keep the currently truthful blocked no-folder composer until an explicit projectless execution contract is accepted. S17 Applied direction §2 selects restriction plus design routing and forbids a hidden default root; it approves no schema/endpoint/registration mode/filesystem grant. S18 asks to resolve context, create/list/replay/boot/turn identity and persistence, rather than authorize an implementation. S21 REQ-010/019/020 require registered/current project and operation authority. S13 WorkerContinuity and S12 assertContinuity require a real canonical directory with cwd equal to that root. `canonicalRoot: null`, cwd from the launching terminal, home directory, or silently substituting the most recent project cannot satisfy that contract.

**Candidate B2 for separate owner selection:** an explicitly declared app-managed isolated execution context for projectless conversations, with a canonical directory and private account home, dedicated identity and instruction basis, default no command network, and no authority over known folders. A user need not select a project folder, but the UI must truthfully identify the sandbox/context and permitted actions. This enables folderless conversation only after its registration/authority and storage contract exists. It prevents incidental access to other projects, but adds storage retention/deletion/export, setup/repair and consent semantics. This is not a hidden default-root workaround and is not authorized here.

**Alternative B3:** a separate hosted text-only mode with no filesystem/tools. It reduces execution capabilities but requires its own accepted service/credential/session contract; it cannot be treated as permission to bypass the existing daemon. **Alternative B4:** require folder attachment before first message indefinitely; least contract change, no genuinely projectless sending.

**Owner slate B:** choose B2, B3, or B4; Root decides instruction and hard-boundary implications, Runtime decides execution-context/registration identity, App decides UI and first-message binding. For B2 specify one context per chat versus shared isolated workspace, user-visible identity, lifetime and deletion, history ownership, allowed tools/attachments, transition to a selected project (recommend a new session with no inherited consent), and schema compatibility. Accepted App known-folders lists remain convenience, never registration authority. ## Decision D — Delegation and recovery

**Recommendation D1:** distinguish Chirality-managed execution from delegated-harness-native execution. Root S01 explicitly permits native descent without assigning roles and adds no native child allowlist/fan-out cap/model allocation/scheduling. Agent 2 non-delegation is instruction+config asserted on that path, not mechanism proven. App choices such as None/Ask before changes/Approve each write/Run bounded briefs (S15 §5.10) cannot be advertised as universal enforcement merely because a session stores a field. Root must define how those preferences coexist with native semantics; Runtime must specify enforcement coverage per class; App must label unsupported or instruction-asserted coverage. No automatic Local-model-to-hosted fallback follows from `briefsRunOn`: S21 REQ-044/047 require explicit activation and forbid silent scheduling/fallback.

Managed delegates require sealed scope/brief and durable parentage/evidence; native approval requests require current originating-child authority independently of the primary's association map. S11 records an actual Candidate2 child approval request rejected by the primary-only Runtime adapter (`FOREIGN_PRIMARY_TURN`) and missing lifetime tracking. Arrival before parent spawn-completed association is a source-supported possible ordering, not an observed ordering established by a retained measured trace. Recommendation: unknown ancestry is unavailable pending authoritative attribution or fails closed; never infer authority from order, name, or descendant existence. Exact native child API and ordering protocol are supplied by the manager's approval-design fan-in, not invented here.

For recovery, S26 CLM-002/003 requires exactly-once active-turn terminalization before restart, recorded canonical-root/account/policy/cwd continuity for thread/resume, otherwise a fresh thread, and no automatic replay or in-flight reattach. S13 RetirementRecord exposes prepared/committed/reconciliation-required plus rolePolicyDigest; stored threadId alone is insufficient. App reconnect must show pending/retiring/reconciliation-needed status separately from the existing four terminal events. A candidate cancellation label must not say supplier decline or denial when only interruption occurred. Terminal/lifetime invalidation should disable stale approval controls and preserve historical actor/root/account/policy/generation/child provenance. Late responses after retirement return a typed stale/unavailable result without sending supplier approval.

**Owner slate D:** accept enforcement class per displayed policy and exact policy-digest compatibility; choose durable child attribution versus a deliberately limited transient mode; rule unsupported supplier decline behavior explicitly; accept restart/reconciliation UI meanings and explicit replay interaction. Runtime owns DEL-02-10/11 contract; Root owns role/policy semantics; App owns consumer acceptance. Session restart or policy edits must not carry an old grant into a new generation.
