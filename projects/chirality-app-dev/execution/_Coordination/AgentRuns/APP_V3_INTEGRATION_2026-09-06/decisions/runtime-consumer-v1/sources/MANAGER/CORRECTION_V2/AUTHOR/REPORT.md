It validates string or safe-integer IDs up to 128 characters; it does not read a turn, generation or capability discriminator. The generation comes from the Runtime-owned transport instance, never from provider JSON. The current handler searches network approvals, then dynamic-tool request IDs, checks the matched thread, and quarantines unknown resolutions. Sections 164–207 and 209–266 establish the shared typed server-request ID namespace and network/tool exclusion. Requests supply thread/turn and are classified by validated method/body. Propose one generation-private registry, keyed by `(owned generation, ID type, exact ID value)` across every supported server-request capability. Thread is an immutable value checked in the entry, not a namespace that permits ID reuse; capability and turn come only from a validated request. Use structured tuple keys; never coerce number 7 to string "7". An entry contains bounded projected thread, optional known turn, class (`unknown`, `network`, `tool`), request signature when known, authority revision, phase, and independent delivery/intent observations. A negative entry grants nothing. Never infer missing notification turn from the current turn, infer network class from the UI, or require invented supplier fields. Uniqueness for the whole generation makes a matching ID/thread resolution applicable to the existing turn without claiming the wire supplied that turn.

## Resolution and dispatch rules

1. Parse and validate on the owned transport. Missing/malformed ID or thread on the current transport fences that generation and enters existing protocol-failure retirement. Missing trusted generation/transport identity cannot be repaired from a JSON field; quarantine/drop at the ingress boundary, fence any ambiguous affected owner before further admission, and grant nothing. A positively identified retired generation cannot alter the new generation. Unknown JSON fields do not supply authority. All source shape validation and unknown-payload projection rules remain required.
2. For a known registry entry, require exact typed ID, owned generation and recorded thread. A thread mismatch is a protocol failure, not an unrelated benign event: revoke/fence the generation before retirement. Capability dispatch uses the immutable entry class. A matching network resolution revokes the callback at every phase; a matching tool resolution aborts that tool callback and prevents its result send. Neither routes into the other's handler. Already-resolved duplicates with the same identity are idempotent negative evidence. Conflicting duplicates fail closed.
3. For an unknown ID, create an `unknown/resolved` negative entry immediately, retaining only the bounded typed ID, thread and generation-local metadata in volatile memory. It poisons that ID for the rest of that generation across all classes. A later request matching its thread may fill in validated class/turn solely for non-authoritative diagnostic correlation; it remains resolved and cannot start a tool, enter a join, publish or send. A later different-thread request is a protocol collision and retires the generation. This proposal deliberately does not remove poison once class is learned.
4. Insert a request's registry entry before placing it into the untrusted join buffer. Cross-class or different-thread/turn/signature reuse is a collision at insertion, including reuse of a retired/resolved entry. Fence the generation, suppress all unsent responses and dispatches, and retire via existing reconciliation. An identical unresolved request may coalesce with its original; an identical request after resolution is rejected without revival. Thus a tool record and a network join can never coexist for the same typed ID. A legacy inconsistent inventory must fail closed when unified; lookup precedence cannot choose a winner.
5. A matching resolution during untrusted buffering removes the pending join and releases its projected request body. It leaves the negative registry entry. Late association, child start, persistence completion, display refresh or a human response cannot promote it. The same rule holds when resolution precedes the request. Resolution is terminal loss of this callback capability only: no human decision, deny, session grant, supplier application or parent/child turn terminal is inferred. Buffered/unknown requests require no invented durable approval row. A sanitized diagnostic count suffices; raw provider payload is never durable.

## Ordering through publication and send

The single generation actor serializes ingress observations, admission, display-publication commits, response reservations, resolution and retirement. Each ingress observation receives a monotonic sequence at host parsing; any fully parsed resolution preceding a commit must be processed before that commit. A backlog cannot let a control operation skip earlier invalidations. No awaited persistence, consent check or transport callback holds the actor: capture a revision, perform work outside, then re-enter. Async completions are proposals for a commit, never commits themselves.

Current packages/core/src/delegated-runtime.ts:197–223 awaits `store.request` before setting the callback map, then reconciles missing unsent prompts through `store.resolve`. The proposed join must not inherit that unchecked post-await insertion or treat absence polling as resolution evidence. Preserve a cause-specific revocation record: only an exact matched notification supports provider-resolved; local expiry, retirement and unknown disappearance remain separate causes. Admission may prepare a sanitized durable origin projection outside the actor. On return, recheck entry unresolved, generation/lifetime/root/account/policy/consent, exact digest/class/thread, and captured revision before marking actionable or publishing. Reads use this live gate, not existence of a durable row. If resolution wins while persistence is pending, a late row stays non-actionable; record capability-loss settlement separately where a durable request exists. Settlement persistence failure keeps the live capability revoked and reconciliation-required; it does not roll back revocation or allow the next dependent action. Crash recovery does not replay any old row or callback.

Publication commits the revision-bound view into the negotiated consumer queue in the actor, with no await between last check and enqueue. If resolution linearizes first, actionable publication count is zero. If publication linearizes first, the already-enqueued view can arrive stale; server responses reject it and the negotiated refresh must remove/disable it. No distributed guarantee of zero stale pixels is asserted. Existing closed v2 has no implicit new revocation event: use the already proposed negotiated polling/view contract until separately accepted event changes exist.

Response reservation captures an actual authenticated human act only while live. The actor reserves once, persists that intent asynchronously, then rechecks every gate on completion. Resolution after reservation but before or during persistence cancels send eligibility; a successfully persisted real human intent remains a historical fact, with delivery `not-sent`, not a grant. If persistence failed or its outcome is uncertain, do not claim `decisionRecorded=true`; revoke admission and require reconciliation without sending. A late completion can append settlement but cannot restore the reservation.

The send commit is a final no-await actor operation: compare revision and all authority gates; if live, mark enqueue-attempted and invoke the single transport enqueue immediately. A preparatory send reservation is revocable, so resolution between reservation and commit wins. No queued callback may perform an unchecked write later. Resolution processed before commit means zero enqueue attempts. If enqueue was attempted first, resolution cannot unsend bytes: set capability resolved, retain actual human intent, and report delivery `unknown` until a successful transport callback provides `sent` evidence. Errors, timeouts, or loss after enqueue remain `unknown` (conservatively including synchronous throws unless the transport contract proves zero bytes accepted). `write(false)` is backpressure, not proof of zero bytes. A later success changes delivery evidence to `sent` but never restores capability. Supplier application remains `unknown`, including when a resolution arrives. No retry or duplicate send is allowed. Only proof before any enqueue attempt permits `not-sent`.

Add a proposed unified registry maximum of 512 entries across live, completed, tool and unknown-resolution IDs, with 256 KiB total projected registry bytes including signatures. Existing narrower per-class limits still apply. IDs remain at most 128 characters, and thread fields use existing identifier limits; count duplicate observations toward the existing 1024 quarantine/diagnostic budget where applicable so duplicates cannot cause unbounded processing/storage. These are proposed fixture limits, not accepted Runtime thresholds or supplier guarantees.

On a limit violation, fence admission before dropping the incoming observation, invalidate all current capabilities and retire the generation; an unrecorded resolution must never coexist with further approval admission. No LRU, expiry, compaction or successful child association may erase negative identity evidence while its generation can still send. Join expiry drops the body but leaves a negative entry. Drop generation-private tombstones only after transport is detached, callbacks are fenced, retirement/reconciliation has completed, and old-generation messages cannot reach a new actor. Restart allocates a new generation and never reattaches old approvals. Failed retirement remains blocked. Public errors/settlements remain under existing or separately negotiated contracts, with no fifth terminal identifier and no schema keys silently added to v2.
