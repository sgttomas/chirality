# UI Lane

## Shared invariants for both targets

- Woven Dialogue remains the mounted primary human–agent collaboration
  surface.
- Visible information is not automatic model context; explicit next-turn
  references and provenance remain distinct.
- Work/Agents remains a projection over admitted records, not an authority or
  inferred intent store.
- Selected-session replay remains read-only and isolated from primary draft,
  attachment, context, permission, interruption, and interaction state.
- Existing `/`, `/chat`, `/workbench`, and `/pipeline` compatibility,
  query/alias/matrix behavior, disabled states, and deep links persist unless a
  later owner gate explicitly changes them.

## Target-specific candidate boundary

The per-domain control plane may specialize only ruled product-profile fields
or composition slots:

1. product label, iconography, color/token accents, and domain boundary copy;
2. ordered/filtered typed-agent views over registered agent identities;
3. structured-information views with source, authority class, currency, and
   evidence references;
4. workflow navigation over explicitly recorded states and actions;
5. decision-gate presentation that records a human act but never infers or
   auto-accepts one;
6. domain resource references and help/onboarding material.

The skin boundary must not grant tools, mutate protected paths, select generic
runtime behavior, invent domain truth, or turn domain proposals into accepted
acts. Standalone remains a complete product target rather than a hidden
fallback for the domain artifact.

## Required first-domain mapping before implementation

For Chirality Piping/OpenPipeStress, a later App-owned product packet must map
each typed agent, structured-information view, workflow state, and decision
gate to:

- its accepted Piping/domain source and owner;
- the App presentation component/slot;
- the recorded input and evidence references;
- the human action and resulting record;
- unavailable, stale, conflict, empty, and permission-denied states;
- explicit non-effects on solver truth and professional reliance.

Coordination input alone is insufficient for this mapping.

## Accessibility and visual evidence

D-APP-36 requires component/render tests for every user-facing control, state,
and disabled/active behavior. Browser or screenshot evidence is required where
target resources, layout, viewport, visual overlap, focus order, responsive
composition, or high-risk interaction differs.

Both targets require keyboard/focus, reduced-motion, contrast, accessible
names, error/status announcements, bounded-data, and narrow/wide viewport
evidence. Shared-component evidence may prove common behavior; it cannot prove
target-specific layout/copy/resource behavior. A domain screenshot cannot
prove standalone parity, and vice versa.
