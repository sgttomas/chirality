# D-APP-34 Packet - Issuance Gate Model After INSP-03

Status: PROPOSAL
Prepared: 2026-06-21
Prepared by: WORKING_ITEMS
Blocks: Any future process change to the per-deliverable `CHECKING -> ISSUED` gate; any attempt to
issue deliverables under a modified evidence model.
Evaluation basis: `plans/artifacts/insp04_gate_process_evaluation_2026-06-21.md`

## Question

After INSP-03 completed 53/53 deliverable assessments, should the project keep the current
per-deliverable SHA-bound issuance gate as-is, modify it with evidence profiles, or replace it with a
different acceptance model?

## Option A - Keep As-Is

Keep the current per-deliverable `CHECKING -> ISSUED` model without new evidence profiles.

Pros:

- Minimal governance change.
- Preserves existing lifecycle semantics.
- Avoids new artifact templates.

Cons:

- Does not resolve the mismatch between runtime-code, governance-doc, validation-release, and
  future-boundary deliverables.
- Leaves PKG-10 doc-only acceptance ambiguous.
- Risks repeated per-deliverable rediscovery of REF-006, AMD-01, and stale-spec issues.

Validation implications:

- Each deliverable would need a bespoke issue checklist assembled from its assessment.
- High chance of inconsistent evidence bars across packages.

## Option B - Modify With Evidence Profiles (Recommended)

Keep `CHECKING`, `ISSUED`, human actor, and approval SHA evidence, but require an issue-readiness
profile before any `CHECKING -> ISSUED` transition.

Profiles:

- Runtime/source.
- UI/product.
- Governance/control.
- Validation/release.
- Future-boundary/doc-only.

Pros:

- Preserves `K-AUTH-1`, `K-AUTH-2`, `K-GATE-1`, and lifecycle SHA binding.
- Lets different deliverable classes have appropriate evidence without weakening the human gate.
- Gives PKG-10 a bounded doc-only path without implying R7 implementation.
- Turns REF-006, AMD-01, and PKG-10 basis into explicit cross-cutting rulings instead of hidden
  per-deliverable variance.

Cons:

- Requires a small governance artifact/template before issuing deliverables.
- Requires INSP-05 to classify roadmap/remediation work by profile.

Validation implications:

- Future issue attempts must cite the selected profile and evidence package.
- Runtime/source and validation/release profiles still require current command evidence.
- Future-boundary/doc-only profile requires a human ruling and explicit non-implementation language.

## Option C - Replace With Package/Tranche Acceptance Only

Retire per-deliverable issuance as the primary gate and use package-level or tranche-level acceptance
records instead.

Pros:

- Less administrative overhead across 53 deliverables.
- Better matches package-batched work.

Cons:

- Weakens direct deliverable-to-SHA provenance.
- Conflicts with the existing lifecycle vocabulary unless docs/source/tooling are amended.
- May obscure deliverable-local blockers and deferrals.

Validation implications:

- Requires broader lifecycle redesign and likely source/tooling changes.
- Not appropriate as a small follow-on to INSP-04.

## Recommendation

Choose Option B.

Option B preserves the human gate and SHA binding while correcting the evidence-model problem found by
INSP-03. It does not issue any deliverable. It only authorizes the next process shape for future issue
readiness.

## Risks

- If Option A is chosen, issuance may remain inconsistent for doc-only and UI-render deliverables.
- If Option B is chosen but profiles are underspecified, the project may add process without gaining
  clarity.
- If Option C is chosen, deliverable-local provenance may weaken unless the lifecycle model is redesigned.
