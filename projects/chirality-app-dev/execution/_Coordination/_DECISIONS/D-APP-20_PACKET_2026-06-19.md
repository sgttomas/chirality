# D-APP-20 Decision Packet - Document Content API Contract (Phase 4 Gate)

**Status:** PROPOSAL
**Date:** 2026-06-19
**Decision ID:** D-APP-20
**Prepared by:** WORKING_ITEMS
**Active design:** `plans/DESIGN_2026-06-18_agent_orchestration_ui.md` (§3.2 Document view, §5 Phase 4, §6 open decisions)

This packet asks how the document **content** endpoint that powers the sidebar Document
view (and later the doc-copilot tertiary screen) should be shaped. It blocks Phase 4.

It does not approve an editor, write capability, provider/release changes, or any
governance-state (`CHECKING`/`ISSUED`) transition.

## Decision Question

What is the contract for serving deliverable document content to the UI: read-only vs
read+write, batch vs streamed, and single-canonical-file vs relative-path-within-deliverable?

## Grounding (current state)

- Roster already exists: `GET /api/project/deliverables`.
- A deliverable is a directory under the project root holding `_STATUS.md`,
  `Dependencies.csv`, and the deliverable body; sibling routes already serve its
  structured parts: `src/app/api/working-root/deliverable/{status,dependencies,status/transition}`.
- `src/lib/workspace/deliverable-contracts.ts` has a private `readRequiredFile` plus path
  guards (`normalizeDeliverablePath`, `assertWithinProjectRoot`, `DELIVERABLE_ID_PATTERN`)
  — the security spine for any content read.
- The viewer is `src/components/shell/chat-markdown.tsx` (already renders markdown read-only).
- No `…/deliverable/content` route exists yet.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Read-only **batch** GET of a single canonical deliverable document | `GET /api/working-root/deliverable/content?deliverablePath=…` returns one markdown body (the deliverable's primary doc), reusing `readRequiredFile` + path guards; viewer reuses `chat-markdown`. | Write/PUT, arbitrary-file reads, streaming, editor. |
| B | Read-only **batch** GET parameterized by a **relative file path** within the deliverable | As A, but `&file=<relpath>` (validated inside the deliverable dir) so the viewer can open `_STATUS.md`, the body, or other in-deliverable markdown. | Write/PUT, reads outside the deliverable dir, streaming, editor. |
| C | Read+write contract from the start (GET + PUT) | Adds a guarded PUT to write the document back now, wiring the editable tertiary screen ahead of Phase 4. | Provider/release changes; governance-state transitions still via the existing `status/transition` route only. |
| D | Streamed/chunked content (SSE) | Content delivered incrementally for large docs/co-editing. | Write, editor. |
| E | Custom | Human supplies alternate shape/constraints. | Anything not named. |

## Recommendation

**Option B.** Markdown deliverables are small, so batch beats streaming (D is premature);
read-only keeps Phase 4 decoupled from the editor decision (D-APP-21); the relative-path
parameter avoids hard-coding a canonical filename and lets the same endpoint serve both the
sidebar Document tab and the tertiary viewer. Promote/wrap `readRequiredFile` behind the new
route and reuse the existing deliverable path guards verbatim. Choose **A** if a single
canonical document per deliverable is guaranteed and multi-file viewing is unwanted; choose
**C** only if the editable tertiary screen is being built in the same tranche as Phase 4.

## Required Constraints If B (or A) Is Approved

- Reuse `assertWithinProjectRoot` / `normalizeDeliverablePath` (and, for B, validate `file`
  resolves *inside* the deliverable dir via `realpath`); no path traversal.
- Read-only: no write verb in this tranche.
- Return redaction-safe content; do not leak absolute host paths beyond what the tree route
  already exposes.
- Add focused route tests (happy path, outside-root rejection, missing-file 404) + viewer
  render test; `npm run typecheck` green.
