## Decision Question

How should the project preserve existing `_STATUS.md` history prose before running the
`INSP-01` bulk transition that moves all 53 deliverables into `CHECKING`?

## Grounding

`INSP-01a` ran a read-only preflight over all 53 deliverable `_STATUS.md` files. The preflight found:

- all 53 files parse successfully and currently read `IN_PROGRESS`;
- the in-memory `CHECKING` transition would add `Checking Approval SHA`, `Authorization Basis`, and
  `Directive` fields in all 53 files;
- all 53 files would be rewritten by normalization;
- 52 files contain one noncanonical history bullet each that the current parser/writer would ignore
  and drop during live transition.

Representative affected lines include semantic-matrix history notes and PKG-00 reset notes. The
preflight therefore failed the `INSP-01a` gate: predicted diffs are not limited to harmless
normalization plus the expected transition row and fields.

The dry-run used commit `77d7233ff02bcfbb5b691797ef5b04ca097bce43` only as a valid SHA-shaped
formatter input. The owner has not yet blessed an `approvalSha` for `INSP-01`.

`plans/artifacts/insp01a_option_b_canonicalization_preview_2026-06-20.md` shows the concrete
parser-preserved rewrite that would be applied to each affected bullet if Option B is selected.
It is preview evidence only and does not itself authorize or apply the rewrite.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Code-preserve arbitrary history prose | Add narrowly scoped lifecycle parser/writer support that preserves noncanonical history bullets, then rerun `INSP-01a`. | Running `INSP-01` before the rerun passes; broader lifecycle behavior changes; `CHECKING -> ISSUED`; any provider/release/domain scope. |
| B | Canonicalize status history prose before transition | Mechanically rewrite the 52 noncanonical bullets into parser-preserved canonical history entries with the original prose carried in bracketed notes, then rerun `INSP-01a`. | Runtime/source code changes; running `INSP-01` before the rerun passes; `CHECKING -> ISSUED`; any provider/release/domain scope. |
| C | Accept lossy normalization | Explicitly accept dropping the 52 noncanonical history bullets during `INSP-01`. | Any unapproved lifecycle transition beyond `IN_PROGRESS -> CHECKING`; `CHECKING -> ISSUED`; provider/release/domain scope. |
| D | Defer / custom | Keep `INSP-01` blocked and provide a different remediation path. | Any bulk lifecycle transition until the custom path is ruled and validated. |

## Recommendation

Choose **Option B**.

It stays inside the D-APP-19 no-code-development constraint, preserves the historical prose as
filesystem truth, and leaves the actual lifecycle engine untouched. After canonicalization, rerun
`INSP-01a`; only if it passes should the owner confirm the blessed `approvalSha` for `INSP-01`.

Option A is technically robust but crosses into source-code change during a plan that explicitly
disallows code development except for the later PKG-00 control-plane truth-fix. Option C is not
recommended because it knowingly loses history from 52 deliverables.

## Validation Implications

For Option B:

- apply only `_STATUS.md` history-line canonicalization in affected deliverable folders;
- rerun the `INSP-01a` preflight and require zero unparsed history bullets;
- run `git diff --check` over touched `_STATUS.md` files;
- skip frontend runtime tests unless source/runtime files are changed;
- after the rerun passes, require the owner to confirm the one blessed `approvalSha` before `INSP-01`.
