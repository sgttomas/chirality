## Decision to rule

Authorize (or decline) the **multi-engine domain profile registry tranche**: replacing the singleton profile gate in `frontend/src/lib/harness/mcp/read-tools.ts` — which accepts only `profileId === 'open_pipe_stress'` and hard-codes that profile's path (`read-tools.ts:544-553`) — with a small explicit registry (profileId → profile path, engine kind, read-transport binding, gate markers), and exposing the two already-live read tools `domain_completeness_check` and `domain_rule_check_run` for `profileId: 'pec'` over `_DomainEngines/profiles/pec.yaml`.

This is the bridge lane's P1 as adopted (brief §5, lines 106-110): *"replace the singleton profile gate with a small registry (id → profile path, engine kind, transport binding); expose the two read tools for `profileId: 'pec'`. No pec writes; no new live tools beyond the read pair."* The F3 fence was opened by D-T0-08 steps (a)/(b) and the tool family was ruled and landed under D-APP-49/D-APP-50; this tranche adds **no tool name, no exposure-flag change, and no new tool surface** — it changes only which registered profileIds the two live read handlers accept, via a governed registry instead of a hard-coded singleton. It still requires its own owner ruling because it is the first act that binds a second engine (pec) into the domain seam — the cross-project coupling D-T0-19 created the lane for — and because the pec loop's authoring grant is packets-only: app-dev source moves only under a D-APP ruling (`_REGISTER.md:12`).

## Recommendation

Recommend **O-A**, with the riders below as binding conditions of the ruling.

### Registry design (O-A detail)

A new runtime module `frontend/src/lib/harness/mcp/domain-profile-registry.ts` (runtime side, NOT in `@chirality/harness-contract` — the package stays dependency-free and contract-only per D-APP-46, and adding a package file would force a new pull-contract export entry; the registry is dispatch, not contract). Indicative shape (final identifiers are the executing tranche's, within these bounds):

```ts
export type DomainEngineKind = 'deterministic-cli' | 'http-api';
export type DomainReadTransportBinding = 'in-process-read-evidence'; // the ONLY binding literal in P1

export type DomainEngineProfileRegistryEntry = {
  profileId: string;                       // 'open_pipe_stress' | 'pec' — ruled entries only
  profileRelativePath: string;             // resolved against projectRoot, existing-path-contained (realpath check preserved)
  engineKind: DomainEngineKind;            // open_pipe_stress: 'deterministic-cli'; pec: 'http-api'
  readTransportBinding: DomainReadTransportBinding;
  identityMarker: string;                  // exact live-file bytes: 'id: "open_pipe_stress"' / 'id: "pec"'
  toolGate: Record<'completeness_checker' | 'rule_check_runner', {
    requiredMarker: string | null;         // ops: '- id: "completeness_checker"' / '- id: "rule_check_runner"'; pec: null
    declaredDeterministicToolId: string | null; // ops: the profile tool id; pec: null (disclosed in the envelope)
  }>;
  transportStatus: { posture: string; tranche: string; inputContract: string; /* per-entry truthful strings */ };
};
```

**Gate behavior (dispatch through the registry):**

1. **Unregistered profileId** → unchanged refusal, byte-for-byte: `HarnessError('INVALID_REQUEST', 400, 'profileId is not registered for this domain transport', { profileId, supportedProfileIds })` — the delta here is that `supportedProfileIds` truthfully enumerates the registry (`['open_pipe_stress', 'pec']`); this is delta 2a of rider 2's closed delta list.
2. **Registered profile whose file lacks its markers** → for a missing per-tool marker, the unchanged message `'profileId does not expose the requested deterministic tool'`; for a missing identity marker, a truthful distinct refusal (the file at the registered path is not the registered profile). Both remain `INVALID_REQUEST`/400.
3. **Envelope** → per-entry `transportStatus`. The open_pipe_stress strings are preserved verbatim (`status: 'live'`, `posture: 'DEC-041 in-process read transport'`, `tranche: 'D-APP-50 tranche-1 read-side exposure'`, `deterministicToolExecution: 'not invoked …'`, `resultSemantics: '… no domain verdict, no live binding claim, and no professional engineering conclusion'`, inputContract naming `open_pipe_stress.yaml` — `read-tools.ts:571-587`). The pec entry gets its own truthful strings: tranche `'D-APP-51 P1 multi-engine registry read exposure'`; `engineKind: 'http-api'` reported **as registry metadata only** with an explicit statement that no HTTP transport exists or is bound in P1; `deterministicToolExecution` stating verbatim that pec.yaml declares no `completeness_checker`/`rule_check_runner` deterministic tools and that this wrapper returns profile + input evidence envelopes only (`declaredDeterministicToolId: null` carried in the envelope); the same no-verdict/no-live-binding/no-professional-conclusion sentence; `writes: false`, `network: false`, `shell: false` unchanged.
4. **Input handling unchanged**: `inputRef`/`rulePackRef`/`valueBindingsRef` stay project-root-contained JSON references through the existing `readProjectJsonReference` path (realpath containment, SHA-256 evidence, JSON summary — `read-tools.ts:467-532`); no new input surface.

**Disclosed defect fix (V-9):** the registry stores each profile's **exact live-file marker bytes** (quoted YAML form), replacing the shipped unquoted-substring checks that cannot match the live profiles. This changes observable behavior for `open_pipe_stress` against the live tree from *erroneous refusal* to *the acceptance D-APP-50's ruling authorized*; it is one of exactly three disclosed open_pipe_stress-visible deltas (rider 2 enumerates all three — nothing else about the open_pipe_stress path may change), it is disclosed here rather than rolled in silently, and it is pinned by a new regression test against the **real** `_DomainEngines/profiles/*.yaml` bytes (vendored verbatim byte fixtures including the quoted ids, plus a thin marker-sync check against the live files — impl-plan test 2), not only synthetic unquoted fixtures.

**What P1 deliberately does NOT contain:** no pec HTTP client, no login/session code, no network or child-process code of any kind (the tranche adds only file-reading dispatch); no change to which tool names exist or which are exposed to the model (`sdk-options-builder` / allowed-name wiring untouched); no change to `domain_propose_operation`/`domain_proposal_validate`/`domain_headless_preview_run` descriptor-only postures or human gates — their first live exposure is P2 = D-APP-52 under its own ruling (write tools additionally per D-T0-19 O-3A mapping and D-T0-20 O-B bounds).
