# D-APP-18 Decision Packet - Default Provider Cutover After Live Packaged Proof

**Status:** PROPOSAL
**Date:** 2026-06-18
**Decision ID:** D-APP-18
**Prepared by:** WORKING_ITEMS
**Active plan:** `plans/PLAN_2026-06-17_live_packaged_agentsdk_read_tool_proof.md`

**Live proof evidence:** `plans/artifacts/dapp17_live_packaged_agentsdk_read_tool_success_2026-06-18.md`

This packet asks whether the project should now approve a bounded implementation tranche
to make `agentSdk` the default provider after the app-directory packaged live read-tool
proof passed.

It does not itself change the default provider. It does not approve release readiness,
publication, signing, notarization, professional approval, certification, sealing,
authentication, or code-compliance acceptance.

## Decision Question

May a future bounded implementation tranche change the harness default provider from the
current default to the SDK-backed Anthropic `agentSdk` path, now that the packaged live
read-tool proof prerequisite has passed?

## Evidence Since D-APP-12 Hold

Proven before D-APP-18:

- no-live packaged SDK package/native CLI resolver proof under `app.asar.unpacked`;
- controlled `CLAUDE_CONFIG_DIR` and `HOME` propagation in packaged proof;
- app-directory packaged live proof with model alias `sonnet`;
- live SDK stream reported `Read` tool use;
- live SDK stream reported the proof token read from the generated target file;
- generated SDK transcript file was observed under controlled `CLAUDE_CONFIG_DIR`;
- redaction scans reported zero API-key findings across proof output, proof project root,
  controlled `CLAUDE_CONFIG_DIR`, and controlled `HOME`;
- `agentSdk` remains opt-in pending this or a later ruling.

Known limitations:

- mounted-DMG parity was not rerun under D-APP-17 and remains outside the ruling;
- the proof used a disposable generated project and one generated read target, not a full
  user workflow;
- transcript content was not committed to the repository;
- release readiness, signing, notarization, publication, and professional-boundary claims
  remain out of scope.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Approve bounded default-provider cutover implementation | Future tranche may change the harness default provider to `agentSdk`, update docs/control-plane surfaces, and run the relevant runtime/package validation gates. | Provider expansion, remote MCP/plugins/tool search/domain tools, release/professional claims, mounted-DMG parity unless separately selected as validation. |
| B | Continue opt-in hold despite passed proof | No default-provider change proceeds. `agentSdk` remains opt-in; live proof evidence is retained for later review. | Default-provider cutover and governance text declaring SDK default. |
| C | Require additional evidence first | Human names extra evidence such as mounted-DMG live parity, longer workflow proof, network-policy proof, transcript review, or UI-route proof before cutover can be considered. | Any default-provider cutover before the named evidence lands. |
| D | Custom ruling | Human supplies alternate scope, constraints, or sequencing. | Anything not explicitly named by the custom ruling. |

## Recommendation

Choose **Option A** if the project accepts the app-directory packaged live read-tool proof
as sufficient to proceed to a bounded default-provider implementation tranche. That
implementation should remain scoped to default selection, documentation/control-plane
alignment, and validation; it should not broaden providers or release posture.

Choose **Option C** if mounted-DMG live parity or a broader user workflow proof is required
before changing the default.

## Required Constraints If Option A Is Approved

- Implement default-provider cutover in a bounded tranche; do not combine it with provider
  expansion or release-readiness work.
- Keep the first-adapter scope to the existing Anthropic/Claude Agent SDK path.
- Preserve explicit hard-deny policy for remote MCP, plugins, broad tool search, domain
  tools, and professional-boundary changes unless separately ruled.
- Update docs/control-plane surfaces to state the new default only after code and tests
  land.
- Run focused provider/default tests, `npm run typecheck`, and relevant package/harness
  validation selected from `docs/VALIDATION_STRATEGY.md`,
  `docs/RELEASE_QUALITY_GATES.md`, and `docs/BUILD_AND_RELEASE.md`.
