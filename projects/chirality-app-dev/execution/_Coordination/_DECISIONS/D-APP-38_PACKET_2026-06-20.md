## Context / Problem

Each of the 53 deliverables records, in its `_REFERENCES.md` "Authoritative Source Corpus" table, a
pinned `ExpectedSHA256` / `ActualSHA256` / `Status` for seven references: six **living** authority
docs (`docs/DIRECTIVE.md`, `docs/CONTRACT.md`, `docs/SPEC.md`, `docs/TYPES.md`, `docs/PLAN.md`,
`docs/PRD.md`) plus one external file (`agents/AGENT_SOFTWARE_DECOMP.md`).

Live recomputation on 2026-06-20 (plain `sha256`; method confirmed by reproducing REF-007 exactly and
REF-003 from commit `26fc253b5`) shows **six of the seven authority-doc references are stale, but only
REF-006 is flagged**:

| Ref | Doc | Recorded status | Reality (2026-06-20) |
|---|---|---|---|
| REF-001 | `docs/DIRECTIVE.md` | MATCH | **STALE** (`dee943d3…` -> `14c77480…`) |
| REF-002 | `docs/CONTRACT.md` | MATCH | **STALE** (`735a8500…` -> `87955a75…`) |
| REF-003 | `docs/SPEC.md` | MATCH | **STALE** (`ba7a62b2…` -> `b011675b…`) |
| REF-004 | `docs/TYPES.md` | MATCH | **STALE** (`f5ebe645…` -> `7d037b44…`) |
| REF-005 | `docs/PLAN.md` | MATCH | **STALE** (`4a8af7de…` -> `86cb8a69…`) |
| REF-006 | `docs/PRD.md` | **HASH_MISMATCH** | STALE (current `33e00c82…`) — only flagged ref |
| REF-007 | `agents/AGENT_SOFTWARE_DECOMP.md` | MATCH | genuinely matches |

Root cause: the authority docs are actively edited (loop-first pivot, D-APP-18 cutover, K-ENGINE-6 —
some this session), but per-deliverable reference reconciliation has not been re-run since roughly
commit `26fc253b5`. The `Status` column drifts silently and is duplicated across 53 files.

Consequence for inspection trust: INSP-03 read the recorded `Status` column rather than recomputing,
so the "Source-State Caveat" section in all 53 Assessment artifacts under-reported drift (it cited only
REF-006). This is the same class of blind spot as the PKG-09 gitignored-artifact false-absence — the
inspection trusted recorded metadata over recomputed ground truth.

D-APP-35 (Option A, refresh REF-006) was ruled on the incomplete premise that PRD was the lone
mismatch. A REF-006-only refresh would honor the letter of D-APP-35 but leave five stale references
still falsely showing MATCH, hiding the systemic issue behind the one fixed ref.

## Decision Needed

What reference-integrity model should the project adopt for authority-doc references in deliverable
`_REFERENCES.md`, and how should the refresh be scoped and kept honest under it?

## Options

**Option A - Automated reconciliation; keep per-deliverable hash pins.**
Keep the per-deliverable `Expected`/`Actual`/`Status` pins, but add a reconciliation tool that
recomputes every reference and rewrites `Status` (and, on human acceptance, `ExpectedSHA256`) across
all deliverables, run as a validation gate on authority-doc edits / pre-merge / pre-issuance. As a
one-time step, refresh all six stale refs to current.
- Pros: preserves per-deliverable content-binding (a deliverable traces to a known doc version, aligned
  with the project's content-binding intent); drift becomes detectable and visible rather than silent.
- Cons: tool + gate to maintain; references still churn on every authority-doc edit; requires an
  explicit `Expected`-hash update policy (auto-accept current vs human-accept).

**Option B - Versioned / snapshot corpus.**
Pin references to a tagged/frozen authority-doc corpus version (a corpus manifest hash or git tag), not
to the latest mutable file. Deliverables cite "authority corpus vX"; `Expected` stays stable until a
deliberate corpus version bump reconciles all deliverables at once.
- Pros: stable, no per-edit churn; explicit, auditable corpus versioning; deliverables bind to a known
  frozen set.
- Cons: needs a corpus-versioning ritual; deliverables can intentionally lag the latest docs;
  migration to introduce a corpus-version field.

**Option C - Centralized integrity; drop embedded per-deliverable hashes.**
Maintain one authoritative corpus manifest (extend `docs/MANIFEST.json` or a new corpus reference file)
recording each authority doc's current hash, recomputed by tool on a cadence; deliverables reference
docs by ID/path only (no embedded `Expected`/`Actual` columns).
- Pros: single source of truth; removes 53x duplication and drift amplification; simplest to keep
  honest.
- Cons: loses per-deliverable content-binding (cannot tell which doc version a given deliverable was
  decomposed against); migration removes columns from 53 files.

**Option D - Custom / hybrid.**
E.g., Option C's central manifest for current truth plus Option B's corpus-version stamp per
deliverable; or Option A's tool feeding Option B's snapshots.

## Recommendation

**Option A, or a D-hybrid of A+B.** Preserve content-binding (a real governance property) but make it
automatically reconciled and gated so it stops drifting silently; adopt B's corpus-version framing if
per-edit churn proves noisy. If per-deliverable duplication is judged not worth the maintenance,
Option C is the cleanest honest minimum. In all cases, defer the actual refresh until the model is
ruled, then apply it once, uniformly, across all deliverables.

## Risks / Implications

- **Do nothing:** source-state caveats remain systematically wrong; a future `CHECKING -> ISSUED`
  would bind to false "MATCH" reference records.
- **Literal D-APP-35 (REF-006 only):** re-stales on the next PRD edit and entrenches the misleading
  state for REF-001..005.
- Whatever is chosen should build on the existing reconciliation conventions
  (`agents/AGENT_RECONCILIATION.md`, `agents/AGENT_SOFTWARE_DECOMP.md`), not a parallel mechanism.

## Validation Implications

A reconciliation/refresh tranche would touch up to 53 `_REFERENCES.md` files and may add a tool plus a
gate entry in `docs/VALIDATION_STRATEGY.md` / `docs/RELEASE_QUALITY_GATES.md`. No runtime/source
change. Verify by recompute-and-compare; `git diff --check`; no lifecycle transition.
