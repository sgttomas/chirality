## Ruling

Option A is approved.

`STAB-04` may expose bounded local mutating Chirality MCP tools through the formal
handler-level permission/evidence wrapper:

- `mcp__chirality__status_transition`; and
- `mcp__chirality__deps_write`.

Implementation may proceed immediately in stepwise order:

1. `status_transition`;
2. `deps_write`.

MCP-driven `CHECKING` / `ISSUED` lifecycle transitions are allowed only with actor
`HUMAN` and valid `approvalSha` evidence accepted by the existing lifecycle engine.
For this ruling, `approvalSha` is required and sufficient as lifecycle approval
evidence.

`deps_write` may write dependency satisfaction-state changes when the write satisfies
the existing Dependencies.csv v3.1 writer/linter semantics.

## Boundaries

This ruling approves only bounded local mutating Chirality MCP exposure for the two
named tools above. The implementation must keep both tools unavailable unless
explicitly requested in `workspaceWrite` mode.

The implementation must enforce permission, path policy, actor policy, redaction,
bounded diff metadata, and evidence recording inside the mutating MCP handler wrapper.
Raw in-process SDK MCP `mcp_message` calls must not rely on automatic SDK
`canUseTool` or hook callbacks for authorization or evidence.

This ruling does not approve:

- `mcp__chirality__scaffold_exec`;
- remote MCP servers;
- network-capable MCP tools;
- plugins or marketplace work;
- domain-engine protected-path writes;
- concrete non-Anthropic provider implementation or provider routing;
- default-provider cutover;
- provider-network expansion;
- Pi runtime paths;
- release-readiness claims;
- lifecycle issuance;
- professional approval;
- certification, sealing, authentication, or code-compliance acceptance;
- professional-boundary claim changes.
