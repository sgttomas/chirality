# D-APP-32 Decision Packet - Tertiary-Form Affordance & Sidebar Tab Surface

**Decision ID:** D-APP-32
**Prepared by:** WORKING_ITEMS

This packet asks how the demoted `/workbench` and `/pipeline` (and the portal matrix) are surfaced from the right sidebar — and whether that expands the sidebar public tab set. It blocks the tertiary-form affordance in tranche 28d. It does not delete any route or screen.

## Decision Question

How are the demoted tertiary screens (`/workbench`, `/pipeline`, portal matrix, file tree) reached from the right sidebar — new `SidebarTabId` tabs, a single launcher/menu entry, or unchanged top-nav-as-gateway — and does the chosen affordance expand the sidebar tab set?

## Grounding (current state)

- The multi-view sidebar tabs are a fixed `SidebarTabId` union (`src/components/shell/workspace-sidebar.tsx:11-18`): Files, Sessions, Tools, Subagents, Document, Workflow, Tool Kit. Adding workbench/pipeline as tabs expands this union.
- DESIGN §3.2 states the sidebar "is the gateway to tertiary screens (each view can open its full-screen tertiary form)" — the design already anticipates a sidebar view opening a full-screen tertiary form.
- The `/workbench` and `/pipeline` routes are KEPT under D-APP-28/28d (they still render `WorkbenchClient`/`PipelineClient`); only their IA status changes from primary to tertiary.
- Top-nav lives in `ShellFrame` `NAVIGATION_ITEMS` (`src/components/shell/shell-frame.tsx:19-22`): `/`, `/pipeline`, `/workbench` (`/chat` intentionally absent).

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | New sidebar tabs per tertiary screen | Add `workbench`/`pipeline` (and/or portal) to `SidebarTabId` + `SIDEBAR_TABS`, each opening its full-screen tertiary form — directly matches §3.2 "each view can open its full-screen tertiary form." | Keeping the tab set fixed; (accepts) a larger tab bar. |
| B | Single launcher / menu entry in the sidebar | One "Screens" entry lists the tertiary screens (workbench/pipeline/portal/file tree) without one tab each; keeps the tab set small. | A dedicated tab per screen. |
| C | Keep top-nav as the gateway, relabel as tertiary | Sidebar tab set unchanged; `ShellFrame` nav remains the entry, relabeled to reflect tertiary status. Minimal churn. | Making the sidebar the gateway (partly at odds with §3.2). |
| D | Custom | Human supplies alternate affordance. | Anything not named. |

## Recommendation

**Option A**, with B as the fallback if the tab set grows unwieldy. A aligns most directly with DESIGN §3.2 — the sidebar is the gateway to tertiary screens, and each view opens its full-screen tertiary form — so the affordance follows the target IA rather than working around it. Choose **B** if the owner prefers a smaller tab bar and a single "Screens" launcher caps the tab count better than one tab per screen. Choose **C** only when minimizing churn outweighs IA alignment: it is the lowest-churn path but leaves the top-nav (not the sidebar) as the gateway, which is partly at odds with the §3.2 target. Reserve **D** for an alternate affordance the human specifies.

## Required Constraints If A (or B) Is Approved

- Nothing deleted: `/workbench` + `/pipeline` routes stay and still render their clients; every tertiary screen reachable.
- If `SidebarTabId` is expanded, keep the existing WAI-ARIA tabs pattern and per-layout default-tab behaviour.
- No engine / public-contract / permission-plane change.
- `npm run typecheck` + workspace-sidebar / shell tests green.
