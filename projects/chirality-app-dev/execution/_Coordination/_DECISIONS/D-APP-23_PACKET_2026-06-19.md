# D-APP-23 Decision Packet - Portal Launch Model & Sidebar Placement

**Status:** PROPOSAL
**Date:** 2026-06-19
**Decision ID:** D-APP-23
**Prepared by:** WORKING_ITEMS
**Active design:** `plans/DESIGN_2026-06-18_agent_orchestration_ui.md` (§3.1 primary loop, §3.3 portal, §5.2 transitional sidebar-left note, §6)

This is the largest architectural fork remaining: whether the app stays navigation-centric
(routes) or pivots so the live loop is the primary surface with in-place session provisioning.
It gates Phase 5 and whether the sidebar moves from left to right.

## Decision Question

How does an operator launch work from the portal: matrix-cell route navigation (`router.push`,
today) vs in-place session provisioning that focuses the live loop without a full route change?
And does the multi-view sidebar stay on the left or move to the right of the primary loop?

## Grounding (current state)

- `src/components/portal/agent-matrix.tsx` uses `useRouter().push(target)` to
  `/workbench?agent=…` and `/pipeline?category=…`; the route's `children` is still the main
  execution surface and the live loop is the Chat panel beside it.
- DESIGN §5.2 records the sidebar is **transitionally on the LEFT** because the target IA
  ("sidebar on the right of the primary screen") assumes this very routing decision — main =
  the loop. The placement is intentionally not forced until this is ruled.
- The three routes (portal `/`, `/workbench`, `/pipeline`) all work today.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Keep matrix-cell `router.push` (status quo) | Navigation-centric; loop stays a panel within each route; sidebar stays LEFT. | Loop-as-primary pivot; sidebar-right relayout. |
| B | In-place session provisioning (loop-first) | A matrix cell boots a session and focuses the live loop in place (no full route change); loop becomes the primary surface; sidebar moves RIGHT per target IA. | Preserving the current route-as-main-surface model for those entries. |
| C | Hybrid migration | Keep routes for tertiary screens (workbench/pipeline) but add a loop-first "start session" entry from the portal; relayout sidebar to right only for the loop-first surface. | A full removal of route navigation. |
| D | Custom | Human supplies alternate model/sequencing. | Anything not named. |

## Recommendation

**Option C (hybrid).** It is the lowest-risk path to the owner's stated end-state (the live
loop as the primary surface): it preserves the three working routes and the tertiary screens
while introducing the loop-first entry and the sidebar-right relayout incrementally, so Phase 5
can land without a big-bang rewrite. **B** is the eventual destination and is the right ruling
if the owner wants to commit to loop-first now and accept reworking the route surfaces. **A**
only if the navigation-centric model is preferred long-term (which conflicts with the §3.1
target IA). This ruling also resolves the §5.2 sidebar left→right question.

## Required Constraints If C (or B) Is Approved

- Keep in-flight turns alive across any relayout (chat stays mounted, as it already does when
  the sidebar collapses).
- Fix the broken EVALUATIVE matrix cells as part of, or before, the portal rework (tracked in
  Phase 5 / §3.3).
- Preserve the public UIEvent contract and the permission plane unchanged; this is a
  routing/layout change, not an engine change.
- `npm run typecheck` + layout-geometry/route tests green.
