# D-APP-12 Decision Packet - Default Provider Cutover To `agentSdk`

**Status:** PROPOSAL
**Date:** 2026-06-16
**Prepared by:** WORKING_ITEMS
**Active plan item:** `STAB-02` SDK Runtime Readiness & Default-Provider Cutover Decision

This packet asks whether Chirality should change the default harness provider from the
current default to the SDK-backed Anthropic path selected by
`CHIRALITY_HARNESS_PROVIDER=agentSdk`.

## Decision Question

May the app make `agentSdk` the default provider, and may governance text declare the
SDK-backed Anthropic path the active default runtime?

## Current Evidence State

Landed evidence:

- STAB-02(a): active-turn API-key injection for `ClaudeAgentSdkManager` landed and
  validates that the SDK `query()` call sees the resolved key while prior env state is
  restored and persisted error evidence is redacted.
- STAB-02(b): route-level opt-in `agentSdk` scripted dev turn landed. It exercises the
  real SDK `query()` path while replacing only the SDK subprocess with an offline
  deterministic subprocess.
- STAB-02(c): opt-in `agentSdk` network proof landed through
  `proof:network-policy -- --provider agentSdk --scripted-agent-sdk`, with loopback /
  `api.anthropic.com` allowlist evidence and no non-allowlisted TCP endpoints.
- Section 8 and Section 9 harness validation have passed in recent runtime-stabilization
  tranches.
- STAB-05 persona-composer runtime context has landed, so scripted SDK turns now run with
  governed persona context.

Missing evidence:

- STAB-02(d) packaged subprocess proof has **not** landed.
- There is no recorded `asarUnpack` validation for
  `node_modules/@anthropic-ai/claude-agent-sdk/**`.
- There is no recorded packaged app turn proving the SDK CLI subprocess resolves from
  `app.asar.unpacked`.
- There is no recorded packaged HOME/transcript proof for the SDK subprocess.
- There is no recorded `desktop:pack` / `desktop:dist` packaged SDK subprocess evidence.

## Authority Basis

- `execution/_Coordination/_DECISIONS/D-APP-11_RULING_2026-06-16.md` accepted the Runtime

- `plans/PLAN_2026-06-16_runtime_stabilization.md` says `agentSdk` remains opt-in until
  STAB-02(a)-(d), Section 8, and Section 9 are green.

  first-adapter probe and states the default remains unchanged unless a later bounded
  runtime tranche changes it.

## Blocks

Until D-APP-12 is ruled, do not implement or document:

- `agentSdk` as the default harness provider;
- `agentSdk` as the shipped active default runtime;
- governance wording that declares SDK-backed Anthropic execution complete or default;
- release-readiness claims based on the SDK path;
- packaged SDK subprocess acceptance;
- provider-network expansion beyond the existing approved Anthropic path;
- concrete non-Anthropic provider routing;
- Pi adapter, fork, package import, sidecar, runtime-floor migration, or spike.

## Recommendation

Approve **Option B**.

Rationale: the dev/scripted SDK path has meaningful evidence, but the default provider is
load-bearing runtime behavior. The active plan identifies packaged subprocess resolution,
HOME/transcript behavior, asar layout, signing, and packaged execution as the remaining
risk. Cutting over before STAB-02(d) would convert an opt-in probe into the default
without proving the packaged execution path.

If the human wants the SDK path to remain experimental for the rest of this stabilization
program, approve **Option C** instead.

## Required Implementation Constraints If A Later Cutover Is Approved

- Default-provider source changes must be limited to the provider resolver and directly
  related tests/docs.
- `agentSdk` cutover must not imply concrete non-Anthropic provider support.
- `agentSdk` cutover must not imply provider-network expansion beyond the approved
  Anthropic path.
- `agentSdk` cutover must preserve API-key redaction and active-turn env restoration.
- `agentSdk` cutover must preserve tool descriptor, permission overlay, hook, MCP,
  subagent, and network-denial policies already landed.
- Fallback behavior must be explicit: either no fallback, fallback to the existing
  default only on configured failure classes, or a human-named alternative.
- No release-readiness, lifecycle issuance, professional approval, certification, sealing,
  authentication, code-compliance, or professional-boundary claim is implied.

## Validation Implications

Minimum validation before any default-provider cutover implementation should be accepted:

- STAB-02(d) packaged subprocess proof:
  - `npm run build`;
  - `npm run desktop:pack`;
  - launch packaged directory build;
  - run one read-tool `agentSdk` turn;
  - confirm SDK subprocess resolves from `app.asar.unpacked`;
  - confirm SDK transcript/HOME path is resolvable and policy-compliant;
  - `npm run desktop:dist`;
  - repeat packaged `agentSdk` turn from the distributable path or record the exact
    blocker.
- `npm run harness:validate:agentsdk-dev-turn`;
- `npm run proof:network-policy -- --provider agentSdk --scripted-agent-sdk`;
- `npm run typecheck`;
- `npm run test`;
- `npm run harness:validate:premerge`;
- `npm run instruction-root:integrity`.

Run a live-provider proof only if the human explicitly approves live API use for the
cutover evidence. Otherwise keep deterministic scripted evidence separate from packaged
subprocess evidence.
