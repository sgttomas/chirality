## Recommendation

Recommend **O-A**, with the riders below as binding conditions of the ruling.

### O-A design (bounds the executing tranche; exact file/function detail is the tranche's, inside these bounds)

**1. Transport client** — new runtime module `frontend/src/lib/harness/mcp/pec-bridge-client.ts` (runtime side only; the dependency-free `@chirality/harness-contract` package gains **no** transport code, preserving the D-APP-46 posture):

- **Loopback by construction:** base URL is always `http://127.0.0.1:<port>`; the constructor takes a port (from `CHIRALITY_PEC_PORT`, default 4810; validated integer 1–65535) and **has no host parameter**. No redirect following.
- **Endpoint allowlist by construction:** the client exposes exactly four operations — `login()`, `createProposal(projectId, contract, csv, sourceName?)`, `refreshProposal(projectId, proposalId, expectedVersion)`, `getProposal(projectId, proposalId)` — each building its own method+path internally. No generic `request(method, path)` is exported; no list, export, intake, accept, reject, or apply method exists. (The D-T0-20 O-B structural bound, brief §6; `login` is the brief-§3 identity/session design, while the three data endpoints are the §4-mapped set the §6 bound enumerates.)
- **Identity & secret handling:** credentials come from the harness host's local environment (`CHIRALITY_PEC_AGENT_EMAIL`, `CHIRALITY_PEC_AGENT_PASSWORD`), read only inside `login()`, never committed, never logged, never placed in tool results, harness events, error details, or the model context. The login response body (which carries the session identity) is **not** propagated into any tool result. The account is the owner-provisioned agent person (D-PEC-10 actor model: own person record, `is_admin=0`, coordinator-class grant carrying `import.propose`, never `import.accept`).
- **Session:** the `pec_session` cookie is held in client memory only; on a `401`, re-login **once** and retry the request **once**; never persisted to disk; discarded with the client.
- **Error taxonomy** (surfaced to the model as structured tool results, per brief §3): `401` → one re-auth cycle, then `auth_failed` reported; `403` → engine refusal reported verbatim, **never escalated or retried**; `400` → contract/echo mismatch reported; `409 STALE_PROPOSAL` → reported as **normal flow** (`normalFlow: true`, guidance: "refresh the dry-run; a human re-reviews and re-accepts in pec"); `409` version conflict → reported; `5xx`/network → reported once, **no retries** (no retry storms). The client sends no `Origin` header (Node fetch default), which the pec RV-21 guard permits for programmatic clients — recorded honestly in the envelope, not hidden.
- **Server lifecycle:** the client never starts, stops, or owns any pec server or DB. Hermetic tests and the rehearsal spawn a scratch-DB server (O-2B-style, D-PEC-06 seed guard) under this same client and actor model — tests only, never the owner's instance.

### Riders (binding conditions of an O-A ruling)

1. **Sequencing:** the tranche executes only after the **D-APP-51** (P1 registry) tranche has landed, and consumes the registry it lands — no parallel or interim second gate mechanism (the D-APP-50-after-D-APP-49 sequencing precedent, D-APP-50 rider 1).
2. **Secret handling:** credentials only from local environment variables; never committed, never in tool results, harness events, error payloads, logs, evidence artifacts, or the model context; the login response is never propagated into tool results; the repo secret-scan check (`proof:secret-scan`) and an explicit redaction unit test cover the client's error paths.
3. **Loopback only:** the client constructs `http://127.0.0.1:<port>` and structurally cannot accept another host; no redirect following; port from local config (default 4810). Any non-loopback reach is a new D-APP row.
4. **Endpoint allowlist:** exactly login + propose + refresh + get-proposal, each a dedicated method (login per brief §3 identity design; the three data endpoints are the brief-§4-mapped set the §6 bound enumerates); no generic request surface is exported or reachable from handlers. Any additional endpoint (list, exports, Explain, intake, …) is its own future D-APP row re-checked against the D-T0-20 O-B bound (brief §6).
5. **No apply, ever, here — and no force anywhere:** accept, apply, reject-of-others, and `force` are not registered as tools, not implemented as client methods, and not reachable through any code path this tranche adds. Any future exposure is its own PROPOSAL packet (D-APP-50 rider-2 precedent; K-DOMAIN-3). Additionally, and covering acts **outside** the tool surface: every demo-cast apply call in any rehearsal, test, or script under this tranche passes `force: false`; `force=true` never occurs in any form (the Receipt 32 exclusion is absolute and carries no scratch carve-out; pec's apply takes `force` at `projects/pec/server/src/services/proposals.ts:178`), and the evidence manifest records the force value on every demo-cast apply disclosure line.
6. **409 as normal flow:** `STALE_PROPOSAL` is surfaced as the ruled recovery loop (refresh → human re-review/re-accept), marked `normalFlow: true` with that guidance — never retried around, never presented as a transport failure; no automatic retries on any 4xx/5xx beyond the single 401 re-login cycle.
7. **Validate stays read-grade:** `domain_proposal_validate` performs only `GET`; tests pin that it never issues a POST and never triggers a recompute (brief §8 risk 5); refresh rides only the write-graded tool.
8. **Hermetic spawn for tests only:** any spawned pec server runs against a D-PEC-06-guarded scratch DB on a loopback port and is torn down by the test/rehearsal; the harness never starts, stops, or owns the owner's real server or DB, and nothing in shipped runtime code spawns a server.
