## Ruling

The R6 Extensibility & MCP Boundary Maturity Plan
(`plans/PLAN_2026-06-17_r6_extensibility_mcp_boundary.md`, tranches R6-01 through R6-05)
is **accepted as the active development queue**. It is the next bounded program after the
Runtime Stabilization program (STAB-00..STAB-06) completed and closed. `WORKING_ITEMS`
may select and execute its tranches per the plan's sequencing (§6), starting with R6-01
(the collision-prevention invariant).

The coordination surfaces (`execution/_Coordination/_COORDINATION.md`,
`NEXT_INSTANCE_PROMPT.md`, and `_LATEST.md`) are updated to point to this plan as the
active queue.

Deliverable-binding (per plan §8): R6-01 (collision invariant) is tracked under
**DEL-06-02** (SDK Read Tool Surface and Tool Validation); the catalog and contributor
documentation are tracked as governance artifacts under `docs/PLAN.md` §R6 and SOW-064,
**without** a decomposition amendment. No new `DEL-06-07` is created at this time.

## Boundaries

This ruling accepts the *program structure and tranche selection* only. R6 exposes **no
new capability**. It does **not** approve, and the following remain out of scope until a
governed future amendment (plan §7):

- remote MCP servers, plugin marketplace, or remote execution;
- broad tool search (the fence remains; maturing local tool governance is R6's purpose,
  but lifting the fence is a separate future ruling);
- `mcp__chirality__domain_*` domain tools (gated on the R7 domain-profile amendment);
- default-provider cutover (held by D-APP-12 Option B; `agentSdk` stays opt-in);
- shipped `bypassPermissions` ordinary workflow;
- concrete non-Anthropic provider implementation or provider routing;
- any change to the professional/reliance boundary (CONTRACT K-AUTH-1, K-PROF-1);
- release-readiness, lifecycle issuance, professional approval, certification, sealing,
  authentication, or code-compliance claims.

## Required Next Action

`WORKING_ITEMS` may select **R6-01 — Collision-Prevention Invariant** as the first
bounded tranche: harden `createDescriptorLookup` to fail closed on duplicate

new tool is exposed and no permission/path/network behavior changes.

## Validation Requirements

R6-01 and R6-02 (catalog) are code/test tranches: `npm run test` (new uniqueness,
disjointness, parity, and catalog-matches-registry tests) and `npm run typecheck`. R6-03
(contributor guide) and R6-05 (refresh/closeout) are governance-only and use static checks
with frontend tests explicitly recorded as skipped. R6-04 (optional module organization)
additionally runs `npm run harness:validate:premerge` to confirm the tool surface is
unchanged. `proof:network-policy` and packaging are not in scope for R6.
