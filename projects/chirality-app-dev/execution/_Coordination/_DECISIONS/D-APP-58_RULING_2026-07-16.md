## Agent selection under delegated latitude

**Location convention (agent's decision):** the deterministic domain-engine
adapter manifest for a registered profile is assigned the fixed conventional
path `_DomainEngines/profiles/<profileId>.adapter.yaml` (e.g.
`_DomainEngines/profiles/open_pipe_stress.adapter.yaml`,
`_DomainEngines/profiles/pec.adapter.yaml`).

**Schema id (agent's decision):** `domain-engine-adapter-manifest/v1` — a
named, versioned obligation. Declared minimum content: a versioned `schema:`
string; a `profile_id` binding to the adopted profile; per-tool adapter
bindings for each of the profile's `deterministic_tools[]` entries (tool
`id`, invocation/transport binding, and `validate_result_schema` /
`apply_result_schema` refs — explicit `TBD` permitted, never inferred from
chat); a boundary-notice reference; and an authority-class header ("adapter
configuration authority only; never domain truth or lifecycle"). Full field
design, the loader, and deterministic validation-in-code are deferred to the
future governed tranche that authors the first manifest instance.

**The assignment is declarative only.** No manifest file, loader, or
validator is created by this tranche. Manifest instances are authored under
engine-side / tier-0 bridge authority in a fresh governed tranche
(K-ENGINE-6); this project never writes `_DomainEngines/**` (F-APP-3).

### Rationale

1. **K-DOMAIN-1 places manifests on the Chirality-governed side.**
   `docs/CONTRACT.md` K-DOMAIN-1: domain engines own authoritative domain
   truth; Chirality "governs interaction, profiles, manifests, proposals,
   review notes, records, and human gates." An adapter manifest is
   Chirality-governed bridge configuration — the same authority class as the
   owner-endorsed type (`_harness/adapter.yaml`: "harness configuration
   authority only, never lifecycle or project truth"). Placing it inside
   engine trees would put a Chirality-governed artifact under engine-owned
   `protected_write_paths` and does not generalize to the http-api `pec`
   engine, which has no filesystem engine tree. A new profile-declared field
   would require amending TYPES §11.1 (pinned to framework
   `agents/AGENT_DOMAIN_ENGINE.md`), the framework-owned validator
   `tools/validation/validate_domain_engine_profile.py` (outside the app-dev
   write fence), and the D-APP-49 inert type mirror — all excess scope for no
   deterministic gain.
2. **Beside-the-profile placement reproduces the owner-endorsed type pattern
   faithfully:** a fixed conventional path deterministically derivable from
   `profileId` alone (PRD FR-109), the same derivation the closed registry
   already uses for `profileRelativePath`
   (`frontend/src/lib/harness/mcp/domain-profile-registry.ts`), a versioned
   schema string, and code validation by a future loader. Creation authority
   is the tier-0 bridge loop, which owns `_DomainEngines/**` writes.
3. **Schema fields trace to accepted sources only:** TYPES §11.1
   `deterministic_tools[].{validate,apply}_result_schema` (TBD-permitted,
   never chat-inferred), SPEC §18's pairing of "deterministic adapter
   manifests" with "boundary notices," and K-DOMAIN-4's professional
   boundary.
