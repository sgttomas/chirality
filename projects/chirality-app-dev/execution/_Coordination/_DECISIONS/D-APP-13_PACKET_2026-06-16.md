# D-APP-13 Decision Packet - Mutating Chirality MCP Exposure

**Status:** PROPOSAL
**Date:** 2026-06-16
**Prepared by:** WORKING_ITEMS
**Active plan item:** `STAB-04` Deterministic Chirality MCP Maturity

This packet asks whether bounded mutating Chirality MCP tools may move from
metadata-only / absent runtime posture to explicit `workspaceWrite`-gated exposure.

It does not approve implementation by itself. Only a human ruling record can approve the
selected option.

## Decision Question

May STAB-04 expose bounded local mutating Chirality MCP tools:

- `mcp__chirality__status_transition`; and
- `mcp__chirality__deps_write`;

using a handler-level permission/evidence wrapper, and may `status_transition` perform
human-gated `CHECKING` / `ISSUED` lifecycle transitions when supplied an `approvalSha`?

## Blocks

Until this packet is ruled, do not implement or expose:

- model-visible `mcp__chirality__status_transition`;
- model-visible `mcp__chirality__deps_write`;
- a mutating Chirality MCP server/tool registry;
- a mutating MCP handler wrapper that can write `_STATUS.md` or `Dependencies.csv`;
- MCP-driven `CHECKING` or `ISSUED` lifecycle transitions;
- MCP-driven dependency-register writes;
- optional `mcp__chirality__scaffold_exec`;
- remote MCP servers, network-capable MCP tools, plugins, marketplace install, or
  domain-engine protected-path writes;
- default-provider cutover or any D-APP-12 outcome.

- Chirality read MCP tools are already exposed and evidence-wrapped in

## Current Baseline

Landed posture:

- read-only Chirality MCP tools (`status_read`, `deps_read`, `scope_scan`,
  `scaffold_preview`) are exposed only when explicitly requested;
- mutating Chirality MCP tools are not exposed;
- lifecycle and dependency write engines exist as local library code and are tested;
- `canUseTool` and hook evidence work for explicit SDK callback requests, but raw SDK
  in-process MCP messages do not automatically pass through those callbacks;
- `agentSdk` remains opt-in; default-provider cutover remains blocked by D-APP-12;
- no remote MCP, plugin, marketplace, provider-network, Pi runtime, release-readiness, or
  professional-boundary expansion is approved.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Approve stepwise `status_transition` and `deps_write` exposure | Future STAB-04 implementation may add descriptors, tool names, mutating MCP server wiring, and handler-level permission/evidence wrapping for `status_transition` first, then `deps_write`, both `workspaceWrite`-gated and off unless explicitly requested. `CHECKING` / `ISSUED` may proceed only with actor `HUMAN` and valid `approvalSha` evidence accepted by the existing lifecycle engine. | `scaffold_exec`, remote/network MCP, plugins, marketplace, domain-engine protected-path writes, provider/default cutover, release/professional claims. |
| B | Approve `status_transition` only | Future work may expose only `mcp__chirality__status_transition` with handler-level permission/evidence wrapping. | `deps_write`, `scaffold_exec`, remote/network MCP, plugins, provider/default cutover, release/professional claims. |
| C | Approve mutating tools but deny MCP-driven human-gated lifecycle transitions | Future work may expose `status_transition` only for non-human-gated transitions allowed by the existing engine, and may expose `deps_write` if separately implemented with wrapper evidence. | MCP-driven `CHECKING` / `ISSUED`, `scaffold_exec`, remote/network MCP, plugins, provider/default cutover, release/professional claims. |
| D | Keep mutating Chirality MCP metadata-only / unexposed | No mutating Chirality MCP source implementation proceeds. Future work must select another unblocked tranche or return with a narrower packet. | All mutating MCP exposure. |
| E | Approve a narrower custom path | A ruling may name only a subset, additional evidence prerequisite, actor rule, or implementation order. | Anything not explicitly named by the custom ruling. |

## Recommendation

Approve Option A with stepwise implementation.

Rationale: the write engines already exist and are unit-tested; STAB-04 is about bounded
MCP exposure, not new lifecycle or dependency semantics. The SDK behavior probe shows that
mutating MCP safety cannot rely on automatic SDK permission/hook callbacks around raw
MCP messages, so the implementation must enforce permission, path policy, actor policy,
diff metadata, redaction, and audit evidence inside the mutating MCP handler wrapper.

If the human does not want MCP tools to perform `CHECKING` / `ISSUED`, approve Option C
instead. The implementation should not infer that authority from `approvalSha` alone
unless the ruling explicitly allows it.

## Required Implementation Constraints If Approved

- Mutating MCP tools must be unavailable unless explicitly requested in `workspaceWrite`
  mode.
- Handler-level wrapper must record permission/evidence because raw MCP messages do not
  automatically invoke SDK `canUseTool` or hooks.
- Wrapper evidence must store metadata only: input summaries, path metadata, before/after
  SHA and byte length, bounded diff summary, error class, duration, and result summary.
- Raw `_STATUS.md`, raw `Dependencies.csv`, raw full diffs, raw SDK transcripts, secrets,
  and unbounded tool outputs must not be stored in project truth.
- Path policy must preserve project-root containment, instruction-root denial for writes,
  and symlink-write denial.
- `status_transition` must reuse `transition.ts` gates verbatim.
- `deps_write` must reuse the Dependencies.csv v3.1 writer/linter semantics and row
  preservation rules.
- `scaffold_exec` remains denied unless a later ruling explicitly approves it.
- No provider/network/Pi/release/professional-boundary expansion is implied.

## Validation Implications

Minimum validation for any approved implementation:

- `npm run harness:validate:agentsdk-mcp-probe`;
- focused tests for tool descriptors, tool-name filters, SDK option exposure, permission
  denial in non-`workspaceWrite` modes, unknown/denied tools, path containment,
  instruction-root and symlink denial, event evidence, redaction, and result artifact
  budgets;
- lifecycle transition tests for allowed path and each denial code:
  `UNAUTHORIZED_ACTOR`, `BACKWARD_TRANSITION`, `TRANSITION_NOT_ALLOWED`,
  `APPROVAL_SHA_REQUIRED`, and `INVALID_APPROVAL_SHA`;
- dependency writer tests for schema/enum/provenance/target failures, duplicate IDs,
  satisfaction-transition preservation, row preservation, and host-deliverable checks;
- `npm run typecheck`;
- `npm run test`;
- `npm run harness:validate:premerge`;
- `npm run instruction-root:integrity`.

Run `npm run proof:network-policy` only if implementation touches provider, network,
API-key, or outbound behavior.
