# D-APP-39 Packet - Release an Autonomous Development Queue

**Status:** PROPOSAL / AWAITING_RULING
**Date:** 2026-06-20
**Decision ID:** D-APP-39
**Prepared by:** WORKING_ITEMS

## Context / Problem

The D-APP-19 inspection program and the P0 governance cluster are complete. A prioritized,
dependency-ordered development roadmap exists (`plans/artifacts/insp05_development_roadmap_2026-06-21.md`,
P1-P3). But the loop is configured **decision-first**: `NEXT_INSTANCE_PROMPT.md` Selection Rule 2 says
"Do not select autonomous implementation work. Next work requires explicit roadmap-item selection or a
new human directive," and Execution Rules say "Stop when any further progress requires a human ruling."
So roadmap implementation has not proceeded autonomously — by configuration, not by technical limit.

The owner wants to release an autonomous development queue that pulls roadmap work and executes it
without per-tranche human selection.

## Decision Needed

Whether to release an autonomous development queue, at what execution scope, and with what commit
authority — and what guardrails and stop conditions bound it.

## Options Considered

**Execution scope:** (A) reversible layer only; (B) reversible + self-contained runtime code under
validation gates; (C) everything except the hard fences.

**Commit authority:** (1) stage only, human commits; (2) commit locally, human pushes; (3) commit and
push validated tranches autonomously.

## Ruling (owner directive, 2026-06-20)

**Scope C + Commit 3:** the autonomous queue may execute **all roadmap work except the hard fences**,
and **commits and pushes** each validated tranche autonomously. (Recorded in `D-APP-39_RULING_2026-06-20.md`.)

## Hard Fences (always HUMAN-GATED; never autonomous)

1. Provider/network expansion beyond the current Anthropic path.
2. Release/distribution posture: signing, notarization, publication, external distribution, or any
   release-readiness / professional / certification / sealing / authentication / code-compliance claim.
3. R7 domain-engine implementation (protected-path mutation, OperationProposal runtime workflow, solver
   integration); PKG-10 stays future-boundary/doc-only.
4. Deliverable issuance: any `CHECKING -> ISSUED` transition.

Plus the standing **governance-decision gate**: the agent still does not self-rule. A genuinely new
decision (a design fork with material trade-offs not covered by an existing ruling) is raised as a
`PROPOSAL` packet; the agent marks that item `BLOCKED`, continues with other eligible items, and stops
when only blocked/fenced items remain.

## Guardrails

- **Per-tranche validation must pass before commit:** runtime/UI -> `tsc` typecheck + `vitest` (full or
  cited-scope with rationale) + `next build`/`desktop:pack`/`harness:validate:premerge` where applicable
  + the D-APP-36 component/render bar for UI; governance/docs -> `git diff --check` + reference/link
  checks + the D-APP-38 reconciliation tool for authority-doc edits.
- **Recompute, do not trust recorded metadata.** The inspection's two blind spots (gitignored packaging
  artifacts read as absent; stale reference hashes read as MATCH) must not recur: verify against the
  filesystem/tests, not status columns.
- **Shared-repo discipline (critical for autonomous push):** stage only `projects/chirality-app-dev/`;
  run `git diff --cached --name-only` and abort the commit if anything outside that path is staged;
  never commit `projects/chirality-piping/**` or repo-root `tools/**`.
- **K-ENGINE-6 strategic lens:** build governance/UI/audit/lifecycle/adapter value over provider harness
  mechanics; do not build a standalone general harness or chase Claude Code / Pi / Codex parity.
- **Closeout per tranche:** CHANGE-agent git/file-state review; commit message ending with the
  Co-Authored-By trailer; push; update the queue artifact and completion log.

## Stop Conditions

A hard fence; a new decision; a validation failure that cannot be repaired within the tranche; an
out-of-`app-dev` staging stray; an empty eligible queue. On stop, surface state and the decision/blocker
queue; do not invent work or revive completed plans.

## Risks

- **Blast radius:** autonomous push of runtime changes in a shared repo. Mitigated by validation gates,
  the staging discipline, and per-tranche commits (small, revertable units).
- **Regression on the irreversible layer:** mitigated by typecheck/test/build gates and CHANGE-agent
  closeout.
- **Decision stalls:** if many items need rulings the queue drains to blocked items and stops; the owner
  rules a batch (as with D-APP-34..37) and the queue resumes.
