# D-APP-26 Decision Packet - Document Editor Build & Content-Write Contract

**Status:** PROPOSAL
**Date:** 2026-06-19
**Decision ID:** D-APP-26
**Prepared by:** WORKING_ITEMS
**Active design:** `plans/DESIGN_2026-06-18_agent_orchestration_ui.md` (§3.2 Document view, §3.3 Document + copilot editor, §5 step 4)
**Depends on:** D-APP-21 (RULED: CodeMirror markdown-source when built; editor inert until content write is authorized; edits never trigger governance transitions) and D-APP-20 (RULED Option B: the content endpoint is a READ-ONLY batch GET)

This packet asks whether to build the editable document screen now and — the gating sub-decision — whether to authorize a content-WRITE path, with what scope and governance boundary. D-APP-21 already fixed the editor technology (CodeMirror 6 markdown-source); D-APP-20 shipped content as read-only, so a working editor requires a new write contract. It does not approve any governance-state transition.

## Decision Question

Should the editable document screen be built now, and is a content-WRITE path authorized? If so, with what scope (which files) and what governance boundary?

## Grounding (current state)

- Phase 4 shipped read-only: `readDeliverableContent` + `GET /api/working-root/deliverable/content` is **GET-only** (verified — no PUT/PATCH), reusing `readRequiredFile` + canonical-dir path guards; `DocumentView` (sidebar Document tab) reuses `chat-markdown`. No editor dependency was added (D-APP-21).
- D-APP-21 RULED the technology: a **CodeMirror 6 markdown-source** editor when built, chosen because deliverables are governed markdown source where round-trip fidelity + clean git diffs matter. It also constrained: the editor is an **inert read-only buffer until content write is authorized**; document edits **never** perform governance-state transitions; bound the dependency + record bundle-size against the Electron build gates.
- Deliverable bodies are governed markdown/CSV (`_STATUS.md`, `Dependencies.csv`, and the four doc-type bodies `Datasheet`/`Specification`/`Guidance`/`Procedure.md`) that flow through git and `status/transition` gating; `CHECKING`/`ISSUED` require `actor=HUMAN` + `approvalSha` (K-GATE-1, via `src/app/api/working-root/deliverable/status/transition`).
- DESIGN §3.3 sequences the doc-copilot screen as: content API -> markdown viewer (DONE) -> editor -> embedded scoped chat (`WORKING_ITEMS`) reusing the turn engine.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Build the CodeMirror editor now + a narrowly-gated content-write API | A new write endpoint (PUT/PATCH) persists the deliverable **body file only**, reusing the read route canonical-dir + post-realpath validation; writes are ordinary file writes that flow through git; the editor NEVER mutates governance state; write is gated behind operator mode (gated-write/autonomous) and/or an inline approval card. Enables in-app authoring. | Any write to `_STATUS.md` governance fields or any state transition outside the existing `status/transition` route; write in read-only/plan mode. |
| B | Build the editor now but write-disabled (inert buffer, per D-APP-21) | The CodeMirror editing UX is previewable but cannot persist; the write API is deferred to a later content-write ruling. | Any persistence of edits. |
| C | Defer the editor tranche entirely (status quo: read-only viewer) | Nothing new; revisit when an authoring need is concrete or with the secondary phase. | Any in-app document editing. |
| D | Custom | Human supplies alternate scope/sequencing. | Anything not named. |

## Recommendation

**Option A with the constraints below if in-app authoring is wanted now; otherwise C.** A is the only option that yields a usable editor, but it crosses the read-only line D-APP-20 deliberately drew, so it must be ruled explicitly and scoped tightly: body-only, path-guarded, governance state untouched, operator-mode-gated. A write-disabled editor (B) has little standalone value over the shipped read-only viewer, so B is rarely the right stopping point — it makes sense only when the team wants to validate the CodeMirror UX before committing to a write contract. Pick C if the editor is lower priority than the other deferred follow-ons (the pivot / secondary phase) and authoring is not yet a concrete need.

## Required Constraints If A (or B) Is Approved

- The write endpoint reuses the read route canonical-dir + post-realpath validation (reject leaf- and dir-component-symlink escapes); body files only.
- The editor and its write path **never** touch governance state: `CHECKING`/`ISSUED` stays on the existing `status/transition` route with `actor=HUMAN` + `approvalSha` (K-GATE-1).
- Write is gated by operator mode (no writes under read-only/plan); consider an inline approval card consistent with the permission plane.
- Bound the CodeMirror 6 dependency and record its bundle-size impact against the Electron build gates.
- `npm run typecheck` + focused editor/write-route tests (incl. path-guard + governance-isolation cases) green.
