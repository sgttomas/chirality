## Selected semantics

### B1 — App affected-client envelope plus separate Root routes

App selects the prospective client, policy, presentation, packaging, and
conformance posture stated by the remaining selected tokens. Root separately
decides generic sandbox/runtime semantics, Root compatibility and sandbox
identity, DEL-02-06 activation, and any doctrine amendment. This ruling changes
no Root authority byte and creates no Root approval.

### V1 — Root-conditioned Pi `0.82.0` App compatibility target

Pi `0.82.0` is accepted prospectively as the App compatibility target only
after Root accepts the same adapter identity and the required supply-chain,
native-primitive, sandbox, security, packaging, regression, and conformance
evidence passes. The ruling does not itself reconcile or release the existing
`0.80.10` authority versus `0.82.0` executable-surface conflict.

### P1 — Pi-native-first primitives behind Chirality contracts

The target posture reuses Pi's agent/model/session/tool loop and conforming
native Read/Write/Edit/Bash implementations inside the selected sandbox
architecture. Chirality retains public tool identity and schema, versioned
registration and exposure policy, pre-execution authorization, path/mount
derivation, human gates, result limits and redaction, canonical events,
evidence, interruption, and audit.

Each accepted versioned capability profile maps a public tool identity to
exactly one conforming implementation family. An unavailable, failed, or
non-conforming selected implementation fails closed; there is no silent
runtime fallback or substitution. An implementation-family change requires a
new accepted profile/registration, renewed evidence, and a new session.

### X1 — Separate role/run sandbox for every tool-executing Agent 0/1/2

The selected target architecture gives each tool-executing Agent 0, Agent 1,
and Agent 2 instance/run a fresh, separate OS-enforced sandbox with a profile
derived from that role's and run's sealed authority. Parent and child do not
share a writable sandbox. Sandboxing narrows authority and never enlarges it;
Agent 0, Agent 1, and Agent 2 hierarchy and write boundaries remain unchanged.
Pi remains Agent-2-only and gains no primary, supervisor, Agent 0, or Agent 1
role.

### H1 — Root-conditioned Agent-2-only Bash in an enforced narrow sandbox

App requests a Root doctrine successor under which an Agent 2 Bash run has
only mechanically enforced mounts and capabilities derived from its sealed
brief, default-denied tool network, a bounded process tree, and complete
timeout, output, artifact, interruption, and audit evidence. Serialization is
required where actual mounted write overlap requires it.

H1 grants no Bash now. Until Root separately rules and implements the
successor, the current Root rule remains binding: a Bash-bearing managed child
has project-root read/write scope and is the serialized integration owner for
its stage. This App ruling grants no Bash to Agent 0 or Agent 1.

### R1 — Strict replay-and-bind, held behind Root identity

Durable resume uses a fresh sandboxed worker and replays only admitted product
audit events after exact equality over the Root compatibility identity,
accepted Pi version, sandbox-profile identity, exact model, residency epoch,
and transcript/event-prefix SHA-256. A mismatch may offer an explicit new
session from transcript, never silent resume or operation replay.

R1 is held until Root has accepted and implemented the required compatibility
and sandbox identities and the later App affected-client gates have passed.
