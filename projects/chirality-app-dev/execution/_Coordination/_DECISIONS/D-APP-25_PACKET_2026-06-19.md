# D-APP-25 Decision Packet - Manager-Lifecycle & Anthropic-Manager Event Bridging

**Status:** PROPOSAL
**Date:** 2026-06-19
**Decision ID:** D-APP-25
**Prepared by:** WORKING_ITEMS
**Active design:** `plans/DESIGN_2026-06-18_agent_orchestration_ui.md` (§4 keystone scope, §6)
**Related:** D-APP-18 (default-provider cutover, AWAITING_RULING)

This packet asks whether to extend the Phase-1 `harness:event` bridge beyond its deliberate
increment-1 scope. It does not change the public event contract surface (still one public
`harness:event` type) or the redaction policy.

## Decision Question

Should the live `harness:event` bridge also carry (a) manager-level turn-lifecycle events and
(b) the `AnthropicAgentSdkManager`, or stay at the increment-1 scope (Claude SDK manager only,
lifecycle persisted-only)?

## Grounding (current state)

- Phase 1 bridged rich events **only** under `ClaudeAgentSdkManager` via the provider-neutral
  `harnessEventToUiEvent` (`src/lib/harness/harness-ui-bridge.ts`).
- Manager-level lifecycle events (`turn.accepted/started/cancelled/failed`, `interruption.*`)
  are **persisted-only** — appended to `events.jsonl` but not yielded as `harness:event`. The
  UI still gets cost via the mapper's `turn.completed`/`model.completed` and terminal/error
  state via the existing `turn:error`/`process:exit`.
- `src/lib/harness/anthropic-agent-sdk-manager.ts` exists but does **not** bridge; only the
  Claude SDK manager produces the rich stream.
- DESIGN §4 explicitly scoped increment-1 this way and named both extensions as follow-ons.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Bridge manager-lifecycle events too | Yield `turn.*` / `interruption.*` as `harness:event` so the live loop shows a full turn timeline (accepted → started → completed/cancelled/failed). | Anthropic-manager parity. |
| B | Bridge `AnthropicAgentSdkManager` to parity | The Anthropic provider emits the same rich `harness:event` stream as the Claude manager. | Manager-lifecycle bridging. |
| C | Both A and B | Full lifecycle + provider parity. | — |
| D | Neither now (status quo) | Keep increment-1 scope; cost + terminal state already reach the UI. | Lifecycle timeline + Anthropic rich stream until later. |
| E | Custom | Human supplies alternate scope. | Anything not named. |

## Recommendation

**Option D (status quo) for now.** The live UI already receives cost and terminal/error state,
so manager-lifecycle bridging (A) is additive polish best taken up when the loop wants a full
turn timeline. Anthropic parity (B) only matters if/when that provider is actually exercised;
the default-provider question is D-APP-18 and the shipped rich path is the Claude SDK manager,
so B is low priority until a provider need is concrete. Revisit **A** alongside Phase 5 (richer
loop), and **B** if/when a non-Claude provider is selected.

## Required Constraints If A or B Is Approved

- Keep exactly one public event type (`harness:event`); do not add provider-shaped public
  names — the conformance check (`engine-conformance.ts` / `PUBLIC_UI_EVENT_NAMES`) must stay
  green and `process:exit` must remain the terminal event.
- Run every bridged payload through `redactJsonLike` (same as persistence); no new leak path.
- For B, reuse the provider-neutral `harnessEventToUiEvent`; do not fork a second bridge.
- `npm run typecheck` + exact-sequence manager tests + conformance tests green.
