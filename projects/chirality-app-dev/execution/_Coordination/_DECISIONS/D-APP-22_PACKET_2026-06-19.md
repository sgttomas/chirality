# D-APP-22 Decision Packet - Live-Stream History / events.jsonl Replay

**Status:** PROPOSAL
**Date:** 2026-06-19
**Decision ID:** D-APP-22
**Prepared by:** WORKING_ITEMS
**Active design:** `plans/DESIGN_2026-06-18_agent_orchestration_ui.md` (§4 keystone "replay is free", §6)

This packet asks whether the live loop UI should hydrate historical state from the persisted
event log, or stay live-only. It does not change the public event contract or persistence.

## Decision Question

Should the live event-stream UI load/tail `events.jsonl` to show prior-turn or prior-session
history, or remain live-only (active turn only)?

## Grounding (current state)

- The replay primitive already exists: `replayHarnessEvents(sessionId)` in
  `src/lib/harness/session-events.ts` returns the persisted `HarnessEvent[]` (+ malformed-line
  count + summary).
- "Live == replay" holds by construction: the same pure derivations
  (`lib/shell/harness-event-views.ts`) collapse both the live bridged stream and the persisted
  log into identical rows.
- The live buffer (`components/workspace/harness-events-provider.tsx`) is **live-only** and is
  wiped by `clearEvents()` at each turn start; nothing currently consumes `replayHarnessEvents`
  from the UI.

## Options

| Option | Ruling | What it permits | What remains denied |
|---|---|---|---|
| A | Stay live-only (status quo) | Buffer reflects only the active turn; lowest complexity. | Cross-turn / cross-reload / cross-session history in the loop. |
| B | Hydrate-on-open (batch replay) | On session open, seed the buffer from `replayHarnessEvents`, then append live; history survives reload and supports the Phase-5 session-list "open a past session". | Continuous multi-client tailing. |
| C | Continuous tail of `events.jsonl` | Stream the log live for multi-client mirroring / external observers. | n/a (superset of B). |
| D | Custom | Human supplies alternate behavior. | Anything not named. |

## Recommendation

**Option A for now; adopt B when the Phase 5 session-list lands.** Live-only keeps the loop
focused and matches today's single-active-turn model. B is low-risk precisely because the
derivations are identical (no new render path), and it becomes valuable exactly when the
session-list UI lets an operator reopen a past session — so it is best sequenced with Phase 5,
not Phase 4. Reserve **C** for an actual multi-client/observer requirement (none today;
higher I/O and lifecycle cost).

## Required Constraints If B Is Approved

- Reuse `replayHarnessEvents`; do not fork a second parser; respect `MAX_LIVE_HARNESS_EVENTS`
  buffer bound (truncate oldest on hydrate).
- Hydrate must not double-count events already streamed live in the same turn.
- Surface `malformedLineCount` honestly (do not silently drop a corrupt log).
- `npm run typecheck` + a hydrate/derive parity test green.
