## 5. Options

### Option A — One lightly skinned application graph

Use one Next/Electron graph and shared Woven shell. One immutable build-bound
profile supplies target copy/resources/navigation and six first-domain module
references.

Benefits: lowest current structural MCI (`24`) and closest fit to today's
single graph.

Risks: target awareness remains
`NOT_YET_MEASURED_WITHIN_ALLOWLIST`. No zero is inferred. Conditional spread,
target leakage, and implicit plugin-architecture risk require a later mock and
deterministic allowlist proof.

Effect of ruling: adopts A only as the planning baseline for later exact
requirements, PRD/SCOPE_CHANGE, packaging-identity, prototype, and validation
packets. No source work is authorized.

### Option B — Shared core with target-specific shells

Extract common Woven/UI/state/client packages and compose separate standalone
and Piping shell/build roots.

Benefits: strongest explicit target isolation and clearest independent-shell
scaling boundary.

Risks: highest structural MCI (`43`), a 61-file extraction-review population,
three new package roots, and an 11-site naive duplicate-composition risk set.
Public shared-package acyclicity, zero shared-to-target imports, and `DC=0`
remain later proof obligations.

Effect of ruling: adopts B only as the planning baseline; extraction and source
changes still require separately governed work.

### Option C — Build-time product profiles with six bounded slots

Use one shared Woven shell with an immutable product manifest, generated
build-time profile binding, and six closed target modules/slots matching the
exact U set one-for-one:

1. `NavigationWorkspaceSlot`;
2. `StructuredInformationSlot`;
3. `WorkflowSlot`;
4. `DecisionGateSlot`;
5. `TypedAgentReviewSlot`; and
6. `UiAgentConformanceSlot`.

No runtime target switching is permitted. Target adapters may consume only
declared shared public APIs; opposite-target resources/adapters must be absent
from each artifact.

Target resource/identity manifests remain separately governed build-profile
fields; the six slots above are the exact U-aligned presentation/conformance
set and do not silently absorb packaging authority.

Benefits: exact six-slot alignment with `U=6`, explicit build-time target
closure, `DC=0` intent, and structural MCI `28` without B's package extraction.

Risks: the manifest/slot schema becomes a governed product contract. Adapter
sprawl, private shared imports, cross-slot state, or shared-shell sequencing
changes would invalidate C and trigger reconsideration of B.

Effect of ruling: adopts C only as the planning baseline for later exact
requirements, manifest/slot, PRD/SCOPE_CHANGE, packaging identity,
coexistence, prototype, and validation packets. No manifest, adapter, or source
implementation is authorized.
