# Boundary Review Checklists

## Status

| Field | Value |
|---|---|
| Source deliverables | DEL-01-03 Product Identity and Professional Boundary Copy; DEL-01-04 Scope Boundary and Retired Scope Register |
| Lifecycle posture | CHECKING evidence only; not ISSUED |
| Authority corpus | D-APP-38 corpus v1; REF-006 `docs/PRD.md` currently MATCH |
| Generated by | ADQ-03 autonomous development tranche |

These checklists normalize professional-boundary, product-identity, and scope-boundary review. They are
review aids and evidence templates. They do not approve, certify, sign, seal, issue, publish, release,
externally validate, or make professional work reliable. A completed checklist is evidence for a human
review process, not a substitute for the accountable human decision or any required lifecycle workflow.

## Use Rules

| Rule | Required handling |
|---|---|
| Evidence only | Record checked surfaces, source basis, findings, and proposed wording. Do not treat checklist completion as approval. |
| Human gates | Route authority-sensitive wording and boundary crossings to the accountable human or governing decision process. |
| Source state | Record D-APP-38 corpus status when PRD-backed claims are used; rerun reconciliation if authority docs change. |
| Unknowns | Preserve `TBD`, `ASSUMPTION`, `PROPOSAL`, conflict, or human-ruling-needed labels where support is incomplete. |
| Scope | Keep provider/network expansion, release/distribution posture, R7 domain-engine implementation, and `CHECKING -> ISSUED` issuance behind their hard fences. |

## Professional Boundary Checklist

| CheckID | Review item | Pass evidence | Route or fail when |
|---|---|---|---|
| PB-01 | Product-facing copy identifies the product as Chirality. | Surface name, copy excerpt, and source reference show Chirality-owned identity. | Copy makes the app appear to be Claude Code, Anthropic, a vendor CLI, or a feature-parity target. |
| PB-02 | SDK/provider references are implementation detail. | SDK wording is behind Chirality-owned runtime contracts, audit records, permission policy, and adapter framing. | SDK/provider branding becomes product identity, governance authority, or public semantic owner. |
| PB-03 | Agent output is described as draft assistance, proposal, or decision support. | Copy preserves non-binding language unless a separate human approval record exists. | Copy says or implies agent output is approved, issued, sealed, certified, or reliable by itself. |
| PB-04 | Runtime events, SDK transcripts, validator results, summaries, and generated artifacts are not approval records. | Copy distinguishes evidence records from binding acceptance records. | Copy treats a transcript, event, validation pass, or artifact as professional approval or external validation. |
| PB-05 | Authority-sensitive terms are reserved for accountable humans and governed workflows. | Terms such as approve, certify, sign, seal, issue, transmit, release for reliance, code-compliant, externally validate, and solver truth are absent or routed. | An AI system, SDK, tool, validator, runtime event, or domain adapter is named as the approving or certifying actor. |
| PB-06 | Reliance-boundary copy does not rely on prompt text or opaque SDK defaults alone. | Copy names Chirality-owned enforcement, verified SDK hook/callback behavior, MCP wrapper policy, release check, or human gate. | Copy claims prompts, model behavior, `allowedTools`, or SDK defaults are sufficient enforcement for P0 boundaries. |
| PB-07 | Future domain-engine notices preserve domain-truth separation. | Notices state that domain engines own domain truth and that human acceptance is required before application. | Copy implies Chirality owns solver truth, code compliance, external validation, or professional approval. |
| PB-08 | Release and distribution wording stays within approved posture. | Copy describes evidence, local build, or validation scope without claiming release readiness, publication, signing, notarization, or professional clearance. | Copy crosses release/distribution posture without a governing human decision. |
| PB-09 | Source uncertainty remains visible. | Review note records REF-006 corpus state, active conflicts, and any `TBD` items. | Unsupported facts are smoothed into accepted claims. |

## Scope Boundary Checklist

| CheckID | Boundary item | Pass evidence | Route or fail when |
|---|---|---|---|
| SB-01 | Remote MCP, plugins, remote execution, marketplace extension, broad tool search, and shell-network expansion remain out of current scope. | Review note cites current out-of-scope status and any amendment trigger. | Work proposes implementation or release of remote/plugin/network expansion without a governed decision. |
| SB-02 | Shipped builds do not load ambient Claude settings. | Copy/config review preserves `settingSources: []` shipped posture and excludes user/local settings. | Shipped or ordinary operator flow loads ambient `~/.claude` or local Claude settings. |
| SB-03 | Ordinary shipped workflows do not use `bypassPermissions`. | Review distinguishes guarded developer-local bypass from shipped/operator behavior. | Copy, config, or tests blur developer bypass into shipped or ordinary operation. |
| SB-04 | Retired PKG-08 execution-scope items remain retired. | Review preserves retired state for execution-root validator, dependency graph generator, deliverable lock, unified pipeline run record, and staleness propagation tooling. | Runtime event logging or adjacent work is used to reactivate retired pipeline hardening scope. |
| SB-05 | Windows/Linux packaging remains outside current release scope. | Review names current target as macOS 15+ Apple Silicon local-builder DMG posture and records amendment trigger for other platforms. | Work claims or implements Windows/Linux release packaging without a release-scope amendment. |
| SB-06 | Domain operation execution and protected domain paths remain future-amendment scope. | Review records proposal-record and human-acceptance boundary. | Work executes domain operations, writes protected domain-engine truth, or implements R7 domain engine behavior. |
| SB-07 | Boundary-row human rulings remain visible. | DEL-01-04 boundary rows preserve `Human Ruling = TBD` or an explicit human ruling/deferral record. | A row is treated as accepted or issued without human ruling evidence. |
| SB-08 | Dependency and lifecycle non-claims are preserved. | Review confirms no dependency row satisfaction, `_STATUS.md` transition, or issuance is implied by checklist evidence. | Checklist completion is used to satisfy dependencies or move `CHECKING -> ISSUED`. |
| SB-09 | Amendment triggers are explicit. | Each proposed boundary crossing names the affected boundary, required governed change surface, validation impact, and human decision need. | A boundary crossing is silently linearized into ordinary implementation work. |

## Boundary Notice Examples

Use these as starting points, not as mandatory UI strings.

| Context | Example copy |
|---|---|
| Draft output | This output is draft assistance. An accountable human must review and accept it before reliance. |
| Runtime event | Runtime events record what happened during a turn; they are evidence records, not approval records. |
| SDK disclosure | This runtime may use an SDK-backed engine behind Chirality-owned contracts, permission policy, and audit records. |
| Validator result | This validator result is check evidence, not external validation, certification, or professional approval. |
| Domain notice | Domain-engine output requires human review and does not represent Chirality-owned solver truth, code compliance, or professional approval. |
| Scope boundary | This capability is outside current scope and requires a governed amendment before implementation or release. |
