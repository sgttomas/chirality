# Guidance — DEL-050-05 Vendor Document Turnover Package

## Purpose

This deliverable exists because PKG-050 (Stabilizer Overheads Compressors) is acquired as a vendor-engineered mechanical package, and the Owner/EPC Integrator needs a controlled, auditable body of vendor documentation to:

- operate, maintain, and modify the compressor package over its life,
- close the EPC turnover gate (sibling `DEL-050-06`),
- and satisfy the scope items `SOW-0173`–`SOW-0176`.

The Comp & Liquids Design Basis Manual establishes that mechanical packages "shall include … vendor document registers" alongside datasheets, cause-and-effect inputs, utility loads, and similar artifacts (DBM-Comp_and_Liquids §617).

## Principles

- **The register is the index of record.** The vendor document register is the single, current truth list for all vendor documentation in PKG-050. Submittals, transmittals, and turnover records all reference the register.
- **Source first, summary second.** Where source documents (`26020-Package_Requirements.docx`, `26020-Packages_Interfaces_4_export.xlsx`, project document control standard) speak, they govern; this Guidance does not substitute for them.
- **Traceable scope coverage.** Every register entry should trace back to a package requirement, code requirement, or SOW row.
- **No silent acceptance.** EPC Integrator acceptance happens in `DEL-050-06`. This deliverable produces evidence; it does not certify itself.

## Considerations

- **Document classes likely in scope** (ASSUMPTION pending source confirmation): general arrangement and fabrication drawings; P&IDs and control schematics interfacing with EPC; design calculations; pressure-equipment certifications and U-stamp documentation where applicable; material test reports; inspection and test plans with executed records; performance test reports; lubricant and consumables data; spare-parts list; vendor operations and maintenance manuals; training materials.
- **Submittal lifecycle** (ASSUMPTION): for-review → for-approval → certified-for-construction → as-built. Each transition is a register-state change with transmittal evidence.
- **Interface with sibling deliverables**:
  - `DEL-050-02_package-datasheet` provides the design data set the vendor documentation must remain consistent with;
  - `DEL-050-03_construction-work-package` consumes vendor installation / tie-in information;
  - `DEL-050-04_vendor-engineered-equipment-package` is the engineering content whose documentation this deliverable indexes and turns over;
  - `DEL-050-06_epc-vendor-package-review-and-acceptance` is the downstream review and acceptance step.
- **SOW coverage**: `SOW-0173`–`SOW-0176` — full SOW row text was not accessible during this draft; mapping detail is TBD.

## Trade-offs

- **Register granularity vs. workload.** A finer register (per-document, per-revision rows) yields stronger traceability and turnover defensibility but increases vendor administrative load. Industry practice favors per-document with revision history (ASSUMPTION; project document control standard TBD).
- **Native + PDF vs. PDF-only deliverables.** Native files (e.g., CAD, calc spreadsheets) preserve downstream modifiability and audit value but expand the turnover footprint and licensing concerns. Project standard TBD.
- **Early partial turnover vs. single end-of-project turnover.** Phased turnover supports operations readiness but increases register revision churn; consolidated turnover is simpler but delays usable documentation.
