# Scientific binary64 JSON — prospective M34 design

Recommendation by `/root/load_state_design`, HELPS_HUMANS, to ROOT and WORKING_ITEMS: add a new explicitly selected `openpipestress_jcs_binary64_v1` profile, with schema-owned exact integer fields. Preserve `openpipestress_jcs_ijson_v1`, its failures/hashes, and the older unrestricted serializer unchanged. The final name/version is ROOT-owned. `P/` means `projects/chirality-piping/`. This design is not implemented and does not delay current source-method qualification.

## Why a successor is needed

The inspected `core/serialization/canonical_json/src/lib.rs` rejects finite floats whose fractional part is zero and magnitude exceeds 9007199254740991. Every sufficiently large binary64 number is integral-valued, including 1e160; this is not an IEEE overflow. The current producer log and CURRENT_STATE explicitly record this refusal before solve. Existing `ecma_number_to_string` already has large-finite/subnormal reference vectors. Removing only the float guard is insufficient: `canonical_number` preserves serde i64/u64 values exactly, so 9007199254740993 can retain different bytes from the binary64 value received through JavaScript.

[Primary standards and errata](REFERENCES.md) distinguish finite binary64 numerical values from exact-integer application semantics. The replacement selects this distinction deliberately; it does not relabel v1 as historically wrong or broaden a passed old qualification.

## Numeric contract: two domains, one serializer

1. **Scientific real:** a finite IEEE754 binary64 value, including an integral-valued large real. The domain is selected by the versioned record/schema, not by a decimal point, exponent, Rust serde number variant or Python host type. All accepted numeric tokens in the new canonicalizer are converted once to binary64 using correctly rounded nearest/ties-to-even conversion, then rendered through the Rust-owned ECMAScript number formatter. The old exact i64/u64 formatting branch is never used by this profile. Thus 1e160, 1e20 and 2^68 are real values, not automatically exact counts.
2. **Exact integer:** indices, counts, dimensions of arrays, budgets/iteration numbers and integer-valued enums must remain exact and within `[-(2^53-1),2^53-1]`, or a narrower schema bound. Nonnegative counts additionally require >=0. IDs, arbitrary precision numerators/denominators and float bit patterns remain strings in their existing explicit formats. This successor does not add BigInt/decimal arithmetic to the solver.

The record's existing typed validators own a small explicit inventory of exact integer fields; no runtime user-defined type language or path-guessing framework is needed. Everything accepted as a JSON number by the generic new renderer has binary64 canonical semantics. Correct integer semantics are an additional mandatory admission check for a qualified typed record, before normalization/rounding can erase the original input. Unknown record versions cannot qualify by calling the generic renderer alone.

For the new text protocol, select a simple exact-integer grammar: fields in that inventory accept integer tokens only, with no decimal point/exponent and no negative zero, then exact range/field checks. `1`, `0`, and permitted negative integer tokens work; `1.0`, `1e0` and `1.0000000000000000001` are rejected in exact-integer fields even though some parse to 1. This is a prospective application rule, not a JCS requirement. It avoids deciding exact integer meaning after float rounding. Existing text/historical profiles retain their actual acceptance rules. A schema's generic JSON `type:integer` check alone is insufficient because many validators inspect already-rounded values.

Programmatic Rust/Python exact integers must be their proper integer type and range; JavaScript counts must be Number.isSafeInteger and satisfy narrower bounds before JSON.stringify. Actual JSON emitted by those APIs is checked again. Python bool is not an integer-domain value. Explicit scientific-real fields can accept a Python/Rust integer via a declared conversion to binary64; an unsafe Python integer in an untyped object helper must not silently become a real. Use the typed field adapter or raw-text real path to declare that conversion. Decimal/Fraction/BigInt values require an explicit conversion or string-valued external representation; ordinary object freezing rejects them.

## Text parsing, round trips and exceptional values

Keep strict JSON syntax, duplicate-key rejection after escape decoding, finite values, UTF-8 input/output, valid Unicode scalar strings and UTF-16 property sorting. New input also rejects Unicode noncharacters as required by the I-JSON basis, including top-level strings. Preserve strings exactly: no Unicode normalization or number-looking-string conversion. Continue rejecting cyclic/non-plain objects, getters, symbols, undefined, array holes and coercing toJSON behavior in the JS/Python programmatic adapters. Do not let JSON.stringify convert NaN/Infinity to null before validation.

Scientific real lexemes such as `9007199254740993`, `9007199254740993.0` and `9.007199254740993e15` represent the same nearest binary64 value 9007199254740992 under this profile. They are not exact decimal/integer storage; the same tokens in an exact-count field fail. Likewise 0.1 is an accepted binary64 approximation, not exact rational1/10. Preserve original entered text when required for an input audit, separately from the actual consumed value. A canonical semantic hash does not authenticate decimal spelling or discarded digits. Exponent syntax must not be a bypass for an exact-integer check.

Reject overflow to infinity. Accept representable subnormals and require bitwise round-trip parity in supported parsers. Reject a nonzero numerical lexeme that rounds/underflows to zero at ingress rather than silently transforming a supplied nonzero input into physical zero. This is an explicit scientific-ingress restriction beyond JCS's rendering algorithm. Conversion to a nonzero nearest subnormal is allowed; input accuracy and downstream numerical-method acceptance are separate. Solver methods may still refuse subnormal arithmetic/results under their own justified criteria. No flush-to-zero behavior is accepted as a serialization pass.

RFC8785 verified erratum7920 recommends rejecting negative-zero input because canonicalization maps it to positive zero. Select that stricter rule for new input: reject `-0`, `-0.0`, `-0e3` and programmatic IEEE negative zero before any JSON.stringify/canonicalization collapse. The renderer's existing IEEE negative-zero→`0` behavior remains unchanged for history and standalone algorithm tests. Fresh computed output can contain IEEE -0 internally; the new producer explicitly normalizes public numerical zero fields to +0 before final row binding and hashing. Exact source/arithmetic bit strings are not altered. A proof recipe must state this terminal public-zero projection, and must validate published bits after that projection; never claim raw bit identity where zero-sign normalization occurred. This requires the successor producer/semantic version, not a silent edit of source-blocks-1. New profile canonicalization itself is never used to repair an untrusted result carrying -0.

Correct conversion must operate on the original numeric token, not decimal→rounded temporary→second rounding. For the new Rust path, both serde integer and float variants end at the same binary64 formatter. Retain `float_roundtrip` where needed, but a feature flag is not evidence of cross-language conversion parity. A thin numeric-token/raw-field capture during strict parsing can preserve lexemes for integer/underflow/negative-zero checks; do not regex-match whole JSON. The internal type need only hold checked text, normalized value and its admitted record contract. No public tagged wrapper is added around every number. Declare and enforce new-profile-only bounded request-byte, nesting and token limits; reuse existing limits only where they actually exist. The inspected v1 checked CLI reads stdin without an explicit byte cap, so no inherited generic v1 request/token limit is claimed or retrofitted here. Count range checks need only bounded integer accumulation; negative-zero and nonzero-underflow checks need sign/nonzero-significand information, not an unbounded decimal arithmetic engine. Preserve integer variants for admitted typed count fields as needed by DTO deserialization, while the new hash writer uses binary64 numeric rendering uniformly; do not turn a validated count into a serde floating variant that its typed reader then rejects.

## Authority and actual invocation binding

Use Rust as the single canonical-byte authority in native, WASM and the existing explicit Python subprocess adapter. Add new entrypoints/profile dispatch beside v1; no JS/Python hash fallback. CLI requests/responses echo the selected protocol/profile and reject unsupported combinations. The public hash carrier names the profile, payload scope, record/semantic version and actual payload identity; domain-separated receipt hashes use successor domain strings. Preserve old profile constants and dispatch branches. A v1 refusal must never trigger automatic retry under the new profile.

Validate at the first available text boundary before an ordinary JSON parser can discard duplicate keys, fractional integer tokens, original underflow or negative zero. Native/headless raw-file routes feed that text to the checked authority; browser external-file imports do the same before JSON.parse. Browser-created objects undergo the strict typed freeze before serialization. An already-parsed foreign object cannot establish that its discarded input text met these rules; only the object actually supplied can be authenticated. Do not claim raw-byte custody for such a route.

The current source receipt captures a serde Value before typed DTO conversion, not original source bytes. Preserve that historical meaning. Its successor must capture the complete validated actual invocation (including omitted/unknown-field policy and actual requested solver mode) before building typed normalized model objects. Keep raw supplied document and consumed binary64/typed projection linked, including all fields the contract retains. Hashing the later DTO alone would lose real invocation content. Do not construct a capture from a caller-supplied digest. Domain-separated source/plan/row receipts retain original operand-bit strings and source replay. Record numerical normalization separately from units/material resolution. Semantic equality of rounded input decimals is permitted by the new profile; it is not a claim that original text or numerical intent was identical.

Make those identities concrete in the private capture and any published custody claim: `ingress_kind = received_text | programmatic_snapshot`; `source_text_scope`; `source_utf8_sha256` plus retained exact source bytes when raw-text custody is claimed; and a separate `canonical_invocation_sha256` over the complete admitted request value, actual requested mode, profile and successor receipt domain. The raw digest covers exactly its named byte scope (for example a received model file, or the actual serialized invocation), never an unstated larger envelope. A programmatic snapshot authenticates the bytes actually emitted by the checked adapter, not a caller's lost earlier decimal text. If original text was not retained, omit that claim rather than synthesizing it with reserialization. Canonical identity may legitimately collapse whitespace, escaped spelling and rounded real lexemes; a raw byte digest must not. Both are source-created from the actual ingress/call, not accepted from caller-supplied hashes. Keep the dependency acyclic and do not include a carrier's own digest in its preimage.

No authority is gained from carrying the profile label. Qualified Current/export/rules still require the real native/headless invocation capture, matching model/case/requested mode, source replay, numerical standing and validated result rows. Fresh receipt hash profile and method-semantic IDs change together. A new profile cannot launder old unauthenticated carriers or make a withheld Sensitive result eligible.

## Scientific quantity publication: value, unit and display are separate

A wider JSON profile does not prevent precision loss from the chosen unit. ROOT supplied an independently evaluated represented-operand scalar example: force1e-306N divided by area596902.6041820607m² gives stress near1.675315190441e-312Pa. Its first actual source-method probe was refused with `exact radix loses represented bits`, remained p1 Sensitive and had no qualified source receipt; that probe is not the unsafe-admission reproduction. Independent exact Fraction arithmetic over those actual binary64 inputs gives relative error about6.64575e-13 for the direct Pa division, but about1.269450175e-6 after the current fixed MPa publication divides by1e6. The latter misses the unchanged1e-9 criterion; Pa can retain enough precision. Both numeric values are finite/subnormal and JSON-serializable. Neither a serializer pass nor a blanket subnormal refusal explains the distinction.

A later structurally scaled request (OD2e15m, wall1e14m, E1e-29Pa, G1e-53Pa, Fx1e-282N) did reproduce unsafe source-blocks-1 admission in both solver modes. The preserved pre-repair request/raw pairs and represented-input oracle under numerical `SOURCE_RECOVERY_IMPLEMENTATION_01/_run_records/stress_range_scaled_before` show five axial MPa rows and the summary with relative error about1.2694501751682153e-6 against unchanged1e-9. This separate observed producer reproduction supports the same unit-range conclusion; it does not make the earlier scalar/probe example a qualified execution. Original failures, before outputs and subsequent containment remain at their owning numerical records; BASIS.json records the consulted origins/hashes. No producer or native run was performed by this design assignment.

For the successor stress carrier, publish the actual evaluated SI quantity `value` in `Pa`, with `dimension=stress`, and its numerical bounds/standing. Recover and compare stress extrema/maxima in that same basis; publish summaries as an explicit quantity with unit/dimension/governing identity rather than reusing a field named `max_stress_mpa` with changed units. Result rows, semantic signatures, canonical derivatives, analysis records, rule input and machine export must agree on that new contract. Existing MPa rows/tables/summary fields and hashes remain historical and unchanged. This is a narrow quantity-carrier extension alongside the new numeric profile, not a unitless value substitution.

Keep the actual loss locations distinct. The source-block fixed-MPa producer recipe in the supplied numerical finding is different from current physics/p1 persistence: the canonical derivative copies received value/unit into target rows, while AnalysisRun retains unit annotations and hashes/binds unchanged received results and rows without embedding a second numeric row-value table. Bounded joined-source inspection confirms the display chain `QuantityReadout` → `displayQuantityService` → `operation_applier/display_units` → `units::convert_for_dimension`: it accepts finite cross-unit outputs without a relative-error bound, so finite subnormal or zero projections can be labelled converted. This is a source/interface observation, not a reproduced current physics producer or native failure. The successor adds a precision/range-aware display response and preserves the entered/base quantity when conversion is inadequate; it does not rewrite the immutable received result.

UI formatting is a view of the retained Pa quantity. Prefer scientific Pa when a requested unit cannot preserve the qualified value. An MPa display can be produced as a decimal/scientific string from the retained Pa value using checked formatting without first rounding the scaled result to binary64; label it as display text and keep the exact base value/unit available. Do not show a conversion-rounded zero or an inadequately resolved MPa number as an equally qualified machine quantity. A machine-readable requested-unit conversion must retain sufficient error bounds under the existing criterion; otherwise return an explicit conversion-range/precision limitation or export the valid Pa quantity. A formatted string is not a second numerical result or a new arithmetic datatype. No generic arbitrary-precision framework is needed.

The producer remains responsible for the raw calculation error and the final stored-unit projection error separately. If Pa itself is insufficient, withhold the quantity or use a separately qualified method; do not move the tolerance. Current NUM containment and p1 semantics stay unchanged. The decisive case tests actual Pa and MPa values, their bit patterns and exact-input error, plus summary/export/native formatting. An allowed scientific lexeme is not evidence that either unit meets the mechanics criterion.

## Decisive checks

[Conformance cases](CASES.md) supply exact source/expected-bit distinctions and negative controls. [Independent probe](probe_numeric_domains.py) runs standard-library conversion/domain examples only; it is not Rust/JS/WASM parity or product evidence. Required implementation checks include raw literal/serde i64/u64/f64/native/WASM/Python convergence; exact-integer lexical checks before parse erasure; duplicate escaped keys; Unicode sorting and rejection; every RFC AppendixB finite vector; negative-zero and underflow rules; fixed-seed adjacent/halfway decimal values; hash-profile downgrade/mixing rejection; unchanged legacy hashes; and a genuine1e160 invocation through solve/receipt/readers/save/reopen. Actual result values and source bits must be observed, not filled from fixture constants.

This is the smallest recommended successor: one numeric profile, two schema domains, strict ingress and existing hash authority. No new owner method approval, generic typed-JSON framework, arbitrary precision solver, material library or code rule is needed. Ability to transport a finite number does not establish physical suitability, numerical accuracy or a qualified solution at that scale.
