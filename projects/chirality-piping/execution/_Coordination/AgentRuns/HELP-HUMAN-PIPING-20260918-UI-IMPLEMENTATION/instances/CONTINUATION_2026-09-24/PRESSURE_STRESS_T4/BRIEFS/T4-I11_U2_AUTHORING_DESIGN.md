# T4-I11: T4-U2's desktop authoring design (M02 minimal)

**Terms:** `R4/BRIEFS/T4_WI_COMMON.md`. Your ID is T4-I11.

**Purpose.** T4-U2's first usable path is authored on the desktop: the user realizes a bend and enters its flexibility factor k, the pressure region accepts the bend, and the model is applied, saved, reopened, solved under `3.0.0/exact_pressure_v3`, shown and exported (plan §2, §3.1 "T4-U2 in detail", authoring bullet). Today no app or operation path writes `mechanics_interface`, so a realized arc reaches a solve only from a hand-edited document (I2 §2). You write the authoring design so implementation can start as soon as T3's U3 merges.

**Read:** plan §1 (C1), §2, §3.1 (T4-U1's `bend_plane_orientation` bullet, T4-U2a, T4-U2), §4.1 D-2 and D-3, §4.2 H-1, §4.3 items 1–2; I1 §3.1 (desktop), §5.3 rows 2 and 4; I2 §2; I3 §5's authoring rows (for what T4-U3 later does to joint authoring, which is out of your scope). The code at `ed012c7ccf`: `P/apps/desktop/src/features/{component-creation,pressure-authoring,model-tree,model-workspace,results,operations}`, `P/core/model_operations/operation_applier/src/lib.rs`, the Tauri commands in `P/apps/desktop/src-tauri/src/lib.rs`, the document migration and save path, `P/apps/desktop/e2e/` and the desktop CI workflow (dual-viewport runs).

**The design must give:**
1. **User flows,** step by step: create a bend at a corner, or realize an existing geometry-only bend; enter k (k = 1 means no extra flexibility; agents never populate k); choose a pressure profile on a new document (new authoring writes v3; existing v2 documents stay v2 and readable); add the bend to a pressure region; solve; inspect; save, reopen, export. What the user sees when a geometry-only bend is in a pressure region (D-2's "realize this bend" refusal), when a kink exceeds the tangency tolerance (refused as a mitre until T4-U7), and when p < 0 under v2.
2. **Data writes.** Every field each operation writes or validates (`mechanics_interface.solver_consumption = curved_bend_macro_element`, `modifiers.flexibility_factor_user_value`, the bend geometry, the pressure contract, region membership), as new or extended operation-applier operations with their refusal codes (the applier's `OP-*` namespace). How `bend_plane_orientation` is handled given T4-U1 either removes its requirement or makes the solver consume it; recommend one. One radius/angle authority.
3. **Tangency.** Where tangency is checked during authoring, and a proposed engineering tolerance for the solve-time rule (small kinks carried exactly by the remainder term; larger refused as mitres; H-2, RV1 N-2), with reasoning.
4. **UI.** The panels and controls changed (component panel, property inspector, pressure authoring panel's member picker and its "straightness" text), with states and messages. Keep to M02 minimal: no new bend element kind, no automatic tangent-point insertion unless it is the smallest correct path.
5. **Tests.** Applier unit tests, desktop unit tests, e2e flows (including the dual-viewport runs), the save–reopen–export round trip, and what the native witness on the owner's Mac must show for T4-U2.
6. **Sequencing.** Which parts can be built against today's contract before T4-U2a lands, which wait for the v3 identity, and the files touched, so they can be split into small commits. Note any conflict with T3's reader lanes or the shared `previewService.ts`.

**Output.** `AUTHORING_DESIGN.md` (at most about six pages) and a one-page `RETURN.md` with any decision it needs (mark which are within WORKING_ITEMS' authority and which would change the approved plan).
