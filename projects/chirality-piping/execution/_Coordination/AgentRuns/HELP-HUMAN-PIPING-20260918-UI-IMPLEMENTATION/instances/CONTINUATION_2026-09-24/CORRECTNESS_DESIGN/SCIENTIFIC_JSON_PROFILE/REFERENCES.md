# Primary-source qualification

Checked 2026-09-25. The references concern interchange/canonicalization; they do not prove a solver or all implementation paths conform. No secondary sources or engineering library content were used.

- [RFC7493 §2.2](https://www.rfc-editor.org/rfc/rfc7493.html#section-2.2) describes interoperable binary64 magnitude/precision and the limit on expecting exact large integers. This supports separate real/count domains; it does not forbid every integral-valued large real. The application retains ±(2^53−1) for exact integer fields. The document is an IETF Proposed Standard.
- [RFC8785 §3.1–3.2.2.3 and AppendixB](https://www.rfc-editor.org/rfc/rfc8785.html) specifies binary64-based JCS serialization, including rounding, large finite values and subnormals. Its integer note distinguishes application interpretation from the canonical algorithm. Negative-zero rendering is positive zero; invalid numeric/Unicode input must not silently turn into another payload. JCS uses UTF-16 key order and preserves string content without Unicode normalization. This is an Informational RFC, not an Internet Standards Track specification. The new application's underflow-to-zero refusal and strict exact-integer token grammar are explicit additional policies, not requirements attributed to JCS.
- [RFC8785 errata](https://www.rfc-editor.org/errata/rfc8785): the official listing returned two Verified entries. [7920](https://www.rfc-editor.org/errata/eid7920), technical, verified2024-05-15, recommends rejection of parsed negative-zero input to avoid losing sign-sensitive distinctions. The design selects that recommendation for new ingress; it does not change existing profiles or pretend an erratum is an automatic product migration. [6292](https://www.rfc-editor.org/errata/eid6292), editorial, corrects an ECMAScript section reference.
- [RFC7493 errata](https://www.rfc-editor.org/errata/rfc7493): both listed entries are Reported, not Verified. [5354](https://www.rfc-editor.org/errata/eid5354) proposes including ±2^53 in the stated exact-integer limit; this design does not adopt the unverified change or broaden safe counters. [6861](https://www.rfc-editor.org/errata/eid6861) points out the top-level-string wording issue in Unicode constraints. The new ingress deliberately applies the same scalar/noncharacter rules to every string, including a root string, without modifying history.

Direct errata page opens initially returned a tool internal error. A bounded official-domain search then returned complete RFC Editor status records and individual entry pages. The listed status is the observed official-source result, not an inference from absence. RFC Editor information pages were also consulted; no superseding RFC was identified in that bounded check. No exhaustive standards-surveillance claim is made.

The design's separation follows elementary representation facts, independently probed here: an input decimal may round to binary64; different decimal/integer/exponent spellings can denote the same consumed value; serde can retain an integer variant beyond JavaScript's exact-integer range; a canonical semantic hash cannot recover original spelling or pre-parse precision. The existing code already uses Ryu-based rendering. Reuse is conditional on actual conformance checks, not the crate description or these standards alone.
