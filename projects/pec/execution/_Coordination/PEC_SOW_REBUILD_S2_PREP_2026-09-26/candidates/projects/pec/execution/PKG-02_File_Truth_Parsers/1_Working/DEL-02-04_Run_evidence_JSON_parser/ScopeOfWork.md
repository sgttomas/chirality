## Completion and Reliance Basis — Epistemology

The requirements below state what future production must satisfy. Nothing in
this section asserts that a parser, a grammar declaration, a fixture or a test
exists.

- **REQ-001** — The parser shall read files named `STATUS.json` and `RUNTIME_SUMMARY.json` located beneath the `execution/` tree of a loop whose registered feed profile declares the JSON run-evidence surface (REQ-013), within the tree it reads for that loop (TBD-005), and shall emit from them RunRecord summaries, per the `SOW-014` statement (CLM-001) and the register `Description` (CLM-004). Records held only at an archive tag and absent from that tree are not read (CON-005).
- **REQ-002** — The parser shall document each grammar it applies — an identifier and version, every key it reads and that key's semantics — and shall let no undeclared key influence its output, per the `PKG-02` out-of-scope line "interpretation beyond declared grammars" (CLM-006). Every summary shall name the grammar it was read under. Where a file declares a `schema` value no grammar recognizes, and where a file declares none, the grammar documentation shall state what the parser does; silent best-effort interpretation of unrecognized shapes is prohibited (CON-001).
- **REQ-003** — The parser's emitted summaries shall be typed as the RunRecord entity of the record-tier contract of CLM-008 in force at production. This deliverable shall define no record-tier entity type of its own, shall add no type to that model, and shall not depend on any upstream artifact existing; it depends on the upstream contract only (CON-002).
- **REQ-004** — The parser shall admit only checkout-contained run evidence beneath `execution/**`. Application-owned Runtime service user-data shall not be an input and shall not be representable in any emitted summary, per the `SOW-014` ledger note "Application-owned Runtime service user-data is operational, never an input" (CLM-001), the PRD v2.4 §7.1 RunRecord row (CLM-002) and `PEC-K-05` (CLM-012).
- **REQ-005** — Every emitted summary and every stated limitation shall carry provenance sufficient for a per-claim citation to its live source — loop, path, blob SHA, examined commit, grammar identifier, and the feed profile identifier, version and state under which the file was read — per `PEC-ORI-004`. The act of attaching citations to a response is excluded here by REQ-011; this requirement obliges the parser to carry what that act needs, and no more.
- **REQ-006** — Where a declared loop has no run-evidence file, or a file is unreadable, malformed as JSON, or carries a shape no declared grammar recognizes, the parser shall report that condition explicitly to its caller, naming the loop and, for a file, the file and the fault, and reporting a declared loop with no file as a stated coverage limit; a silently dropped, empty, partial, or defaulted summary is prohibited, per `PEC-ORI-006` ("Where a feed is unparseable or stale, the response shall state the measurement limitation explicitly; silent omission is prohibited"). Rendering such a limitation into a response is excluded here by REQ-011; this deliverable makes the limitation available to it.
- **REQ-007** — The parser shall create, modify, or delete no file and no Git state, including the run-evidence files it reads, per `PEC-RCN-004` ("it shall never modify a source file"), `PEC-RCN-006` ("The reconciler writes only its own store and generated views"), and the `PKG-02` out-of-scope line "Writing anything".
- **REQ-008** — The emitted summaries shall be content-minimal: paths, counts, identifiers, states, SHAs and hashes, never file or diff content, per `PEC-K-10` ("Paths, counts, SHAs, states, hashes — never file or diff content"). Run-evidence JSON is bound to no accepted schema (CON-001), so any value may carry free text; no emitted field shall be able to hold it. The ingest guard is excluded here by REQ-011; this requirement binds what the parser is able to emit, and CON-006 bounds how it treats values outside the guard's classes.
- **REQ-009** — The parser shall be deterministic over its inputs: the same file set at the same content under the same registry declaration and grammars shall yield the same summaries and limitations, so that the record tier remains fully regenerable from sources per `PEC-K-02` and the upstream regenerability obligation of CLM-008.

## Production and Verification Method — Praxeology

Production proceeds in the order grammar declarations → registry-driven
discovery and state labelling → extraction → limitation reporting → fixtures
and tests. Each stage is the acceptance surface of the next, and a grammar
declared before code exists cannot have been fitted to whatever the code
accepted. All work is bounded to this deliverable folder, the `PKG-02`
service-core source and the fixture paths a ruled packet names; this contract
authorizes no register, decomposition, PRD, registry or upstream-deliverable
edit, and no v2 source write by itself. Tests implement the verification
methods below and create no scope.

- **VER-001** — Execute the parser over a well-formed fixture pair in a declared loop and assert the emitted summaries equal the fixture's declared expectation, each naming its grammar; compare the keys actually read, by instrumentation or code inspection, against the documented grammar; mutate an undeclared key and assert output invariance; execute the unrecognized-`schema` and absent-`schema` fixtures and assert the documented behaviour in each case.
- **VER-002** — Inspect this deliverable's source for any record-tier type definition and assert none; review every emitted summary field by field against the record-tier contract in force at review time, recording the open CON-002 condition where that contract does not admit JSON-sourced summaries; search source and fixtures for any assumption that an upstream schema, model or store exists, asserting none.
- **VER-003** — Tier-boundary exercise: point the parser at a fixture tree containing files beneath and outside `execution/**` plus a fixture shaped as application-owned Runtime service user-data, and assert that only the `execution/**` files are read and that the service user-data fixture yields no summary and no record-tier field.
- **VER-004** — Provenance resolution: for a sample summary and limitation from each fixture kind, resolve the recorded provenance to its live source and assert that loop, path, blob SHA, examined commit, grammar identifier and profile identifier, version and state are present and locatable.
- **VER-005** — Execute the parser over a declared loop with no run-evidence file and over absent, unreadable, malformed-JSON and schema-unrecognized fixtures, and assert, per case, an explicit limitation naming the loop and, for each file, the file and the fault, or the coverage limit for the loop without files, with no dropped, empty, partial or defaulted summary returned.
- **VER-006** — Hash the fixture corpus, and the objects, refs, index and worktree of any fixture repository, before and after a parser run and assert byte-identity; inspect the module's call graph for write, create, delete or ref-updating operations.
- **VER-007** — Content-minimal inspection: run the parser over a fixture whose run-evidence keys carry distinctive free prose, diff-shaped text and file content, and assert field by field that the emitted summaries carry none of it; review every emitted field's type for capacity to hold prose.
- **VER-008** — Determinism check: run the parser twice over the same unchanged fixture corpus, registry declaration and grammars and assert identical summaries and limitations; inspect the emitted field inventory for any value not derived from the source files and the declaration.
- **VER-009** — Inspect the `PKG-02` dependency manifest and the module's import graph for third-party runtime dependencies and network calls, and re-run the `DEL-01-05` zero-dependency and locality enforcement once that deliverable is available, without discharging it here.
- **VER-010** — Boundary inspection: assert the module opens no `WORK_GRAPH.json` or other sibling feed path, emits no entity type other than RunRecord and no presence-tier fact, and contains no code path for any excluded act of REQ-011.
- **VER-011** — Run the `PKG-02` test suite and confirm that each of VER-001 through VER-010 and VER-012 through VER-014 has a corresponding executing automated test and that no test asserts a criterion absent from this contract.
- **VER-012** — Execute over a fixture registry with a loop declaring the JSON run-evidence surface, a loop without that declaration whose tree holds run-evidence files, and no available registry; assert reading, non-reading and the no-declaration report respectively, and that no declaration is inferred from files.
- **VER-013** — Execute over fixture loops declared historical and declared live; assert the declared state on every summary and limitation; alter file dates and remove files and assert no label changes; assert no freshness or staleness field is emitted.
- **VER-014** — Execute over fixtures whose declared run identifier differs from the folder name, fixtures with no declared identifier, and fixtures whose prose or paths contain identifier-shaped text; assert the declared identifier or the unavailable marking, with none drawn from a folder name, path, date or prose; inspect the output schema for fields joined from another feed.

## Governing Values and Decisions — Axiology

- **AX-001** — `OBJ-001` governs: orientation is a sub-second query with per-claim citations. A run-evidence summary that cannot say which file, commit and declaration it came from cannot serve a cited orientation; provenance is therefore a property of what this parser emits (REQ-005) rather than a decoration added downstream.
- **AX-002** — `OBJ-002` governs indirectly, through the record tier. This deliverable produces facts the SHA comparison operates over; it does not perform that comparison, and no requirement here may be read as claiming otherwise. Its contribution is output that is deterministic and regenerable (REQ-009), so a difference between two reconciles is structural and never a judgment.
- **AX-003** — `PEC-K-05` governs the tier boundary. Run evidence committed under `execution/**` is record-tier input; the Runtime service an application owns keeps operational user-data that is never an input (CLM-012). REQ-004 enforces the line at the input, so operational state has no route into a record-tier citation through this parser.
- **AX-004** — `PEC-K-10` content-minimal is a residency posture, not a storage optimization, and run-evidence JSON, bound to no accepted schema, can carry free text in any value (CON-001). The strongest available enforcement is a summary that has nowhere to put prose (REQ-008); the ingest-side guard is `DEL-01-03`'s.
- **AX-005** — `PEC-K-02` files govern: run-evidence JSON is authored project truth and PEC's summary of it is a projection, regenerable and never citable as authority over the file. `PEC-RCN-004` and `PEC-RCN-006` make the read-only posture a rule (REQ-007).
- **AX-006** — `PEC-K-01` graceful absence governs: no governed act may require a PEC read or write. A loop with no declared JSON surface, or a declared loop whose tree holds no run-evidence file — PEC's own condition at `aca930622` (CLM-014, CLM-015) — is a stated coverage condition, never a blocked act and never a silent gap.
- **AX-007** — `DL-4`, extended by `DL-20`, makes this deliverable atomic: one feed kind, one separately testable unit. Absorbing a sibling grammar (including `WORK_GRAPH.json`, which shares this feed's profile surface), the RunRecord type, the join, the registry or any consuming derivation would undo it (REQ-011, REQ-015).
- **AX-008** — The edges cited are `[E-P06]` (upstream, `DEL-01-01` → `DEL-02-04`, `PROPOSAL`) and `[E-P22]` (downstream, `DEL-02-04` → `DEL-03-01`, `PROPOSAL`). Stratum is provenance, not authority: it records how an edge was derived, and citation converts no `PROPOSAL` into a `DECLARED` edge.
- **AX-009** — Edge direction is a constraint on this contract, not a licence. `RequiredMaturity` `INITIALIZED` on `[E-P06]` makes the upstream *contract* the reliable input, not any upstream artifact, which is why CON-002 is recorded. Consuming that contract imposes no obligation on `DEL-01-01`, and being consumed by `DEL-03-01` neither expands nor transfers scope in either direction.
- **AX-010** — Unknowns stay marked. TBD-001 through TBD-007 and CON-001, CON-002 and CON-004 through CON-007 are recorded rather than resolved by inference; a production choice that settled a CON item would be a decision taken in the wrong place. `C-04` `PHASE_PRECEDENCE` and `C-10` `STRATUM_RULE` are register-wide non-gating constraints recorded in `_DEPENDENCIES.md`, and blocker output under `FULL_GRAPH` at threshold `INITIALIZED` is advisory visibility only, never work assignment.
- **AX-011** — This contract is lifecycle-neutral. `_STATUS.md` remains the sole lifecycle authority and is untouched by the run that authored this document; the deliverable is at `INITIALIZED` and nothing has been built.
- **AX-012** — Rebuild provenance. This contract replaces the prior contract (SHA-256 `bdb4eea0143ef6c777b0ed5914e7a8846d818437f77ec96cea03d8557f3bcb87`) as a whole and is its rebuild under the S2 Scope of Work rebuild packet (provisional `D-PEC-100`), authored `MODE=INIT` against revision 1.6, PRD v2.4, the SCA-005 feed model and the applied `D-PEC-96` registry. Retired: the prior contract's `DEL-02-04/CON-003` (cited in qualified form because it is no longer defined here), whose empty-first-corpus premise no longer holds (CLM-016, CLM-018); its number is not reused. Every other earlier ID is kept with its meaning, rewritten where its sources changed: the pin, the PRD v2.4 quotations, the Runtime service user-data referent in place of the daemon, the current dependency cells, the corpus observation and the lifecycle state. New: CLM-015 through CLM-018, TBD-005 through TBD-007, REQ-013 through REQ-015, AC-013 through AC-015, VER-012 through VER-014, CON-004 through CON-007, AX-012 and AX-013.
- **AX-013** — A feed profile is PEC's reading hypothesis, never the loop's truth (PRD §16 item 3). Discovery and the historical-or-current label follow the declaration and nothing else, so an undeclared loop is unread by design and its silence is reported, and a declared-historical loop's silence is never staleness (REQ-013, REQ-014, CON-004).
