# Decision Log — COV_SCA002_PRECHANGE

| Ref | Decision | Rationale |
|---|---|---|
| D-1 | `SCOPE = ALL` rather than a subset scoped to affected packages/deliverables | `AGENT_SCOPE_CHANGE.md` Gate 1 step 5 says "scoped to affected packages/deliverables". At the moment this baseline runs, **the affected set is not yet determined** — scope width (intake §7 O-A / O-B / O-C) is the owner's Gate 1 ruling. `ALL` is the strict superset of every option (O-A 17 deliverables, O-C 20, O-B 26) and is the only scoping that guarantees the post-change baseline is comparable whichever option is ruled. Cost is negligible (64 deliverables). |
| D-2 | `AUDIT_DECOMP` executed **inline** by the SCOPE_CHANGE Agent 1 instance rather than dispatched as a Type-2 agent | Agent 2 dispatch is unavailable in this harness. The SCA-002 launch brief directs: "run the deterministic audit tooling inline and record that substitution". Root `AGENTS.md` single-agent fallback applies. The `AGENT_AUDIT_DECOMP.md` v2.1 protocol was implemented as a deterministic read-only script; read-only invariants were preserved. |
| D-3 | Check 9 (Derivative Package Parity) recorded `SKIPPED` | The protocol states: when `DECOMP_VARIANT != DOMAIN`, record `SKIPPED` with reason "Derivative-package parity not variant-owned by this audit". `DECOMP_VARIANT = SOFTWARE`. |
| D-4 | Checks 9b.2 and 9b.3 applied at **full severity**, not advisory `INFO` | The protocol downgrades these to `INFO` for `PROJECT`/`SOFTWARE` "unless companion registers are present, in which case they apply at full severity". Four authoritative companion registers are present and declared in the Companion Inventory (`ScopeLedger.csv`, `Deliverables.csv`, `ContextBudgetQA.csv`, `Companion_Inventory.csv`). Full severity therefore applies. This is what surfaced Finding W-1. |
| D-5 | §3 objective-side `MappedDeliverables` parsed with **range expansion** | The §3 table uses range notation (`DEL-04-01..05`, `DEL-06-01..06`, `DEL-09-01..07`). A literal `DEL-\d{2}-\d{2}` scan undercounts and produces three spurious Check-7 `BLOCKER`s on OBJ-001/003/004. After expansion, §3's objective-side view and the `Deliverables.csv` deliverable-side view **agree exactly for all six objectives**. Recorded because the first pass raised those false positives and they must not be mistaken for real findings. |
| D-6 | Check 6 `artifact_presence_pct` reported as `0.0` without escalation | `AnticipatedArtifacts` values in `Deliverables.csv` are prose descriptions of intended outputs, not filenames, so fuzzy filename matching is not meaningful. All 64 deliverables are `OPEN`; the protocol escalates to `WARNING` only at `IN_PROGRESS` or later. Logged as 64 `INFO` rows. |
| D-7 | Finding W-1 recorded and escalated, **not corrected** | Gate 1 holds no write authority over decomposition truth (`D-PEC-64` §2.5, §5). The correction — if the owner wants one — is Gate 3 exact-text work, and it lies outside SCA-002's declared `MODIFY` mapping change class, so it needs an explicit owner act to bring it in scope. |
| D-8 | Check 10 evaluated against the **SCA-001** snapshot | `_ScopeChange/_LATEST.md` still names `SCA-001` during Gates 1–4 by design (`D-PEC-64` §2.4: the pointer updates only at Gate 5). The SCA-002 session workspace created at Gate 1 is deliberately **not** pointed to and is correctly absent from this check. |
