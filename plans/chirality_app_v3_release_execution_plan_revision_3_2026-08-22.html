1. Decision and owner rulings

Proceed toward v3.0.0-rc.1, but do not begin held implementation merely because this document is merged. The release candidate includes Codex-native delegation as the owner-required outcome. Present authority still permits only the managed app-harness delegation path, so the Root and App instruments named at G0.5 must change before that outcome is implemented. Preparation builds remain unsigned or ad hoc. Only an exact artifact named in a later owner release act may enter Developer ID signing, notarization, stapling, and publication.

Codex owns its inner harness

Codex may create, steer, wait for, interrupt, and synthesize its native descendants according to the capabilities of the pinned upstream runtime. Chirality does not impose a child allowlist, fixed topology, or its own concurrency cap.

Chirality owns the outer authority boundary

Every primary and descendant thread remains inside the same project-data root, explicit readable-root/platform-default envelope, filesystem/network posture, approval system, consent state, protected-path policy, process lifetime, and privacy boundary. This is enforced and empirically tested, not entrusted to prompt text.

AGENTS.md supplies semantic posture

Untyped, Agent 0, and Agent 1 sessions may use Codex-native delegation. Agent 2/TASK does not create another orchestration layer. The first rule preserves Codex’s latitude; the second requires a proved runtime role posture rather than after-the-fact instruction review alone.

Notarization belongs to release

CI and preparation do not notarize. When the owner decides that an RC will actually be distributed, the frozen candidate enters the owner-operated signing/notarization lane. No rebuild is allowed between final source acceptance and release signing.

v3.0.0-rc.1 is not a completed app. It is the first publicly distributable candidate whose product core is coherent and supportable enough for real use while development continues. Stability is defined by bounded behavior, durable failure states, data integrity, and an honest capability surface—not by feature completeness.

3.2 Success criteria

  1. A new user can install the released DMG, pass Gatekeeper, start Chirality, choose Codex (Preview), sign in with ChatGPT, grant project consent, and complete a turn.
  2. Codex can delegate natively when it judges delegation useful; the UI shows attributable descendant activity and correctly routes concurrent descendant approvals.
  3. No primary or descendant thread can read, write, execute, reach the network, persist secrets, or outlive the session beyond the effective approved boundary. Project data is root-bound; any curated macOS platform-default reads are explicit, non-user-data runtime dependencies and are tested separately from the project envelope.
  4. Interrupt, quit, crash, logout, daemon restart, and upgrade do not leave an orphan App Server, stale socket, corrupted project state, or misleading “success” terminal.
  5. The exact public bytes trace to an accepted source identity and release identity, include notices and an SBOM, and pass signing, notarization, stapling, clean-machine, checksum, and download-backcheck evidence.

4.2 Process shape selected for proof

  1. A distinct second LaunchAgent starts and owns one user-wide supervisor. The Electron/Chromium daemon never calls spawn for that supervisor, because the measured signal regression follows browser-process spawning itself.
  2. The daemon connects to the supervisor through a versioned control protocol on a Unix socket beneath a 0700 directory with mode 0600. Peer-UID verification and a rotated boot token bind the connection; plist environment values are never trusted as authorization.
  3. The supervisor canonicalizes project roots with realpath and owns at most one App Server worker per canonical root by default. A worker may never serve a union of projects. If G-ROLE proves that Agent 2/TASK isolation requires a separate process profile, the accepted design may key workers by (canonicalRoot, rolePosture, effectiveConfigDigest); every such worker remains root-specific.
  4. The supervisor creates each worker's process group, app-owned CODEX_HOME, explicit configuration, narrow environment, and newline-delimited App Server stdio. Lifecycle operations live on a separate supervisor port rather than changing AgentEnginePort.
  5. On quit, logout, consent revocation, project close, crash recovery, or upgrade, the supervisor enumerates with explicit exact-pin sourceKinds, uses the returned thread.sessionId rather than deriving a session-tree root, interrupts each known active descendant, and performs background-terminal list/terminate/clean for each loaded thread. Those methods are per-thread and non-recursive. The supervisor then terminates the worker process group by deadline and proves no orphan or stale socket remains. Because one root worker may contain concurrent sibling sessions, process-group retirement is worker-wide: before the kill, every active sibling is captured in one terminalization transaction; after the kill, each receives exactly one durable interrupted or failed terminal naming worker retirement. No unaffected sibling may remain shown as running or completed.
  6. Finder activation during a live turn reconnects the restarted daemon to the existing supervisor inventory. LaunchAgent migration and re-attachment must preserve exactly one durable terminal and must not duplicate a root-bound worker.

4.3 Pre-architecture feasibility decision

G-HELPER runs before WP-03 design freeze. It must prove launchd ownership, packaging location, socket authentication, daemon retirement/re-attachment, active-turn continuity, plist migration, worker process groups, and clean shutdown in a packaged build. Failure sends the architecture back to G0.5; it is not patched around inside Electron.

5.1 Two delegation classes

5.2 Native delegation rule

Configuration intent: native multi-agent capability is enabled for untyped, Agent 0, and Agent 1 sessions; the concurrency cap is left unset so Chirality adds no numeric limit; Chirality does not impose a child allowlist, fixed fan-out, model allocation, or scheduling policy. Upstream/account/platform limits remain effective and must be displayed honestly.

“Without Chirality restrictions” applies to the inner topology—not to external authority. Custom-agent configuration may supply different defaults. The effective authority ceiling is the combination of explicit App Server turn sandbox/approval settings, any supported administrator-managed requirements, and Chirality’s enclosing root-specific OS/process boundary. Current OpenAI documentation says descendants inherit the current sandbox and describes parent live overrides being reapplied in the CLI; equivalent App Server behavior is an exact-pin proof obligation. No descendant may exceed the proved ceiling.

An ordinary Chirality installation does not claim to install a managed requirements.toml: documented managed-requirement sources belong to system, cloud, or MDM administration. When present, configRequirements/read records them as an additional ceiling. The RC itself uses isolated app configuration, marks project .codex input untrusted before thread/start, supplies explicit sandbox and approval policy on every turn, reads back effective configuration, and relies on the enclosing worker boundary.

5.3 Agent 0/1/2 semantics

  • Untyped primary: is a valid human entry posture and may delegate.
  • Agent 0: may delegate to Agent 1 and may directly dispatch bounded Agent 2 work as root AGENTS.md permits.
  • Agent 1: may manage and delegate bounded work to Agent 2 forms; a descendant explicitly dispatched as Agent 1 may continue managing.
  • Agent 2/TASK: executes one sealed bounded objective and may not delegate. A bounded native specialist or ephemeral generalist is treated as Agent 2 even if Codex created it internally.
  • Equivalent evidence: when AGENTS.md requires sealed briefs, scopes, parentage, and returns, the delegated-harness adapter must preserve equivalent observable evidence to the extent exposed by the exact pin. Where an upstream descendant cannot be represented faithfully, it remains upstream-native evidence and is not promoted into a governed Chirality child record.
  • Runtime role gate: G-ROLE must prove a sealed exact-pin agent/feature configuration or a role-specific root-bound worker profile that disables further delegation for Agent 2/TASK without constraining capable sessions. This is not assumed to be a thread/start field. If neither mechanism works, the owning loops must rule the contract conflict; the app may not silently weaken Agent 2 or globally disable the native delegation required for RC.
  • Conformance consequence: an instruction breach makes workflow evidence non-conforming. Hard containment must still hold independently.

5.4 Thread-aware approval contract

The current Root API v1 and broker key are insufficient. G-APPR is first an exact-pin compatibility spike; implementation then requires an accepted Root API v2. The target correlation record is:

ApprovalEnvelope = {
  jsonRpcRequestId,
  projectId,
  chiralitySessionId,
  rootThreadId,
  requestKind,
  subject:
    | { mode: "single", sourceThreadId, turnId,
        requestId | itemId, ancestryEvidence }
    | { mode: "network-destination-group",
        host, protocol, port,
        members: nonEmptyAttributedMemberList,
        confinementEvidenceDigest }
}

The UI shows the requesting primary/descendant and action. Correctly attributed file and command requests receive only the user’s exact decision. Missing or ambiguous attribution is denied/cancelled or allowed to fail; it is never guessed as a parent request. A child action that fails without emitting a request is surfaced to the parent and is never retried with broader authority. Session-scoped approval is used only when offered and explicitly chosen.

Managed network approval is different: current App Server documentation says concurrent requests to the same host, protocol, and port may be coalesced into one prompt that unblocks the group. The Root API v2 therefore represents this as an explicit destination group, not as several fictitiously independent prompts. G-APPR must prove on the exact pin that a group cannot cross project, root, Chirality session, or other authority/source boundary; every exposed member must be attributable, and the UI must state the exact grouped scope. If membership is unavailable or the confinement invariant cannot be proved, the group is denied and managed network approval remains unavailable for RC.

5.5 Upstream evidence used by this plan

Current official documentation says subagents inherit the active sandbox and permission mode; its CLI discussion says live overrides are reapplied on spawn. App Server approval requests carry threadId/turnId and, for command/file requests, itemId; collabToolCall exposes sender and optional receiver/new-thread identity. It documents destination-based network-prompt grouping but not whether grouping can cross thread/session authority. It also does not guarantee descendant instruction sources, child-event subscription, recursive interruption, or the source identity used for every descendant approval. Those remain exact-pin tests. thread/list must be called with explicit appServer and all exact-pin subAgent* source kinds because omission defaults to cli/vscode; returned thread.sessionId is persisted. Experimental ancestor listing and per-loaded-thread background-terminal cleanup may aid observation, but explicit descendant iteration plus process-group termination remains the final cleanup path.

6. Process, containment, and failure behavior

6.1 Required layers

  1. Declared policy: one effective root-bound profile names sandbox mode, approval policy, writable root, restricted readable roots, any curated platform-default reads, temporary-directory posture, login-shell posture, network posture, protected paths, role posture, and exact feature flags. A process never receives a union of project roots.
  2. Enforcement: the exact packaged App Server must enforce the policy for primary and descendant actions inside a root-specific worker. RC explicitly does not adopt Apple App Sandbox; the public artifact uses hardened runtime, while G-SBX proves the separately selected App Server/Seatbelt and enclosing process posture in that bundle.
  3. Positive sentinel: each worker/thread profile performs safe canary reads and writes that must be denied outside the canonical root/declared read envelope, including arbitrary sibling user data and writes to /tmp and $TMPDIR. Login-shell requests are denied. A policy that parses but does not enforce is a failure.
  4. Protected-path compiler: G-PROT round-trips every profile rule through read, file-change, and shell-write enforcement. A mid-path glob or other rule that cannot be represented blocks workspace-write for that project; “expressible subset” is not success.
  5. Client RPC boundary: the adapter exposes a closed method allowlist. RC rejects thread/shellCommand and experimental process/* because the documented implementations run outside Codex’s sandbox; it also rejects every unneeded state-mutating or extra-root method. command/exec is adapter-internal, may be used only for bounded conformance probes with the same explicit restricted sandbox policy, and is never renderer-callable.
  6. Approval boundary: escalation requests surface through the thread-aware broker. No missing UI, disconnected client, or ambiguous request becomes implicit approval.
  7. Process boundary: the helper owns, drains, kills, and scans the process tree. A successful turn cannot hide an orphan.

6.2 Workspace-write enablement

Native delegation remains the RC outcome, but workspace-write is conditional on containment proof. Every turn supplies a root-specific workspaceWrite.readOnlyAccess restriction; the read-only fallback supplies a root-specific readOnly.access restriction. Both may include only the canonical project root plus explicitly accepted curated macOS platform defaults needed for runtime compatibility—never default full-filesystem read access. Workspace-write excludes /tmp and $TMPDIR; any tool scratch space is a 0700, app-managed, ignored directory beneath the canonical root. Login shells are disabled. If the exact packaged candidate cannot pass G-SBX, G-SENT, G-PROT, G-ROLE, G-APPR, and G-ENV, the candidate may expose a native-delegation-capable read-only Codex Preview only if that restricted read envelope passes the same read canaries and the owner explicitly accepts reduced capability at G0/G4; otherwise publication is blocked. No failure justifies silent global delegation disablement, an “expressible paths only” waiver, default full-filesystem reads, or broader access.

6.3 Environment posture

  • Construct the daemon, supervisor, and App Server environments from reviewed allowlists; do not clone process.env.
  • Scan installed LaunchAgent plists and the effective launchd environment. Plists are user-writable input, not trusted policy or authentication.
  • Packaged builds ignore or hard-fail CHIRALITY_ALLOW_SDK_BYPASS; they clamp or reject non-positive approval timeouts rather than turning zero into an indefinite pending grant path.
  • Exclude unrelated API keys, proxy variables, shell startup mutations, and the user’s ambient CODEX_HOME. Set allow_login_shell = false; exclude /tmp and $TMPDIR from workspace-write; point any required command scratch space to the root-local managed directory. Command networking under workspace-write remains off unless a governed K-NET-1 tranche explicitly enables a bounded category.
  • Use an app-specific CODEX_HOME with documented ownership, permissions, backup, deletion, and upgrade behavior.
  • Treat unavailable keyring access, invalid config, unsupported feature state, or sandbox refusal as typed unavailable; never fall back to plaintext credentials or an uncontained process.

6.4 Terminal and shutdown invariants

  • Exactly one top-level durable terminal per Chirality turn: completed, failed, or interrupted.
  • RC interrupts and drains every observed descendant before terminal publication. Exact-pin tests cover child spawn events, subscriptions, ancestry reconstruction, per-child interruption, root interruption, experimental cleanup when used, and process-group fallback. A targeted interrupt uses per-thread mechanisms first; if containment requires worker-wide process-group retirement, every concurrently active same-root sibling is atomically terminalized before the initiating operation returns.
  • App Server EOF, malformed protocol, crash, or helper loss yields a typed failure and invalidates the instance.
  • Shutdown has measured grace and force deadlines; after force termination, an orphan/socket scan must be clean before a new instance starts. Daemon retirement/restart must reattach without losing buffered terminal state.

7. Authentication, data, and privacy

7.1 ChatGPT login for Codex

  1. Before thread/start, explain that selected project context may be sent to OpenAI and record consent in the chosen non-secret store.
  2. Call account/read to display non-secret state.
  3. Default RC flow: account/login/start with type: "chatgptDeviceCode".
  4. Render the returned verificationUrl and userCode; the start response has no documented expiry field. Support cancellation by loginId and wait for account/login/completed plus account/updated.
  5. Browser callback login (type: "chatgpt") may be added only as a declared localhost exception with loopback bind, ephemeral port, bounded lifetime, no token logging, and a specific K-NET-1 disposition.
  6. Logout calls account/logout, ends active Codex sessions, clears visible account state, and verifies the adapter-private credential state is no longer usable.

7.2 Credential boundary

Access/refresh tokens, cookies, Keychain payloads, and auth URLs with sensitive parameters never enter renderer code, project truth, Chirality event logs, support bundles, or ordinary application logs. The device-code ceremony is a narrow exception required by the documented frontend-owned UX: only the returned verificationUrl and userCode cross a dedicated, typed login-UI IPC channel and exist ephemerally in a dedicated renderer view. They are excluded from persistence, telemetry, replay/SSE, screenshots captured by support tooling, support bundles, crash/event logs, and post-ceremony retention. On success, cancellation, failure, logout, or view disposal, Chirality clears DOM/reachable application state and queued IPC references, then destroys the dedicated view. JavaScript string reclamation is nondeterministic, so RC acceptance does not claim physical zeroization of unreachable V8 memory; such a requirement would first move the ceremony outside JavaScript-managed memory. The shared account contract otherwise exposes state such as signedOut, signingIn, signedIn, expired, and unavailable, not token material. G-KEY treats ad-hoc/unsigned → Developer ID and signed N → N+1 as explicit transitions. If credential continuity cannot be proven without weakening storage, the non-destructive behavior is a clearly explained one-time sign-in—not plaintext export, token copying, or silent account loss.

7.3 Typed event projection

Raw Record<string, unknown> payloads may not flow from App Server to the turn coordinator, SSE, events.jsonl, logs, or support bundles. Root HarnessEvent schema v2 becomes a closed type-indexed discriminated union. The App Server adapter validates generated exact-pin wire types, projects only allowed fields before the coordinator, and applies structural redaction before every sink. Unknown types become bounded diagnostic codes, never raw payload. The breaking tranche migrates both Root adapters, frontend legacy consumers/replay, and schema-version readers together.

7.4 Consent store decision

Hosted-engine consent is private user-local application state under the app’s user-data directory, not tracked project truth. For a managed ChatGPT account with a non-null normalized email, it is keyed by canonical-root digest, adapter/provider, a stable non-secret digest of that exact identity, privacy-notice version, and policy version—not merely by account type or identity class. Official App Server documentation permits account/read.account.email to be null. In that state Chirality never creates reusable persisted account consent: it uses a volatile, non-secret login-epoch identifier, requires fresh consent after every app/supervisor start and every account/login/logout/update transition, and invalidates all project consent before context can flow. If the adapter cannot prove a new epoch after an ambiguous account transition, hosted project work is typed unavailable. The daemon checks consent before creating a project-bound worker, before boot or thread/start, and before every turn/start. A change from identified account A to B invalidates the prior digest and requires fresh consent. The server-owned canonical root and turn cwd are fixed for the life of the thread; every differing caller-supplied cwd is rejected because turn overrides persist and instruction reload is not guaranteed. After consent to another root, Chirality acquires that root’s worker and starts a fresh thread. Revocation interrupts work and closes that root’s worker. The tracked project manifest never stores consent.

Official documentation establishes that thread/start loads instruction sources and may initialize required MCP servers, and that turn/start may override cwd. It does not establish that git metadata is read at thread start; this plan makes no such timing claim.

7.5 Claude posture

Claude remains API-key authenticated in RC. Chirality does not advertise, design around, or promise Claude subscription login. Such a capability may enter a future plan only after written Anthropic approval for this third-party product and a new contract/security review. Product copy must follow Anthropic branding requirements.

12.1 Preparation lane

  2. Set the electron-builder macOS identity to null (or the exact accepted equivalent) and keep CSC_IDENTITY_AUTO_DISCOVERY=false; fail if the artifact is opportunistically Developer ID signed.

  6. Run package-level tests and label the result preparation / not for distribution.
  7. Repeat freely during development. None of these builds consumes the owner’s notarization time or claims public-release integrity.

  2.   3. Verify Apple Developer enrollment, Developer ID Application identity, bundle IDs, local credential custody, and the reviewed procedure; perform its preflight/dry run before Apple service calls.

B.3 Experimental dependencies

The reviewed surface treats parent/ancestor filters on thread/list and thread/backgroundTerminals/* as experimental. They may improve observability but cannot be the sole containment or cleanup mechanism. Stable launch/process-group cleanup remains mandatory. Experimental process/* is expressly prohibited because it runs outside Codex’s sandbox.
