1. Decision at a glance

Recommended release posture

Proceed toward v3.0.0-rc.1 as a stable product candidate. Keep existing engines intact, introduce Codex App Server as an explicit Codex (Preview) delegated-harness profile, and make all failure, privacy, packaging, and rollback behavior release-grade even though product development will continue.

1Stable does not mean complete

The release bar is dependable behavior for declared workflows, not closure of every planned feature or every historical deliverable. A feature may remain absent; a shipped feature may not be ambiguous, silently unsafe, or unrecoverable.

2Two runtime profiles

Chirality-native contracts remain the sovereign path for local models and embedded applications such as OpenPipeStress. Codex is integrated as an already-formed external harness, not reduced to a bare model.

3ChatGPT login through Codex

App Server owns the managed browser or device-code login, token persistence, and refresh. Chirality owns the account UI, process boundary, project consent, audit mapping, and safe external-browser handoff.

4Claude-ready, not Claude-promised

The new interactive-account contract must be provider-neutral so a supported Claude account flow can be added later. rc.1 must not claim Claude subscription OAuth until a separate official support, licensing, and integration investigation passes.

5Full harness, bounded authority

Codex retains its native ability to delegate to subagents without a Chirality-authored cap or topology. Chirality secures the enclosing project, permission, data, interruption, and cleanup boundary; AGENTS.md supplies the Agent 0/1/2 operating postures.

Release tension to preserve honestly. The App Server protocol offers exactly the deep integration required, but the official documentation currently calls the command experimental and unsupported for production workloads. Permission profiles are also beta. This does not forbid an RC integration; it requires a visible Preview label, strict version pinning, failure isolation, and no claim that the upstream interface is production-stable.

2. Purpose and release definition

2.1 Purpose

This document translates the owner’s product direction and the App Server investigation into an executable release path. It is written for both humans and agents: humans should be able to judge product and risk decisions quickly; agents should be able to derive bounded work briefs, path scopes, dependencies, evidence requirements, and stop conditions without inferring missing authority.

Planning status. This file lives under plans/ and is therefore forward-looking and non-governing. It does not supersede Root or App authority documents, accepted snapshots, deliverable status, scope-change records, holds, or human gates. After review, accepted content must be routed through the appropriate Root and App instruments before implementation or release authority exists.

2.2 What “stable product” means for this release

Stability is defined operationally. A v3.0.0-rc.1 build is a stable product candidate when all declared primary workflows are deterministic at their boundaries, failures are contained and understandable, persistence is recoverable, sensitive state is isolated, and the packaged artifact can be installed and exercised on a clean supported Mac.

Stable for RC meansIt does not mean
Every shipped engine has an explicit capability profile and never silently substitutes another engine. Every planned provider, agent, tool, domain workflow, or user-interface refinement is finished.
Launch, project registration, login, turn execution, approval, interruption, restart, logout, and failure paths are proven. Every historical deliverable has reached its terminal governed lifecycle state.
Private-data disclosure boundaries are shown before use and enforced by project selection and permission posture. The application prevents a user from intentionally sending selected project material to a hosted engine.
The DMG is signed, notarized, checksum-published, dependency-audited, and rollback-capable. An automatic updater, multi-platform build, or complete support organization must exist.
Preview dependencies are isolated so their failure cannot corrupt the stable product core. Every upstream dependency is itself declared production-stable by its supplier.

2.3 Release train

v3.0.0-rc.1

First public release candidate. Existing engines preserved. Codex delegated harness opt-in and marked Preview. Manual distribution through a GitHub prerelease. Known limitations published.

v3.0.0-rc.N

Only release-blocking fixes, migration corrections, upstream pin updates forced by critical defects, and evidence closure. Avoid feature expansion during the candidate train.

v3.0.0

Stable product declaration after the RC acceptance window and all GA gates. Codex may remain visibly Preview inside a stable app if its isolation and support posture remain explicit.

Post-3.0

Claude interactive account research, deeper local-model capabilities, OpenPipeStress integration, expanded platform support, updater design, and additional delegated harnesses.

5.2 Binding architectural decisions

  1. Codex is a harness adapter. Give it a distinct adapter class and capability descriptor; do not disguise it as a model-only provider.
  2. The Runtime daemon remains exclusive owner. One persistent App Server child per daemon is the default; one App Server thread maps to one Chirality session.
  3. Use stdio only. Newline-delimited JSON over child stdin/stdout; no WebSocket, Unix-socket WebSocket, health listener, or remote host.
  4. Preserve Codex base instructions. PersonaComposer output enters as developer instructions. Verify and record project instruction sources.
  5. Keep native and Chirality tool provenance separate. Native calls are codex-native; dynamic Chirality calls are chirality-dynamic.
  6. Retain Codex-native delegation. Leave native multi-agent tools enabled and do not impose a Chirality concurrency cap, child allowlist, fixed topology, or model/reasoning filter merely because a selection can delegate. Codex decides when and how to use its own subagents within upstream and account limits.
  7. Apply the project’s role doctrine semantically. The effective AGENTS.md hierarchy imputes Agent 0/1/2 postures and patterns: untyped sessions remain untyped and may use native delegation; Agent 0 and Agent 1 may delegate as declared; Agent 2 does not. When the project doctrine requires sealed briefs, declared scopes, parentage, and returned evidence, the native facility must preserve their equivalent. This is an instruction and conformance obligation, not a product-wide switch that weakens Agent 0 or Agent 1.
  8. Contain and observe the whole native tree. Every Codex descendant inherits the parent turn’s live sandbox and approval posture and may not expand project, protected-path, network, or data authority. Interrupt, daemon shutdown, project removal, and app exit drain or terminate all known descendants and verify no child work remains.
  9. Do not overclaim native child identity. Record App Server parentage, source kind, status, and returns when exposed, labeled as codex-native-subagent. A native child is not automatically a Chirality-managed AgentRun or Agent 2 evidence package; audit fidelity is explicitly bounded by the selected App Server protocol.
  10. Alias reserved names. Expose canonical mcp__chirality__name tools to App Server as chirality.name, then restore the canonical identity in audit records.
  11. Use least-privilege permission profiles. Read and workspace profiles are project-scoped; protected paths are projected into deny/read-only rules; command network stays disabled.
  12. Fail closed on profile or capability drift. If the bundled candidate cannot enforce the selected profile, Codex is unavailable. There is no broad legacy fallback.
  13. Never silently switch engines. Missing login, exhausted limits, process failure, incompatible protocol, or failed containment returns a typed unavailable/error state.
  14. Separate account state from API-key state. Add an interactive-account port; do not distort the current API-key-shaped credential interface.
  15. Resume only an identical surface. Binary, protocol, model, instruction, dynamic-tool, and permission hashes must match before thread resume.
  16. Private data is an operator choice. Hosted-engine enablement is per project and precedes transmission; the private domains repository is never inferred from the public Chirality repository.

7.3 Claude interactive-login provision

The v3 contract should support multiple interactive account implementations, but the Codex flow must not be generalized by pretending all providers expose the same login mechanics. Define common lifecycle state and commands, then permit provider-specific metadata and methods behind the port.

RC scope rule: retain the current Claude/Anthropic credential path. Run a separate official-source investigation into whether third-party desktop applications may use a managed Claude subscription login, under what terms, and through which supported SDK. If that work is not complete, the UI says “API key” for Claude and “ChatGPT account” for Codex; it does not present a misleading generic OAuth switch.

10.3 Evidence quality rules

  • Every gate summary names source SHA, artifact SHA-256, App Server package/version/hash, macOS version, architecture, test command, timestamps, and terminal result.
  • Live-account evidence is redacted before persistence and contains no token, callback query, browser history, Keychain enumeration, or unnecessary personal identifier.
  • Development success cannot substitute for packaged success; unsigned package evidence cannot substitute for the signed/notarized candidate.
  • Evidence generated against one App Server version, schema, or permission profile is stale after any of those change.
  • Native-child evidence states exactly what App Server exposed. Missing parentage or event detail is recorded as an observability limit; it must never be reconstructed as a complete Chirality-managed AgentRun.
  • Skipped tests require named justification. No P0 acceptance scenario may be skipped or manually upgraded.
  • A fresh reviewer receives this plan, exact diff, accepted upstream snapshots, test summaries, artifact manifest, and known limitations—not conversational memory.
