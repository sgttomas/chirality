1. Decision and owner rulings

Proceed toward v3.0.0-rc.1, but do not begin held implementation merely because this final plan is merged. The release candidate includes Codex-native delegation as the owner-required outcome. Present authority still permits only the managed app-harness delegation path, so the Root and App instruments named at G0.5 must change before that outcome is implemented. Preparation builds remain unsigned or ad hoc. Only an exact artifact named in a later owner release act may enter Developer ID signing, notarization, stapling, and publication.

Codex owns its inner harness

Codex may create, steer, wait for, interrupt, and synthesize its native descendants according to the capabilities of the pinned upstream runtime. Chirality does not impose a child allowlist, fixed topology, or its own concurrency cap.

Chirality owns the outer authority boundary

Every primary and descendant thread remains inside the same project-data root, explicit readable-root envelope, filesystem/network posture, approval system, consent state, protected-path policy, process lifetime, and privacy boundary. The RC does not load the implicit macOS platform-default read bundle. Enforcement is proved on the actual turn path, not entrusted to prompt text.

AGENTS.md supplies semantic posture

A Codex-native descendant is not automatically reclassified as Chirality Agent 2. AGENTS.md still supplies the semantic Agent 0/1/2 pattern; an explicitly selected Agent 2/TASK posture does not re-delegate and is offered through Codex only when an exact-pin configuration profile proves that behavior. Chirality does not reshape Codex’s otherwise native topology.

Notarization belongs to release

CI and preparation do not notarize. When the owner decides that an RC will actually be distributed, the frozen candidate enters the owner-operated signing/notarization lane. No rebuild is allowed between final source acceptance and release signing.

4.2 Process shape selected for proof

  1. Two launchd jobs. Retain the current daemon LaunchAgent. Add a separately labelled Delegated Harness Process Supervisor LaunchAgent. The daemon remains the single Chirality runtime broker; the process supervisor is a lifecycle helper, not another runtime or agent harness.
  2. Concrete host. The second job executes the packaged Electron binary with ELECTRON_RUN_AS_NODE=1, the bundled runtime-cli/chirality-cli.mjs, and a new --runtime-supervisor entry. @chirality/runtime-cli gains a generic two-job renderer/manager rather than retaining hard-coded --runtime-daemon arguments. The packaging manifest and proof scripts pin exact labels, arguments, environment, KeepAlive, and resource paths.
  3. Install and migration actor. An explicit user action in the packaged Runtime panel invokes the existing authorized runtime-control IPC path. It performs an idle-aware, journalled two-plist transaction: stage/fsync both files, preserve rollback copies, commit both, bootstrap/inspect both labels, and roll back on partial failure. Active turns defer ordinary migration. A forced security migration first runs the retirement protocol. The old crash-only daemon definition is retired; the current daemon job itself is retained with the accepted always-restart posture.
  4. Two private sockets, no TCP. The public project-scoped daemon API remains on control.sock. A second daemon-to-supervisor socket is confined to the app’s 0700 runtime directory with mode 0600. Authentication uses a verified socket/owner record, same-UID path ownership, a boot/generation identity, and a rotated high-entropy bearer token delivered through app-private state. Node does not claim peer credentials it cannot read. K-CONTROL-1 must explicitly authorize the second purpose-limited socket.
  5. Root/profile worker identity. The process supervisor resolves the checkout with realpath. A worker key is always (canonicalRoot, rolePosture, effectiveConfigDigest); there is at most one live worker per exact key and never a union of roots. closeRoot(projectId, canonicalRoot) closes every profile worker registered to that project/root.
  6. Private operational homes. Each canonical root receives a private app-owned CODEX_HOME; role-profile overlays are process-level configuration, not project input. Homes do not share token files or Keychain payloads by copy or symlink. G3 may prove safe upstream keyring reuse across root homes; absent that proof, each root requires an explicit managed login. Logout iterates and verifies every known root home.
  7. Retirement, not attachment. Targeted thread interruption comes first. Before worker-wide retirement, the coordinator fences the worker generation, persists a prepared journal naming every active session/turn, stops the process group by deadline, and idempotently appends exactly one truthful terminal to every affected session—even when its async generator is no longer being pulled. Only then is the journal committed and the root released. A failed append leaves the root quarantined and reconciliation-required; restart completes the journal before new root work.
  8. Fresh recovery. Planned daemon retirement applies the same terminal protocol before exit. After an unplanned daemon crash, startup reconciles any session marked running and any prepared retirement journal, retires the corresponding worker generation, and writes a failure terminal. The next user action starts a fresh App Server thread. No turn replay, buffered-continuation, or attach route is claimed for RC.

“No Chirality topology restriction” applies to the inner organization of work, not to external authority. The same canonical root, restricted reads, write policy, command-network denial, approvals, consent, protected-path rules, process lifetime, and privacy boundary enclose every native thread. Current OpenAI documentation says subagents inherit the active sandbox and permission mode and that live parent overrides are reapplied in interactive clients; equivalent behavior through the exact App Server pin remains a packaged proof obligation.

An ordinary Chirality installation does not claim to install administrator-managed requirements.toml. When one exists, configRequirements/read records it as an additional ceiling; an unmanaged machine returns null. The RC uses isolated root homes, untrusted project configuration, process-level profile overlays, explicit turn/start sandbox/approval policy, effective-config evidence, and the enclosing process boundary.

5.3 Agent 0/1/2 posture without topology imitation

  • Untyped primary: is a valid human entry posture and may use native delegation. This requires the DEL-02-03 text change and the corresponding subagent-governance.ts:205–213 change; it applies only to the new delegated-harness-native class and does not weaken managed-delegation checks.
  • Agent 0: may delegate to Agent 1 and may directly dispatch bounded Agent 2 work as the accepted root AGENTS.md permits.
  • Agent 1: may manage and delegate bounded work to Agent 2 forms; a native descendant explicitly selected as Agent 1 may continue managing.
  • Explicit Agent 2/TASK: when Chirality or an accepted upstream custom-agent selection explicitly imputes this role, it executes one bounded objective and does not re-delegate. On the 0.149.0 candidate, G-ROLE must prove a configuration layer that sets features.multi_agent = false, exact-pin features.multi_agent_v2 = false, and [agents] enabled = false, with generated-schema precedence and readback recorded. Project configuration may not override it.
  • Other native descendants: remain delegated-harness-native. Bounded subject matter alone does not convert them into Chirality Agent 2 or authorize Chirality to replace Codex’s topology. Their evidence is accepted only for what the upstream lineage and hard boundary actually prove.
  • Equivalent evidence: when an explicitly governed role requires a sealed brief, scope, parentage, and return, the adapter preserves equivalent evidence to the extent exposed by the exact pin. Where that cannot be represented, the thread remains upstream-native evidence and is not promoted into a governed child record.
  • G0 failure pre-decision: if G-ROLE cannot mechanically contain an explicitly selected Codex Agent 2/TASK profile, the RC withholds that explicit Codex role entry and labels it unavailable; native delegation remains enabled for the general Codex Preview. Chirality does not globally disable native delegation or silently claim Agent 2 conformance. If the owning governance act instead requires every bounded native descendant to be hard-classified as Agent 2, the Codex Preview is blocked until a supported mechanism or a new owner ruling resolves the conflict.
  • Conformance consequence: an instruction breach makes governed workflow evidence non-conforming. Hard filesystem, network, approval, and process containment must still hold independently.

5.4 Thread-aware approval contract

The current Root API v1 and broker key are insufficient. G-APPR is first an exact-pin compatibility spike; implementation then requires an accepted Root API v2. The RC target is deliberately single-request only:

ApprovalEnvelope = {
  jsonRpcRequestId,
  projectId,
  chiralitySessionId,
  rootThreadId,
  sourceThreadId,
  turnId,
  requestKind,
  requestId | itemId,
  ancestryEvidence
}

The UI shows the requesting primary/descendant and action. Correctly attributed file, command, and supported granular-permission requests receive only the user’s exact decision. A single request with neither requestId nor itemId, missing source identity, ambiguous ancestry, disconnected client, or expired turn is denied/cancelled or allowed to fail; it is never guessed as a parent request. A child action that fails without emitting a request is surfaced to the parent and is never retried with broader authority. Session-scoped approval is used only when the exact pin offers it and the user explicitly chooses it.

Managed network approvals are denied in RC. Official App Server documentation says networkApprovalContext exposes host and protocol, while upstream grouping also distinguishes port and may unblock multiple queued requests. The context does not expose that port or a complete membership set, and the grouping scope is not documented as thread- or Chirality-session-confined. Chirality therefore pins command network off, does not create a fictitious destination-group envelope, and denies any managed-network approval request. OpenAI account/model/turn service traffic remains a separately enumerated adapter transport under K-NET-1.

5.5 Upstream evidence used by this plan

Current official documentation says subagents inherit sandbox and permission mode and describes parent live overrides being reapplied in interactive clients. App Server approval requests carry thread/turn/item attribution; collabToolCall exposes sender and optional receiver/new-thread identity. account/read discriminates account state with account.type, while account/updated uses authMode. A turn/start cwd override becomes the default for later turns, which is why Chirality fixes it to the canonical root. thread/shellCommand has no capability gate and runs outside the sandbox, so the client allowlist rejects it unconditionally; experimental process/*, ancestry, and background-terminal methods remain unreachable because RC does not enable experimentalApi. Command network is already off by default and is also pinned explicitly off. thread/list uses explicit stable exact-pin source kinds, and returned thread.sessionId is persisted. Stable collaboration/thread observations plus OS process-group ownership—not an experimental RPC—provide RC attribution and cleanup.

6. Process, containment, and failure behavior

6.1 Required layers

  1. Declared policy: one effective root/profile identity names sandbox mode, approval policy, canonical root, restricted readable roots, exact immutable runtime reads, temporary-directory posture, login-shell posture, command-network posture, protected paths, role posture, account/consent identity, and exact feature flags. A process never receives a union of project roots.
  2. Enforcement: the exact packaged App Server enforces the policy for primary and descendant actions inside a root-specific worker. RC does not adopt Apple App Sandbox; the public artifact uses hardened runtime, while G-SBX proves the App Server/Seatbelt policy and enclosing process posture in that exact bundle.
  3. Restricted-read choice: both read-only and workspace-write policies set includePlatformDefaults: false. G-SBX inventories only the immutable app/system/tool reads actually required and adds their exact roots. It never accepts arbitrary user data or the platform bundle as an unnamed compatibility exception.
  4. Turn-path sentinel: the conformance fixture starts a real thread and sends a representative turn/start carrying the exact candidate policy. A deterministic fake-model/tool limb must issue each primary and descendant canary; an owner-authenticated live limb confirms representative native delegation. A missing attempt or missing denial is inconclusive/fail, never pass.
  5. Protected-path compiler: G-PROT round-trips every profile rule through read, file-change, and shell-write enforcement. A mid-path glob or other rule that cannot be represented blocks workspace-write for that project; “expressible subset” is not success.
  6. Client RPC boundary: the adapter exposes a closed method allowlist. RC rejects ungated thread/shellCommand, all process/*, configuration writes, imports, arbitrary extra-root operations, and every unneeded mutation method before App Server. command/exec may test only its own separately supplied policy and can never stand in for a turn/start proof.
  7. Approval boundary: attributed requests surface through the broker. Managed command-network requests, missing UI, disconnected clients, and ambiguous requests are denied.
  8. Process boundary: the process supervisor owns generations, process groups, deadlines, retirement journals, and orphan scans. A successful turn cannot hide a live descendant or unresolved journal.

6.2 Workspace-write enablement and sentinel cadence

Native delegation remains the RC outcome, but workspace-write is conditional on containment proof. Every turn supplies root-specific restricted workspaceWrite.readOnlyAccess; the reduced-capability fallback supplies root-specific restricted readOnly.access. Neither loads platform defaults. Workspace-write names only the canonical root as writable, excludes /tmp and the actual $TMPDIR, and uses a 0700, ignored, root-local scratch directory. Login shells and command network remain disabled. If exact required immutable runtime reads cannot be enumerated without admitting user-data or temporary-write roots, the affected profile is blocked.

The expensive canary suite runs on initial profile activation, canonical-root/policy/config/exact-pin/package change, G4, and G7—not before each ordinary user turn. Its deterministic limb has a 60-second budget per policy profile and a 10-second timeout per probe; the live descendant limb has a five-minute operator-test budget and never runs in ordinary CI. Every production turn still performs a deterministic preflight of project/root, account epoch/digest, consent version, effective policy digest, worker generation, and fixed cwd. If the adapter cannot bind the exact policy to that turn/start, the turn does not begin.

If workspace-write fails but restricted read-only passes the same read, role, approval, environment, and process gates, the owner may accept a clearly labelled read-only Codex Preview under the G0 pre-decision. Otherwise publication is blocked. No failure permits full/default reads, implicit platform defaults, temporary-directory writes, login shells, command network, automatic fallback, or global native-delegation disablement.

6.3 Environment and packaged-host posture

  • Construct daemon, process-supervisor, and App Server environments from reviewed allowlists; never clone process.env.
  • Scan both installed LaunchAgent plists and effective launchd environments. Plists are user-writable input, not authorization.
  • Packaged builds ignore or hard-fail CHIRALITY_ALLOW_SDK_BYPASS; they clamp or reject non-positive approval timeouts rather than creating an indefinite grant path.
  • Exclude unrelated API keys, proxy variables, shell-startup mutations, ambient CODEX_HOME, and ungoverned config. Set allow_login_shell = false, explicitly keep command network false, and verify both temporary-root exclusions end to end.
  • Give each canonical root a private app-owned CODEX_HOME with documented permissions, backup, deletion, logout, and upgrade behavior. Role overlays are sealed at process launch. Project .codex configuration and agents are untrusted.
  • Treat unavailable keyring access, safeStorage decrypt failure, invalid config, unsupported feature state, fuse/entitlement incompatibility, or sandbox refusal as typed unavailable; never fall back to plaintext credentials or an uncontained process.
  • G-SBX, G6a, G6b, and AT-058 inventory Electron fuses and entitlements and prove that the Developer ID-signed binary still honors ELECTRON_RUN_AS_NODE=1. A fuse failure triggers the separately scoped helper fallback.

6.4 Terminal and retirement invariants

  • Exactly one top-level durable terminal per Chirality turn: turn.completed, turn.failed, turn.interrupted, or turn.cancelled. Schema v2 keeps cancelled for client/transport cancellation distinct from an explicit user/system interruption; every adapter, coordinator, replay consumer, SSE path, and conformance rule migrates together.
  • A targeted interrupt uses per-thread mechanisms first. Worker-wide fallback fences the generation, persists a prepared retirement journal, interrupts every known loaded thread, kills the process group by deadline, and calls a coordinator-level terminalization API for every captured session—even if its generator is not being pulled. Experimental process and background-terminal RPCs are not enabled for RC.
  • The retirement API is idempotent by workerRetirementId and session/turn identity. Per-session appends are not misrepresented as one filesystem transaction. Closure occurs only when every expected terminal/status is present and the journal is committed.
  • If any append/status update fails, the worker stays retired, the journal remains reconciliation-required, and the affected root is quarantined. Startup and explicit repair replay the journal idempotently. New work for that root is forbidden until backcheck proves one terminal per captured turn.
  • App Server EOF, malformed protocol, crash, helper loss, or unplanned daemon loss yields a typed failure and invalidates the worker generation. Startup reconciles stale running sessions before admitting work.
  • Shutdown has measured grace and force deadlines. After process-group termination, an orphan/socket scan must be clean. Planned or recovered retirement never reattaches to active work; the next turn uses a fresh thread and no unknown-completion operation is replayed.

7. Authentication, data, and privacy

7.1 ChatGPT login for Codex

  1. Before worker creation or thread/start, explain that selected project context may be sent to OpenAI and record consent in private user-local state.
  2. Call account/read; discriminate the returned account by account.type. Do not read an authMode field there—authMode belongs to account/updated.
  3. Default RC flow: account/login/start with type: "chatgptDeviceCode". Render only the returned verificationUrl and userCode; the response has no documented expiry field.
  4. Support cancellation by loginId; wait for account/login/completed plus account/updated; refresh non-secret state through account/read.
  5. Browser callback login (type: "chatgpt") may be added only as a declared localhost exception with loopback bind, ephemeral port, bounded lifetime, no token logging, and a specific K-NET-1 disposition.
  6. Each root-private CODEX_HOME has an independently proved credential boundary. The app may reuse an OS-keyring login across homes only when G3 proves the exact pin does so without file-token copying or cross-root operational-state exposure; otherwise the Preview explicitly requests login per root.
  7. Logout calls account/logout for every known root home, ends active Codex work through the retirement protocol, invalidates consent, clears visible state, and verifies prior credentials cannot start a new turn.

7.2 Credential boundary and migration states

Access/refresh tokens, cookies, Keychain payloads, API keys, and auth URLs with sensitive parameters never enter renderer code, project truth, Chirality events, support bundles, or ordinary logs. The device-code ceremony is a narrow display exception: only verificationUrl and userCode cross a dedicated typed IPC channel into a dedicated view. They are excluded from persistence, telemetry, replay/SSE, screenshots captured by support tooling, support bundles, crash/event logs, and post-ceremony retention. On success, cancellation, failure, logout, or view disposal, Chirality clears reachable application/DOM/queued-IPC state and destroys the view. RC does not claim physical zeroization of unreachable V8 strings.

Two stores require separate proof. App Server-managed ChatGPT credentials use the exact-pin keyring posture and never fall back to plaintext. Existing Claude and Pi/oMLX keys use Electron safeStorage. The current implementation collapses missing storage, encryption unavailability, read failure, and decrypt failure to null; the governed change replaces that with distinguishable missing, storageUnavailable, decryptFailed (blob preserved), and available results. UI and daemon status preserve that distinction and offer non-destructive reauthentication.

G-KEY covers both stores. 7.3 Typed event projection

Raw Record<string, unknown> payloads may not flow from App Server to the turn coordinator, SSE, events.jsonl, logs, or support bundles. Root HarnessEvent schema v2 becomes a closed type-indexed discriminated union. The adapter validates generated exact-pin wire types, projects allowed fields before the coordinator, and applies structural redaction before every sink. Unknown types become bounded diagnostic codes, never raw payload. The tranche migrates Root Claude/Pi adapters, frontend legacy consumers/replay, and schema-version readers together. It explicitly maps all four terminal types, including existing turn.cancelled.

7.4 Consent store and enforcement port

Hosted-engine consent is private user-local application state under the app’s user-data directory, not tracked project truth. For a managed ChatGPT account with a non-null normalized email, it is keyed by canonical-root digest, adapter/provider, a stable non-secret digest of that exact identity, privacy-notice version, and policy version. When account/read.account.email is null, Chirality persists no reusable account consent: it uses a volatile non-secret login epoch, requires fresh consent after every app/process-supervisor start and every account/login/logout/update transition, and fails typed-unavailable if it cannot prove a fresh epoch.

A new HostedEngineConsentPort is injected into runtime service, worker acquisition, and the turn coordinator. It validates project ID, server-owned canonical root, adapter, exact account digest/epoch, notice/policy digest, role profile, and worker generation before worker boot, thread/start, and every turn/start. The session store remains the authoritative fixed-root check: creation records the authorized canonical root and update rejects project-root mutation. Caller-supplied cwd never reaches App Server; the adapter uses the stored root. Because an upstream per-turn cwd override becomes the thread default for later turns, any mismatch fails before the upstream call. Consent to another root starts a fresh root worker/thread; revocation retires the root and invalidates its home.

Official documentation establishes that thread/start loads instruction sources and may initialize required MCP servers. It does not establish that git metadata is read at thread start; this plan makes no such timing claim.

7.5 Claude posture

Claude remains API-key authenticated in RC. Chirality does not advertise, design around, or promise Claude subscription login. Such a capability may enter a future plan only after written Anthropic approval for this third-party product and a new contract/security review. Product copy must follow Anthropic branding requirements.

11.1 Evidence rules and sentinel budgets

  • Fake-model/tool evidence proves deterministic client, policy, and terminal behavior; it does not substitute for exact-pin, packaged, owner-authenticated, or signed-byte evidence.
  • The deterministic primary/descendant sentinel runs at profile activation and whenever canonical root, effective policy/config, exact pin, or package changes, plus G4 and G7. It has a 60-second budget per policy profile and 10 seconds per probe. Ordinary turns perform only deterministic identity/policy/consent/cwd preflight.
  • The owner-authenticated live descendant limb has a five-minute operator-test budget, never records secrets, and does not run in ordinary CI.
  • Unsigned/ad-hoc and self-signed-transition proof supports preparation gates only. It does not support Developer ID G-KEY, G6b, G7, or G8.
  • Notarized evidence applies only to the exact bytes tested. Rebuild, repackage, re-sign, dependency drift, or source change invalidates it.
  • Upstream documentation is a design input. Generated exact-pin schemas and empirical packaged behavior are the executable evidence.

12. Packaging, signing, notarization, and publication

12.1 Preparation lane

  1. Pin and inventory App Server, the bundled CLI entry, and the Electron-as-Node supervisor host as extra resources; preserve and compare every nested byte and existing code identity during packaging.
  2. Set the electron-builder macOS identity to null (or the exact accepted equivalent) and keep CSC_IDENTITY_AUTO_DISCOVERY=false; fail if the artifact is opportunistically Developer ID signed.
  3. Build local/CI arm64 DMGs without production signing/notarization credentials. RC does not adopt Apple App Sandbox.
  4. Generate checksums, dependency inventory, human-readable notices, CycloneDX JSON with a pinned Syft release, minimum macOS declaration, and a release manifest.
  5. Inventory App Server/host bytes, fuses, entitlements, and any pre-existing vendor signatures before and after desktop:dist; drift or an invalid nested signature fails G5.
  6. Author, seat, and review the signing/notarization runbook as a release-carrier deliverable. The document covers exact nested signing order, hardened-runtime and Electron RunAsNode requirements, verification, Apple submission, recovery, rollback, and credential custody, but performs no Apple service call.
  7. On disposable state, use non-production self-signed identities A and B to exercise keyring and safeStorage transition handling, typed failure states, and reauthentication UX. This is preparation evidence only; it neither predicts Developer ID behavior nor satisfies G-KEY.
  8. Run package-level, two-LaunchAgent migration, supervisor-host, containment, and credential tests and label the result preparation / not for distribution.
  9. Repeat freely during development. None of these builds consumes the owner’s notarization time or claims public-release integrity.

12.2 Actual release lane

  1. Owner release act: select the exact accepted candidate for publication; rule the exact K-RELEASE-1 amendment/F-APP-2 lift; record source digest, candidate digest, release identity, and publication route.
  2. Adopt the already reviewed release runbook at its accepted carrier path; do not author release procedure ad hoc during signing.
  3. Verify Apple Developer enrollment, Developer ID Application identity, bundle IDs, local credential custody, Electron fuses/entitlements, and the reviewed procedure; perform its preflight before Apple service calls.
  4. Build once from the frozen source/lock/supply/config identity, or promote the already frozen candidate through a byte-preserving signing procedure. Do not rebuild after final acceptance without restarting the gate.
  5. Sign nested App Server/host binaries, then app and distribution container in the exact order accepted by the runbook; prove the signed Electron binary still supports the supervisor entry. If it does not, stop and route the separately signed helper alternative as new governed scope.
  6. Submit the exact artifact to Apple’s notary service; staple the accepted ticket.
  7. Run G-KEY, then verify codesign, spctl, staple, checksums, SBOM/notices, clean-machine install, migration, native-engine regression, login, turn, delegation, interrupt, and quit on the exact signed bytes.
  8. Publish as a GitHub prerelease; download through the user-visible path and repeat identity/Gatekeeper/smoke checks.

Credential custody: no Apple signing certificate, App Store Connect key, Apple ID password, or notary credential is placed in GitHub Actions under this plan. The existing unsigned CI posture remains intact. Any future hosted-signing design requires its own explicit owner decision and threat/custody review.

  • Chirality-3.0.0-rc.1-arm64.dmg (signed, notarized, stapled).

Withdraw the affected asset and mark the prerelease accordingly; never replace bytes under the same version/tag. Preserve the evidence and incident reason. If safe, point users to the last accepted release and document data compatibility. A fixed candidate receives a new version and repeats the full release lane.
