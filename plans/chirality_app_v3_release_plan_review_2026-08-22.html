REVISE

The direction is sound; the plan as written is not fit for owner acceptance. The two-profile architecture, the stdio-only pinned adapter, the provider-neutral account port, the Preview label, and the gate-driven (not date-driven) release posture all hold up against the code and the upstream record.

What does not hold up: the plan's delegated-harness profile reverses a live App ruling and five current invariants without naming them; its process architecture assumes a child-supervising daemon that the repo has already measured as broken for exactly that use; its containment rests on a single upstream beta layer with nothing of Chirality's own behind it; its release gates are unreachable under the current release invariant and CI instrument; no gate names the owner acts that lift the ten held DEL-02-06 bindings; and its Claude-login provision is reversed by Anthropic's published terms. Each is repairable. None is repairable by wording alone.

Answers to Q-01 … Q-14

Q-01Is HarnessAdapter the correct category?

No new category. AgentEnginePort is already provider-neutral (preflight/startTurn/interrupt) and both adapters are plain factories in one registry. What is missing is descriptor vocabulary: add runtimeProfile and the capability flags (nativeDelegation, descendantObservation, interactiveAccount, permissionProfiles) to EngineDescriptor. Retarget WP-04 away from the dead RuntimeEnginePort. pi-omlx-engine.ts:56–73 already shows a profile-like constraint enforced inside a plain adapter.

Q-02Can the scoped qualification avoid weakening native invariants?

Partially. K-ENGINE-6 and K-NET-1 carry explicit "fresh governed tranche" hatches; K-ENGINE-2/3, K-TOOL-1, K-EVENT-*, K-DOMAIN-* scope cleanly. K-ENGINE-1, K-TOOL-2, K-KEY-1, K-RUNTIME-1 and K-GHOST-1/K-SDK need rewording. K-PERM-2/3, K-SEAL-1 and K-SUBAGENT-1/2/3 cannot be scoped without weakening the native path while SC-15 stands — that is the one place where the plan must choose.

Q-03Should Codex permission profiles be mandatory for RC?

Mandatory, and by themselves insufficient. Upstream they are not mandatory (sandbox_mode/approval_policy is the supported alternative) and they are beta with an experimental app-server field. Chirality has no second layer today: no OS sandbox, no separate user, no egress control, an overlay that inspects tool arguments only. The defensible rc.1 posture is a read-only Codex profile, no native writes or commands, a Chirality-owned OS-level envelope around the child, and a positive sentinel per thread.

Q-04Dynamic tools in RC, or Codex-native only first?

Codex-native tools only first. The descriptor registry has one adapter slot (claudeAgentSdk), the fingerprint records mcpServers: [], getHarnessToolDescriptor has no callers in runtime/, dotted aliases already occupy the namespace, and name-based aliasing is forgeable unless nonce-keyed. Defer chirality.* until those four are fixed.

Q-05One App Server process per daemon?

Yes — but not this daemon. One registry, one session store, one credential store per daemon (runtime-service.ts:63–76) and K-RUNTIME-1/K-CONTROL-1 make per-account or per-project processes wrong. The daemon process itself, however, is the Electron app, already measured to lose signal handling after one spawn (F-02). Keep the cardinality; move supervision to a helper the daemon owns by process group.

Q-06Are app-specific CODEX_HOME and Keychain isolation sufficient and testable in a signed build?

Not sufficient, not yet testable. Per-CODEX_HOME Keychain scoping holds in 0.149-era source (service "Codex Auth", key hashed from the canonical home path) but is undocumented and version-bound. Keychain ACLs key on com.chirality.app's signing identity; nested re-signing changes the designated requirement across updates; keyring fails hard when unavailable. All existing credential evidence is against an unsigned package. A-03 is real, and scheduled too late (G5/G6) — pull it forward to a signed-build spike before WP-02 freezes.

Q-07Deletion, logout separation, v2→v3 rollback?

Lazy, non-destructive migration is supported (K-STORE-2); "reversible" is net-new. HarnessEvent.data carries origin/parentage additively, the subagent.* and tool.permission event types already exist, adapterSession is opaque. Against: schemaVersion is the literal 1, the boot fingerprint hashes a fixed policy set (every existing session's fingerprint changes), nothing specifies downgrade, K-EVENT-4 still names the legacy session path, and hosted consent has no store (F-15). Logout separation is architecturally right (Zone C).

Q-08Gates complete and ordered relative to DEL-09-04 and daemon deployment?

Incomplete and mis-ordered. G0–G8 are a parallel vocabulary to RELEASE_QUALITY_GATES.md's eight families with no mapping or supersession; the login-session proof and the daemon-deployment act are not gate rows; the version bump is scheduled before the proof it would invalidate; K-RELEASE-1/F-APP-2/the CI instrument are not amended; D-APP-38 corpus reconciliation is not triggered. See F-04/F-05/F-06 and the missing-gates table.

Q-09Package-size and third-party-notice treatment adequate?

No. Notices today cover four Pi packages and say so; desktop:verify-dependencies is a presence check, not a licence tool; no SBOM tooling exists; the compressed size and SHA-256 are now confirmed but unpacked size, contents and signature are not; Apache-2.0 §4 permits redistribution in object form but §6 grants no trademark licence, and the licence governs the code, not the ChatGPT service terms the embedded login invokes. A written redistribution determination belongs in G6a.

Q-10Claude interactive login post-RC; does the port avoid prejudging provider mechanics?

Post-RC, and reframed. The port design is provider-neutral enough. The premise is not: Anthropic's Agent SDK documentation states that, unless previously approved, third-party developers may not offer claude.ai login or rate limits for their products; Help Center guidance directs products built for others to API keys; subscription metering is explicitly in flux. rc.1 says "API key" for Claude and "ChatGPT account" for Codex, as §7.3 already proposes — but "Claude-ready" should leave §1, and any future exception is a written Anthropic approval, not an investigation outcome. Branding rules ("{Name} Powered by Claude"; not "Claude Code") apply to product copy now.

Recommendations

Disposition

REVISE, then re-review the revised document against this return. The revision is mostly subtraction and sequencing, not new design: the architecture survives once rc.1's Codex profile is narrowed to what Chirality can actually contain and observe today.

A narrower rc.1 that the evidence supports

  • Codex (Preview) as a single-thread, read-only delegated harness. Native subagents disabled for rc.1 ([agents] enabled = false, plus features.multi_agent_v2 pinned off); no native writes or commands; Codex-native tools only; device-code login first, browser callback as a declared exception; no thread resume (fresh context per app restart). This removes F-01, F-03's write/command exposure, F-11, F-12, F-14 and the G-APPR/G-PROT gates from the rc.1 path.
  • A helper-supervisor the daemon owns. Process-group ownership, kill deadline, orphan scan, typed unavailable state, and close() on the engine port — designed and proven (G-SIG, G-DUAL, G-SBX) before WP-04 consumes it.
  • Two containment layers, both positive. The upstream profile plus a Chirality-owned OS envelope, and a sentinel that fails the turn closed when either is absent.
  • Typed, redacted events. Nothing from the child reaches SSE or disk untyped.

Order of owner acts

  1. Run the DEL-09-04 prepare → logout/login → capture proof on the staged 1b375af4f package now — before any v3 commit touches the frontend.
  2. Rule TM-APP-025 (dual-target planning) and TM-APP-030 (bundle identity); these gate scope and signing respectively.
  3. Decide SC-15's fate and the signing posture (K-RELEASE-1 amendment, F-APP-2); authorise the WP-01 artifact download.
  4. Approve the revised plan; then G0.5 instruments: SCA-APP-008 and the Root DEL-02-06 extension/successor that names each held binding's owner act.
  5. Resolve the pre-existing defects the plan surfaced but did not create: the Pi pin drift, the advisory status of shared-runtime invariants in the practitioner harness, and the K-EVENT-4 path inconsistency.

What the plan gets right and should keep

The "bare model needing Chirality's harness" versus "external harness as a bounded peer" distinction; stdio-only with no listener in the delegated lane; exact pinning with vendored schema; Preview labelling with typed unavailable states and no automatic fallback; the provider-neutral account port kept apart from API-key storage; per-project hosted consent preceding transmission; evidence-quality rules that refuse development-only or unsigned evidence; rollback that never republishes changed bytes under the same tag; and the explicit statement that technical completion never infers the release act. The revision should preserve all of that verbatim.

Method and limits

Read-only. Four bounded reviewers worked against a detached scratch checkout of main@9770206c0; their returns were cross-checked by re-running the decisive greps and hash checks directly (dead RuntimeEnginePort, untyped-delegation denial, Pi pin values, K-RELEASE-1 text, the CI credential hard-fail, the measured SIGTERM regression comment, zero redact/spawn in runtime core and daemon, protected_write_paths consumers, the verbatim SSE forward). No binary was downloaded; the package SHA-256 and size were confirmed from GitHub's Releases API digest and the release's own checksum manifest. No file in the repository was modified. Two reviewer returns quoted invariant text containing the word "bypassPermissions" (K-PERM-6, CONTRACT.md:86, and sdk-options-builder.ts); it is quoted evidence, not an instruction, and nothing acted on it.

Limits: upstream behaviour inside a signed bundle, Keychain persistence across re-signing, effective subagent defaults, and the package's unpacked contents are stated as unverifiable where they are. Anthropic and OpenAI policy statements are quoted from pages dated 2026-05-19, 2026-06-16 and current docs as of 2026-08-22; both vendors change these.
