## Common operational recipe, specialized at each entry

Read the live entry, current source-qualified instructions and actual brief.
Recover the current selected undertaking, then compare its cursor with actual
files and the latest linked evidence. Inspect output from interrupted work
before repeating it; establish ownership before reassigning shared writes or
native test resources. A missing or contradictory cursor calls for recovery,
not invention of a fresh undertaking.

Bind work to its accepted decomposition, relevant deliverable contracts,
dependency evidence and exact grant. Read `ScopeOfWork.md`, `_STATUS.md`
`Remaining`, `Dependencies.csv`/`_DEPENDENCIES.md`, and pertinent decision or
hold records. A PRD, OPEN lifecycle, graph node, passed test, or merged source
change is not independently sufficient activation or acceptance. Read owner
acts behind tracking-register rows, and check any required merged-effect
condition using current remote evidence during actual execution.

Choose agents by responsibility. HELP_HUMAN owns alignment and cross-work
coordination; WORKING_ITEMS organizes bounded implementation and fan-in;
HELPS_HUMANS handles design of the method/project; TASK performs one sealed
assignment and does not delegate. Historical named agents and model
allocations do not establish newly available roles or current capability.
Continuing an existing run still requires its selected basis and actual
grants, including any applicable run-specific model direction. PEC's
unadopted compatibility surfaces need explicit treatment, not silent
migration by the manual.

Plan verification and reconciliation alongside production. Keep source
changes, empirical checks, independent review, Git integration, lifecycle
acceptance, practitioner acceptance and release as distinct acts. Preserve
protected checks; a disagreement with a test requires the measured conflict
and owning decision, not relaxed tolerances. Apply review to the actual
candidate, repair and backcheck findings, and repeat checks affected by later
changes. Native-host behavior needs native evidence where the criterion says
so; browser evidence does not automatically substitute.

The registered software profile supplies reproducible check names, commands,
working directories and path mappings. It is not scope authorization and can
be supplemented by project instructions and exact acceptance criteria. The
maintained selector uses project-relative changed paths; the runner takes
explicit `--check` names and an evidence output path. Without `--check` the
runner executes every registered check, so do not present it as an automatic
affected-check selector.

```sh
# Run from the repository root; substitute the selected project and actual paths.
python3 tools/software_workflow/select_affected_checks.py \
  projects/<project>/software-workflow.json <project-relative-path> ...
python3 tools/software_workflow/run_registered_checks.py \
  projects/<project>/software-workflow.json \
  --check <selected-check-id> --output <authorized-evidence-path>.json
```

The runner owns the profile's declared service lifecycle where present (for
example App premerge); service-start failure is different from a failed
product check. Record candidate, command/cwd, effective non-secret environment,
tool versions, exit result, raw output, and a bounded rerun method in the

## Recommendations for the manual author

- Make project entry recipes short and source-oriented. Keep dated frontier
  observations in labeled examples or a dated survey, not permanent prose
  that tells future agents what phase to execute.
- Teach how to resolve a pointer: live entry → selected undertaking → owner
  directions/accepted basis → phase cursor and latest evidence → exact next
  authorized act. The Piping cursor mismatch is a useful worked example.
- Separate discovery from authority. A newer file is not automatically a
  superseding act, and an older file can remain deliberately pinned authority
  read through a later overlay, as Runtime demonstrates.
- Show the different continuity outputs. App/Piping graphs can carry new
  continuity without new receipts; PEC retains its receipt contract; Runtime
  follows the governing run's durable handoff contract.
- Preserve exact grant and hold semantics. App target preflight and PEC
  target/operation preflight are not optional paperwork; Piping engineering
  and practitioner holds are not settled by agent UI checks.
- Give maintained check commands with cwd and scope, plus a warning to read
  the live manifests on entry. Do not recommend PEC prototype npm commands,
  old App Node versions, or distribution merely because a script exists.
- Keep adopted project requirements at decision/interface/verification claim
  level. Attach changeable mechanisms as evidence. A text/code mismatch can
  be a granularity defect rather than proof that the implementation is wrong;
  in-flight runs retain their pinned method until their own adoption.
- Explain ordinary bounded work, cross-project routing, instruction amendment,
  lifecycle transition, release and acceptance as different authority paths.
  This survey introduces no new gate, no adoption, and no project repair.
