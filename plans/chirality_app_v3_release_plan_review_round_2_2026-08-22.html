The eight checks §15.4 asked for

1Does Revision 2 faithfully apply each F-01…F-23 disposition?

Mostly. 15 faithful, 8 partial, one limb contradicted. The contradiction is F-01's second limb: round 1 said delete "untyped sessions may use native delegation"; §5.3 line 253 reinstates it ("Untyped, Agent 0, and Agent 1 sessions: may use native Codex delegation"). The partials are itemised in §Fidelity below; most are one-line fixes (name the file K-RUNTIME-1 lives in twice; name K-SDK-1…4 correctly and add K-SDK-5 as new; encode the config enum; add DEL-09-05/06 to the index; put the governed-fallback distinction in the body).

2Is native delegation preserved without confusing inner-topology freedom with authority expansion?

Conceptually yes; mechanically not yet. The "inner topology is Codex's, outer authority is Chirality's" split (§5.2) is the right frame. Three things break it in practice. (a) §5.2's "a custom agent may narrow its posture; it may not expand the enforced ceiling" is contradicted upstream: agent files "can override the same settings as a normal Codex session config", including sandbox_mode, and shipped examples set it in both directions; the only real ceiling is requirements.toml (allowed_sandbox_modes, allowed_approval_policies, allowed_permission_profiles) plus project-trust gating of .codex/agents. (b) §4.2 mandates one App Server per user/app identity while §6.1 mandates a per-thread project root; a single shared process can only be contained to the union of open projects, so the Chirality-owned envelope cannot express "no broader root than the parent session" — enforcement stays upstream, which is round-1 F-03 restated. (c) Agent 2 / TASK sessions: §5.2 declines any per-session-type control and B.1 enables [agents] globally, so "Agent 2 does not create another orchestration layer" is only detected after the fact (AT-030/031), which K-PERM-2 — "subagents … require runtime enforcement" — does not permit. None of these contradicts the owner's ruling: disabling native delegation for Agent 2 and untyped sessions at thread/start is role doctrine, not a topology cap.

3Can primary and descendant approvals be routed and contained on the exact pin?

Unproven, and the plan treats it as settled. Upstream confirms approval requests carry threadId, turnId, itemId. Upstream does not say which threadId a subagent-originated approval carries, whether an app-server client is subscribed to spawned child threads at all, or that a child spawn emits thread/started; and it documents a third outcome — "an action that needs new approval fails and Codex surfaces the error back to the parent workflow" — i.e. no client request. No protocol schema ships in the 0.149.0 release to settle it. On the Chirality side the change is larger than "revise the broker key": PermissionDecisionRequest is {requestId, decision, reason?} under RUNTIME_API_VERSION = "v1", turnId is never populated on live permission events, and the decision port is Root-owned with one implementation inside the Electron daemon. G-APPR must become a spike with a fallback design that tolerates parent-thread attribution and no-request outcomes, and the protocol change must be scoped as a Root API-version bump.

4Are the helper, signal, sandbox, event-redaction, credential, and consent designs executable in the packaged app?

Helper: the plan never says who launches it. The measured regression (electron/main.ts:856–859) is caused by forking from the Chromium browser process, not by what the child is; a "dedicated helper" spawned by the daemon re-triggers it, and a launchd-launched helper is not in the daemon's process group. Transport, re-attach across daemon retirement, packaging location, signing, and authentication are all unnamed. Signal: G-SIG sits at WP-03 exit, after the design it would invalidate. Sandbox: the App Sandbox question has a documented answer — notarization requires hardened runtime, not App Sandbox, and Apple says an embedded tool "must inherit the containing app's sandbox configuration" — so the plan should decide not to adopt App Sandbox now; what remains for the spike is nested-Seatbelt behaviour inside a hardened-runtime bundle, and the repository has no entitlements artifact to test. Events: the fix is structural (close HarnessEvent.data as a union in the Root adapter before the turn coordinator), not a scan; the existing scanner has one key pattern and lists .ndjson but not .jsonl. Credentials: G-KEY is referenced at line 424 and never defined; safeStorage items are signature-bound, so the ad-hoc → Developer ID transition silently loses stored credentials. Consent: the only pre-thread gate is enabledAdapterIds in createSession; it is not re-checked at boot or turn, and upstream lets turn/start override cwd, so consent must be enforced per turn and the store cannot be the git-tracked manifest.

5Does G0.5 prevent every held binding from being lifted by implication?

Not yet. §8.3 says "all ten" and enumerates eight; 5_root_semantic_and_regression_evidence and the cutover/release notice appear in no gate. G0.5's pass evidence is that each binding has a named act; WP-03 and WP-05 are Root implementation work whose entry conditions name G1/G2/G-SIG but not the implementation_act and source_identity bindings that block implementation. (REM-001 itself was satisfied by the preparation-only activation in PR #605; the live hold is the implementation act.) Also unnamed: App-side holds — fence F-APP-2 (D-APP-97: "continues to fence signing, notarization, and distribution") and the APP-HOLD-1 preflight — and the three App rows (TM-APP-027/028/032) that park on the same DEL-02-06 gate G0.5 proposes to move.

6Is notarization unambiguously absent from preparation and mandatory only at actual publication?

Yes — this is Revision 2's cleanest improvement. The credential-free CI ruling means the existing desktop-release-template.yml and its pinning tests need no amendment; AT-038 and §12.2 match them. Two gaps remain: the release lane's "proven order" has nothing to prove — BUILD_AND_RELEASE.md contains zero signing or notarization tooling tokens and package.json's mac block has no identity, entitlements, or notarize keys — so the procedure must be authored and dry-run as a G6a exit deliverable; and the preparation lane should pin identity: null, otherwise a preparation build on a machine holding a Developer ID is silently signed and AT-038 has no configuration to enforce.

7Are all work packages owned by valid App/Root instruments?

No. Only WP-02 and WP-06 name a deliverable; nine "Owning route" cells name packages, agents, humans, or code paths. Root's SOFTWARE decomposition has no deliverable owning engine adapters, a supervisor helper, account contracts, or the event schema; DEL-02-06's accepted Scope of Work is preparation-scoped (REQ-027 "shall not write implementation bytes"; exclusion block makes runtime/** read-only and forbids adding client writes by brief amendment). The lawful Root route is a Root scope change (next free ID, SCA-004) amending decomposition truth and a fresh exact-bytes acceptance of the amended SOW, plus an M2 instruction-surface tranche under DEL-02-03 for the AGENTS.md doctrine change. On the App side, DEL-04-01 ("no generic adapter ownership") and DEL-08-04 ("the daemon owns operational delegation execution"; amended 2026-08-21 with an open D-APP-103 item) are over-read and belong inside SCA-APP-008 (confirmed next free ID).

8What remaining P0/P1 findings, missing gates, or unsupported claims exist?

Twelve P0/P1 findings after consolidation (table below), four dangling or dropped gates (G-KEY undefined; G-PROT dropped with AT-019 hedged to "expressible"; G-SBX with no acceptance scenario; no gate for a live turn during daemon retirement), five dropped round-1 scenarios without justification (version identity, account restart/refresh, instruction identity, thread/session deletion, nested-signature integrity in the preparation lane), and the unsupported upstream claims corrected in §Upstream.

Upstream corrections to carry into revision 3

  • §5.2 ceiling rule — reverse it. Agent files "can override the same settings as a normal Codex session config" (sandbox_mode, mcp_servers, …). The enforced ceiling is requirements.toml; project-scoped .codex/agents load only for trusted projects.
  • §5.5 inheritance sentence — scope it. "Subagents inherit your current sandbox policy … Codex also reapplies the parent turn's live runtime overrides" is confirmed verbatim, but the reapply sentence is documented under the CLI surface only; the app/IDE blocks carry only the inherit sentence. Record it as a runtime assumption for app-server hosts.
  • Approvals carry threadId, turnId, itemId (confirmed). Which thread a subagent's request names, and whether the client is subscribed to child threads, is undocumented; a fail-with-no-request outcome is documented. No protocol schema ships in the release; generate types from the pinned binary.
  • Collab items: collabToolCall fields are {id, tool, status, senderThreadId, receiverThreadId?, newThreadId?, prompt?, agentStatus?} — receiverThreadId is singular. The multi-agent tools (spawn_agent, send_input, resume_agent, wait_agent, close_agent) are stable and on by default; only the thread/list parent/ancestor filters and thread/backgroundTerminals/* are experimental.
  • Descendant drain via protocol exists only on the experimental path (thread/list(ancestorThreadId) → per-child turn/interrupt → backgroundTerminals/clean); there is no thread/interrupt; keep process-group kill as the non-experimental fallback.
  • thread/start loads instruction files (returns instructionSources) and initialises required MCP servers — consent must precede it; git metadata is not documented as read there; turn/start can override cwd, so consent is per turn.
  • Device-code login returns type, loginId, verificationUrl, userCode — no expiry field; account/login/cancel exists.
  • Appendix B.1 keys and values are valid for the 0.149.0 schema. Add: sandbox_workspace_write.network_access defaults false; keyring fails hard (consider auto); web_search is overridden to live under full-access sandbox settings; approval_policy = "untrusted" is in the prose reference but absent from the schema enum; turn/steer requires expectedTurnId and accepts no overrides.
  • App Sandbox: notarization requires hardened runtime and a Developer ID, not App Sandbox; Apple: an embedded command-line tool "must inherit the containing app's sandbox configuration". Decide now not to adopt App Sandbox; the remaining spike is nested-Seatbelt behaviour in a hardened-runtime bundle, which neither vendor documents.
