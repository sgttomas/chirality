1The whole repository at a glance

Chirality is one git repository. The top of it holds the rules; below it sit the places where work happens. Everything authoritative is plain text files — there is no hidden database holding project truth.

  • 1Framework root = the rulebook: the constitution (docs/), the agent role definitions (agents/), reusable skills, deterministic tools — plus _DomainEngines/, the shared tier-0 control area for domain-engine integration (profiles, rulings, bridge snapshots). Release-managed — you don't casually edit it.
  • 2Rules flow downward. Everything below inherits the framework's invariants. A work area can add detail but can never weaken a framework rule (see §3).
  • 3Project roots build software. Each contains many deliverables moving through a lifecycle (§5–6).
  • 4Domain roots turn source documents (handbooks, standards, the app's own governance) into structured, indexed knowledge that the projects rely on.
  • 5Plain text in git is the single source of authoritative truth — corrected from the old absolute phrasing: DIRECTIVE §2.5 does permit non-authoritative convenience state (UI preferences, panel state), but it can never be treated as project truth or override a governed file.

2The five rules everything obeys

Before any diagram of who or how, here are the standing principles. They are the reason the system is auditable and safe to let agents work in. Every later diagram is just these rules made concrete.

  • 1Files are the truth. State lives in readable text you can diff and review by eye. This is why a database is rejected for governance state — you can't review a binary blob at a gate. That rejection is now a formal ruling, D-GOV-01 (ruled 2026-07-01; §10–11), so it stops being re-argued.
  • 2Agents propose; humans decide. An agent can draft, analyze, and recommend — but the moment something becomes binding (approved, issued), a human authors that record. A hard line, not a setting.
  • 3Evidence first. A claim without a cited source is a defect. This is what lets a reviewer trust the work.
  • 4No invention. When the answer isn't known, the agent writes TBD rather than fabricating one. Honest gaps beat confident guesses.
  • 5Surface conflicts. If two sources disagree, the agent points at both rather than silently picking one. (§9 shows what happens when this rule isn't backed by a mechanical check.)
Correction — the constitution's own status The previous explainer presented the K-* rules as settled canon. In fact docs/CONTRACT.md and docs/DIRECTIVE.md carry "DRAFT pending human ratification" banners — the rules are real and practiced, but the ratified record is still owed. Per K-CLAIM-1 (don't overstate warrant), this explainer and every harness report label that status rather than hide it. Partially settled 2026-07-01: D-GOV-05 ratified a minimal harness basis — the source-of-truth rule, human authority (K-AUTH-1/2), the generated-output rule, path containment (K-WRITE-2), provenance (K-PROV-1), status canonicity (K-STATUS-1), and the severity taxonomy. The remainder of the root docs stays DRAFT on its own ratification track (§11).

3Two layers: the rules vs. the work

This is the single most important structural idea. The framework root defines invariants; the working roots do the work and may specialize — add their own detail — but may never weaken a framework rule.

  • 1The framework root sets invariants — the K-* rules. Think of them as the constitution; changing one is a deliberate, human-ratified act, not a routine edit.
  • 2A working root can be stricter or more detailed (its own decisions, registers, conventions, even its own invariant namespace) but can never relax a framework invariant. A child may add rules; it can't repeal the parent's.
  • 3The same ceiling applies everywhere. This is what lets many work areas coexist without the rules fragmenting — and it is why the harness reads each project through an adapter instead of forcing one abstract lifecycle onto both (§10).

4Who is allowed to act

Agents are not interchangeable workers — they have roles with explicit, limited authority. The key question the system always asks is not "how smart is the agent?" but "what is this role permitted to write?"

  • 1The human holds the top. Approvals, gates, and questions of "does this rule apply here?" are human acts. An agent never signs off binding work.
  • 2Type 0 (HELPS_HUMANS) is the generalist that helps maintain the rulebook itself, always paired with a person.
  • 3Type 1 personas each own one lane: DOMAIN_ENGINE orchestrates across roots, WORKING_ITEMS produces deliverable content, TOOLMAKER builds tools, CHANGE is the only one that commits to git, and the AUDIT_*/EVALUATION_* family checks and reviews.
  • 4Type 2 (TASK) is a tightly-bounded worker. It may write only within the folder it was sealed into — it cannot reach elsewhere.
  • 5Tools are advisors, not authorities — with one precisely-drawn exception the old explainer blurred: a precondition guard inside an existing write tool (the write_status.sh patch, §6) may refuse an objectively-broken transition. It still never authors state, never approves, and never edits the record. The read-only harness itself refuses nothing.
Provenance — this repository is the first exhibit Everything in this repository — the code, the plans, most of this thesis — is agent output produced under owner governance: humans authored no code, only governance documents, workflows, specs, and rulings (noted 2026-07-01). Each artifact arrived through the loop this section describes — agents propose, checks run, the owner rules, CHANGE publishes, and the record keeps the evidence: git history, the decision registers, run records. The claim is deliberately narrow: not "agents built it, so trust it," but "the work is inspectable." No attributed crossing of the human-authority line has been found in the record — and attribution itself (free-text actor strings) is the known weakness, which the ruled human_actors allowlist (D-GOV-04, 2026-07-01) and the planned write-path guard close, while the drift metric (the 92/154 baseline, §9) measures what slipped past discipline.

5Anatomy of one deliverable

A "deliverable" is one unit of work, living in its own folder. Open one up and you'll find a small, predictable set of files — each with a single job. Learn these five and you can read any deliverable in the repo.

  • 1_STATUS.md — the canonical state file by rule (K-STATUS-1). Its Current State line is the authority on where the work is; frontmatter records the approval SHA — true for all 53 app-dev files, but piping's 101 files carry no approval-SHA fields at all (their frontmatter is just Current State + Last Updated); this schema divergence is why adapters and per-root guard preconditions exist (§6, §10). §9 shows the honest caveat: in practice this file and its own history disagree in 92 of 154 deliverables (all in piping; app-dev is clean) — which is precisely the harness's first job.
  • 2_CONTEXT.md — the sealed basis: the precise, gate-approved set of inputs the agent is allowed to use. The agent works from this, not "the whole repo." The harness's tranche brief is a projection of this file plus a plan row — never a replacement for it (§10).
  • 3_REFERENCES.md — governing sources pinned by content hash. Known defect the harness lints: some reference rows and run-record frontmatter embed machine-absolute paths (/Users/…), a latent SPEC §0.2.4 violation.
  • 4Dependencies.csv — this deliverable's edges, each with cited evidence. Authority is local to the folder; there is no single central graph (the piping project keeps an approved overall DAG as a separate, human-approved exception).
  • 5_run_records/ — immutable snapshots of every run, kept forever, including failures. This is the audit trail the harness's evidence records will sit beside.

6A deliverable's journey — the states

That _STATUS.md file moves through a fixed sequence. Two points on the track are the constitutional minimum human gates (K-GATE-1) — but they are not the only human acts on the track.

  • 1The seal gate. Before real work begins, a human approves the sealed basis (the _CONTEXT.md from §5). No bounded TASK runs until this is sealed (K-SEAL-1).
  • 2The approval gate (CHECKING → ISSUED). Moving to ISSUED is a human act and the approval binds to a specific git commit (K-AUTH-2). This is the line no tool must ever cross on its own.
  • 3Correction to the old framing. The previous explainer said "everything else can be machine-assisted." Per SPEC §3.3 the move into CHECKING is also a human transition. The two gates are the constitutional minimum (K-GATE-1), not the complete list of human acts. Machines verify readiness up to CHECKING — hashes, citations, evidence presence — which the system already names: warrants go UNWARRANTED → CITED → REVIEWED → AUTHENTICATED; REVIEWED is machine-checkable readiness, AUTHENTICATED is the human act.
  • 4The shell write-path fix. The verified write_status.sh hole is closed by an objective precondition guard, shipped in the harness's first PR but independent of the read-only harness itself. Live verification (2026-07-01) corrected two details: the guard's preconditions are adapter-declared per root — the git-verifiable approval SHA is required where the root's status schema carries SHA fields (all 53 app-dev files); piping's 101 files carry none, so piping gets the committed-human-ruling-path check only, with the missing SHA surfaced as a REVIEW finding until a piping schema alignment is ruled. And the "vendored copy" in staging is a gitignored, regenerated export artifact — the patch lands in the canonical tools/scaffolding/write_status.sh and the export source, with "both copies byte-identical" kept as the acceptance check. Prior art the PR must reconcile with: app-dev's frontend already implements these guard semantics in TypeScript (transition.ts: from-to transition rules, authorized-actor enforcement, required approval SHA for CHECKING/ISSUED, exposed via a status-transition API route — deliverable DEL-07-04), so the shell script is not the only status-write path; the shell guard aligns with that prior art or records why it diverges. And honestly: tool usage is guided, not enforced — a hand edit bypasses any guard; the guard hardens the sanctioned path, and drift detection covers the rest.

7The workflow loop — how work actually flows

Zoom out from one deliverable to the whole cycle of doing work. A task is not "type a request and get code" — it is a controlled intervention that moves the project from one trusted state to the next, then folds the result back into the shared basis. Follow the numbers.

StageWhat happensWho / where
① Basis & Authority Assemble the controlled inputs and decide who may touch what, with which tools. If the basis is incomplete or contradictory, work pauses here. sealed into _CONTEXT.md; human seal gate
Execute & Evidence A bounded agent does the work in isolation and records what it did, with cited evidence. Type-2 TASK → _run_records/
② Check An independent pass verifies the output against the basis and acceptance criteria. Updated: the bench harness runs the tranche's declared validation commands itself and captures the outputs (run-validations); scope and evidence checks read those tool-generated records, never agent attestations. Judgment on sufficiency stays with the reviewer. bench harness (mechanical) + checker/reviewer (judgment)
③ Approve A person authorizes the transition and the approval binds to a git commit. Verification ≠ approval — a green check is structural evidence, never acceptance. human → _STATUS.md + ruling
④ Propagate & Reconcile Affected neighbors/interfaces are notified, superseded versions retired, and the result folded back into the shared basis — only then does the item close. edges, _LATEST pointers, snapshots

8Two kinds of working root

Projects and domains both do governed work, but their internals look different — because they do different jobs. This matters because a tool written for one shape won't fit the other, which is why the harness pilots on the project shape and defers a domain-shape variant (§11).

  • 1Project shape is organized around deliverables and their approval lifecycle — the files from §5, plus the human rulings in _DECISIONS/. The harness reads each project through a small adapter manifest, because even the two pilot projects encode the pattern differently.
  • 2Domain shape is organized around a 6-gate decomposition pipeline: sources are admitted (with hashes), checked, and accepted at each gate. The catalog.sqlite here is the pattern the D-GOV-01 ruling (2026-07-01) formalizes for Chirality governance state and harness projections: a rebuildable, gitignored index you can delete and regenerate — never the authority. The scope matters: engine-owned domain stores (the OpenPipeStress SQLite-backed persistence store for model states and runs) are sanctioned authoritative domain truth under K-DOMAIN-1 and the adopted profile — governed by the K-DOMAIN family, not by this rule. One verified gap is parked in §11: domain gate acceptance binds by content SHA-256, not a git commit SHA.

9The drift problem — why a harness at all

New section. The rules in §2 are practiced, but nothing mechanically checks that the many places restating state still agree with the authority. They don't. This is the concrete, measured problem the bench harness exists to fix — shown here with the system's own files.

  • 1The authority statement — the owner did rule Gate 2 on 2026-06-21; the top of the summary file records it.
  • 2A stale paragraph in the very same file still says the opposite. Nothing flagged it, because nothing checks prose restatements against each other.
  • 3The index contradicts itself — a status banner written early, a table updated later.
  • 4Header comments drift from field values — resolved today only by another inline comment declaring which surface wins.
  • 5Even filenames restate state and go stale. None of this is carelessness; it is what mutable narrative surfaces do without a mechanical audit.
  • 6At project scale the same disease measures 92 of 154 _STATUS.md files whose Current State disagrees with their own last parsed history entry — all 92 in piping (app-dev is 0/53), and all with a single mechanical signature: the history records a human-approved advance to CHECKING, but the frontmatter Current State line was never updated from IN_PROGRESS. That number is the harness's baseline metric: the tool succeeds if it trends down, and fails if it produces more planning instead.
Update — the depicted contradictions are now corrected The control-area contradictions shown above were corrected by the D-GOV-06 cleanup, published 2026-07-01. The figures stay unchanged: they are the measured evidence, and the cleanup diff becomes the harness's adversarial fixtures — the first live files its self-check must pass. The system measured its own drift, ruled the fix (D-GOV-06), and executed it. The 92/154 project-scale baseline in ⑥ remains the live metric until the harness lands.
The design consequence The fix is not a database that owns status (that fork is closed by D-GOV-01, ruled 2026-07-01 — see §10–11), and not more registers restating state in new places. It is a checker with no governed writes that audits every restated-state surface — status files, pointer files, banners vs. tables, header comments vs. fields, filenames vs. fields — plus honest parsing: histories are prose, so every parse is labeled PARSED, PARSED_WITH_ASSUMPTIONS, or UNPARSEABLE, and the tool never silently guesses.

10The bench harness, integrated

Rewritten section. The previous explainer described an earlier design (a seven-check verify CLI). The harness as now proposed is a practitioner bench tool built around the tranche — one bounded piece of work against a project-local context. It reads, narrows, checks, and summarizes. It never writes a governed authority file — its writes fall into three honest categories: read-only inspection (status, drift), generated-artifact output (briefs, reports, captured evidence — all labeled), and the separate write-path guard that only refuses. It never approves, never transitions state, and never becomes the project.

  • 1Adapters are data, not code. Each project carries a tiny human-authored manifest telling the harness where its plan, coordination file, status roots, decision register, and validation commands live — because even the two pilot projects encode the pattern differently (§8). A third project is configuration, not a new parser. Verified addenda: the manifest also declares an explicit .archive/ exclusion (app-dev's .archive/ holds a full duplicate DEL tree that would otherwise be double-counted and linted), disambiguates Dependencies.csv vs _DEPENDENCIES.md as the dependency register, and declares the per-root guard preconditions from §6.
  • 2Six commands, one worldview-free posture. status and drift read the project; next/brief narrow work to one tranche; run-validations executes the brief's declared commands itself and captures the outputs — evidence is generated by the tool, never attested by the agent; scope-check and evidence-check report against the brief. The brief is a cited projection of the sealed context and plan — the sources govern wherever they disagree, and it becomes an enforceable fence only as a committed, human-adopted record (D-GOV-04); BLOCK-capable checks never fire against an unadopted candidate. run-validations runs under a mutation contract (pre/post git status, declared commands only, BLOCK on governed-file mutation outside declared output paths). A green check is structural evidence, never approval.
  • 3Self-exclusion — two classes. Every output lives under a labeled generated path, states its sources and generation time, and is safe to delete. Narrative projections (status, drift, closeout reports) are never read back by any harness component, period. Evidence records captured by run-validations may be read as facts for the tranche that produced them — and never promote into lifecycle, approval, or plan state. This is what lets evidence-check function without rebuilding the drift loop of §9 one level up.
  • 4The practitioner stays the deciding instrument. The tool narrows the question — it does not answer questions of priority, sufficiency, interpretation, risk appetite, or acceptance. Those were never information-retrieval problems.
  • 5The shell write-path fix travels alongside, not inside. The write_status.sh precondition guard (§6) — the shell path's counterpart to the guard logic app-dev's TypeScript transition.ts path already enforces — ships in the same first PR but is independent of the read-only harness — keeping the "harness refuses nothing" claim exactly true.
The substrate question is closed — D-GOV-01 ruled 2026-07-01 Earlier plan generations flipped three times on whether operational governance state may live in a database with write authority (a SQLite control plane with a coordinator and leases was proposed, rejected, re-proposed, and re-cut). D-GOV-01 ended the loop — ruled by the owner 2026-07-01, SHA-bound at 82a35c545: git-tracked plain files are the sole authority for governance state; the harness writes no governed authority files; any governance/harness database is a rebuildable, gitignored projection (the catalog.sqlite pattern from §8); the only write-path interventions are precondition guards. The authority constraint is two-sided: no tool may author or approve governance state, and per K-GATE-1 (D-GOV-02) no tool may non-overridably BLOCK the human's CHECKING → ISSUED judgment either — authority is subtracted in both directions. The fork is closed; re-opening it requires superseding the record — not just writing a new plan.

★Glossary — terms you'll keep seeing

Working root — a folder where governed work happens (projects/* or domains/*). There are six.
Deliverable — one unit of work in its own folder (the DEL-* from §5).
Basis — the controlled set of inputs an agent may rely on; sealed into _CONTEXT.md.
Sealed / seal gate — a human freezing & approving the basis before bounded work may start.
Issued — the final state; a human has vouched for the work, bound to a git commit.
Snapshot — an immutable frozen copy (e.g. a run record); never edited after the fact.
K-* invariant — a numbered constitutional rule (e.g. K-AUTH-1 "only humans approve"). Practiced today; ratified record pending.
Approval SHA — the git commit hash an approval is tied to; if content changes, the approval is voided.
Drift — any restated-state surface no longer matching the authority: a stale banner, a mismatched history, a pinned hash that changed. §9's subject; the harness's baseline metric is 92/154.
Tranche — one bounded piece of work against a project-local context; the harness's core object.
Brief — a generated, source-cited projection of the sealed context plus a plan row for one tranche; carries a non-authority footer; sources govern on disagreement.
Adapter manifest — a tiny per-project file (_harness/adapter.yaml) telling the harness where that project keeps its plan, statuses, decisions, and validation commands.
run-validations — the harness command that executes an adopted brief's declared checks itself, under a mutation contract, and captures outputs; the top of the evidence provenance ladder (attestations never pass silently).
Caveat class — the honesty label on every parsed history: PARSED, PARSED_WITH_ASSUMPTIONS, or UNPARSEABLE. The tool never silently guesses.
Guard — a precondition check inside an existing write tool that refuses an objectively-broken transition (the write_status.sh patch). Refuses; never authors.
Rebuildable cache — the only sanctioned database pattern for governance state and harness projections: gitignored, regenerated from files by one command, safe to delete, never cited. Engine-owned domain stores are governed by K-DOMAIN-1, not this rule.
Self-exclusion — two classes: narrative reports are never read back by the harness; captured evidence records are readable as facts for their tranche and never promote into lifecycle, approval, or plan state.
D-GOV-01..07 — the seven rulings shipped with plan v3: substrate, severity & override, pilot scope, actor identity, minimal governance basis, profile current truth, domain SHA binding. Ruled 2026-07-01 by the owner, SHA-bound at 82a35c545, published under docs/governance_harness/_DECISIONS/.
Persona — an agent role with a defined lane and write scope (DOMAIN_ENGINE, WORKING_ITEMS, TOOLMAKER, CHANGE…).
Read-only inspection — the harness's first write-posture category: a deterministic check that inspects files and reports, leaving every governed file byte-identical. The other two categories are labeled generated-artifact output and the refusal-only guard.
Reconciliation — folding an approved result back into the shared basis so the project stays coherent.
