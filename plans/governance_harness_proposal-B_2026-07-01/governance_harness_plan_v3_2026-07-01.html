Design Principles (Merged)

Files are the reliance boundary

The harness reads authored files and git history. Its outputs are not authority unless a human separately adopts them into the governed record. Every generated file carries the standard header: generated view, not authority; sources cited; regenerate from project files; structural checks are not approval, issue, authentication, or acceptance of residual risk.

Status is multidimensional

No single green badge. Lifecycle state, evidence completeness, reference/hash resolution, approval-SHA status, staleness/drift, scope conformance, human-decision state, warrant state (UNWARRANTED→CITED→REVIEWED→AUTHENTICATED), and domain-profile status stay separate dimensions in every report. A deliverable can be structurally complete and unauthenticated; evidence can be present and insufficient.

Mechanical checks block; judgment surfaces

The harness may fail a command for objective defects within its declared observation boundary — out-of-scope tracked writes, missing required sources, malformed reports, missing disclaimers. It must never approve, issue, seal, authenticate, decide sufficiency, or accept risk. BLOCK never applies to the CHECKING→ISSUED judgment itself (K-GATE-1).

Historical record ≠ current truth

The corpus legitimately contains immutable history, current authority, stale prose, drafts, and generated summaries. The harness distinguishes them, labels parse confidence with caveat classes (PARSED / PARSED_WITH_ASSUMPTIONS / UNPARSEABLE), and surfaces current-truth conflicts rather than picking the newest or most convenient claim.

Self-exclusion — two classes

Narrative projections (status, drift, closeout reports) are never read back by any harness component as input, period. Evidence records produced by run-validations may be read as factual evidence for the tranche that produced them — and never promote into lifecycle state, approval state, plan state, or project status. This is what lets evidence-check function without rebuilding the drift loop one level up.

Scoped cache contract

For Chirality governance state and harness projections, the only permitted database pattern is a rebuildable, gitignored cache: regenerated from files by one command, safe to delete, never cited as authority. This rule does not reach developer tooling caches, and it explicitly does not reach engine-owned domain stores, which are sanctioned authoritative domain truth under K-DOMAIN-1 and the adopted profile.

The Evidence Problem This Plan Answers

The measured baseline: 92 of 154 _STATUS.md files disagree with their own last parsed history entry — app-dev is 0/53 clean; all 92 sit in piping and share one mechanical signature, a human-approved advance to CHECKING recorded in history while the frontmatter Current State line was never updated — and the repo's tier-0 control area contradicts itself about one fact across a summary file's top and bottom, an index banner and its own table, a YAML header comment and its field, and a filename. Every surface that restates state is a drift surface. Those contradictions become the adversarial fixtures for drift and self-check, and the fact itself goes to the owner as D-GOV-06 — the harness surfaces conflicts; it never resolves them.

Architecture

Five layers: human authority → authored files and git history → adapters → harness commands and generated views → bounded work and human review. Boring, local, inspectable.

Adapters: Governed Configuration Plus Versioned Parser Plugins

Each pilot root carries a small committed manifest (_harness/adapter.yaml) locating its plan, coordination file, status roots, decision register, DAG pointer, and validation commands, and selecting a parser dialect. The manifest also disambiguates the dependency register (Dependencies.csv and _DEPENDENCIES.md coexist as distinct files per deliverable) and declares the root's guard preconditions — piping's status schema carries no approval-SHA fields, so the SHA precondition applies only where a root declares it. Parsing behavior lives in versioned plugins. A new project requires configuration first and parser code only when it truly has a new dialect. Adapters emit sourced facts, never unsourced summaries: 

{
  "fact_id": "domain.open_pipe_stress.profile_status",
  "value": "ADOPTED",
  "source_path": "_DomainEngines/profiles/open_pipe_stress.DRAFT.yaml",
  "source_hint": "domain_profile.profile_status",
  "authority_status": "conflicted_current_truth",
  "parse_status": "PARSED",
  "caveat": "Header comment and filename say DRAFT while the field says ADOPTED. Ruling requested: D-GOV-06."
}

The harness degrades gracefully: a surface that is absent or unreadable is reported as such (NOT_APPLICABLE / UNPARSEABLE), never invented. Figures (53, 101, 92/154) were verified live against the repo on 2026-07-01; Phase 1 re-verifies them at execution time.

The run-validations Mutation-Control Contract

Validation commands can mutate the working tree (caches, lockfiles, formatter rewrites, regenerated snapshots). Without controls, run-validations is a backdoor write tool. The contract: 

1. record pre-run  `git status --porcelain`
2. run only commands declared in the HUMAN_ADOPTED brief (or adapter manifest)
3. capture stdout/stderr, exit code, duration, tool versions where cheap
4. record post-run `git status --porcelain`
5. classify changed paths: expected evidence output | ignored cache |
   unexpected tracked change | review-required
6. BLOCK if a validation command modified governed files outside the
   declared evidence/output paths

Prior Art: The TypeScript Transition Guard

write_status.sh is not the only status-write path. chirality-app-dev's frontend already implements the intended guard semantics: src/lib/lifecycle/transition.ts carries a from-to TRANSITION_RULES state machine with backward-transition blocking, per-transition authorized-actor enforcement (UNAUTHORIZED_ACTOR), and a mandatory git-SHA-shaped approvalSha for CHECKING/ISSUED (APPROVAL_SHA_REQUIRED / INVALID_APPROVAL_SHA), exposed through the status-transition API route and named by deliverable DEL-07-04. The first PR aligns the shell guard's preconditions with transition.ts or records why they diverge. Stated honestly: tool usage is guided operationally, not enforced — hand edits bypass any guard — so the guard hardens the sanctioned path only, and drift detection exists precisely because hand edits happen.

Claim Language

No harness output may say approved, issued, professionally accepted, certified, sealed, safe, ready for construction, or closed — unless it is quoting a human-authored governed artifact and labels the quote as such. It says narrower things: the validation artifact is present; the approval SHA is missing/TBD-pending-publish/reachable/unreachable; the diff is inside/outside the adopted fence; the source hash matches or does not; two current-truth sources conflict; human review required.

Tranche Model & Adoption

The core object is the tranche: one bounded intervention against project-local context, small enough for scope containment and evidence review. The brief is its projection — and enforcement authority comes only from adoption.

The brief is a projection

Every brief field cites the source it was derived from (_CONTEXT.md section, plan or queue row, decision register entry, adapter manifest field); the brief is regenerable from those sources; a non-authority footer states that the sources govern on disagreement. The brief narrows attention. It never replaces the sealed basis.

Adoption makes the fence

Lifecycle: CANDIDATE → HUMAN_ADOPTED → EXECUTED → CHECKED → HUMAN_REVIEWED → CLOSED / SUPERSEDED. Adoption follows the D-GOV-04 identity rule and the adopted brief is committed to the governed record — otherwise the adoption does not exist for reliance. BLOCK-capable checks run only against adopted briefs; against candidates, findings cap at REVIEW. This lifecycle is metadata on harness artifacts; it adds no state to the deliverable lifecycle.

Domain Engines In MVP — Read And Report Only

The _DomainEngines/ control area is in MVP scope because its contradictions are the plan's own drift evidence. The domains/* shape verifier stays deferred.

The harness may

Read the index, latest pointer, published rulings, decision stubs, profiles, and validation reports; report profile status, integration level, protected/proposal paths, and contradictions; check that any OperationProposal artifacts sit in allowed proposal paths; check that protected domain truth was not touched by an unauthorized diff.

The harness must not

Apply domain operations; mutate protected engine truth; advance DRAFT → VALIDATED → ADOPTED; equate validation with professional correctness; claim code compliance, certification, sealing, or construction readiness. Validation-passed is necessary, never sufficient (K-DOMAIN-4).
