1. Decision and owner rulings

Proceed toward v3.0.0-rc.1, but do not begin the held implementation merely because this document is merged. First convert the accepted direction into the App and Root instruments that own it. The release candidate includes Codex-native delegation. Preparation builds remain unsigned or ad hoc. Only the exact artifact selected for actual public release is Developer ID signed, notarized, stapled, and accepted.

Codex owns its inner harness

Codex may create, steer, wait for, interrupt, and synthesize its native descendants according to the capabilities of the pinned upstream runtime. Chirality does not impose a child allowlist, fixed topology, or its own concurrency cap.

Chirality owns the outer authority boundary

Every primary and descendant thread remains inside the same project root, filesystem/network posture, approval system, consent state, protected-path policy, process lifetime, and privacy boundary. This is enforced and empirically tested, not entrusted to prompt text.

AGENTS.md supplies semantic posture

Agent 0 may supervise and delegate, Agent 1 may manage and delegate bounded work, and Agent 2 does not create another orchestration layer. These are instruction-governed workflow semantics. They do not substitute for the hard authority boundary.

Notarization belongs to release

CI and preparation do not notarize. When the owner decides that an RC will actually be distributed, the frozen candidate enters the owner-operated signing/notarization lane. No rebuild is allowed between final source acceptance and release signing.

1.1 Binding intent versus present authority

This document records the owner’s intended direction and the proposed execution path. It is a derivative planning artifact, not an amendment to CONTRACT.md, an implementation grant, a cutover act, a release act, or a substitute for an accepted snapshot. Conflicting live contracts remain binding until their owning workflows amend and accept them.

1.2 Release/notarization rule

Preparation: local and CI artifacts are unsigned or ad hoc and are labelled non-distributable. Actual release: if v3.0.0-rc.1 is published for users to download, that publication is a release. The exact frozen artifact must then be signed, notarized, stapled, Gatekeeper-tested, checksummed, published, downloaded again, and reverified.

3. Release definition and scope

3.1 What “stable product candidate” means

v3.0.0-rc.1 is not a completed app. It is the first publicly distributable candidate whose product core is coherent and supportable enough for real use while development continues. Stability is defined by bounded behavior, durable failure states, data integrity, and an honest capability surface—not by feature completeness.

3.2 Success criteria

  1. A new user can install the released DMG, pass Gatekeeper, start Chirality, choose Codex (Preview), sign in with ChatGPT, grant project consent, and complete a turn.
  2. Codex can delegate natively when it judges delegation useful; the UI shows attributable descendant activity and correctly routes concurrent descendant approvals.
  3. No primary or descendant thread can read, write, execute, reach the network, persist secrets, or outlive the session beyond the effective approved boundary.
  4. Interrupt, quit, crash, logout, daemon restart, and upgrade do not leave an orphan App Server, stale socket, corrupted project state, or misleading “success” terminal.
  5. The exact public bytes trace to an accepted source identity and release identity, include notices and an SBOM, and pass signing, notarization, stapling, clean-machine, checksum, and download-backcheck evidence.

4.2 Process shape

  1. The Chirality daemon requests a delegated-harness instance from a dedicated helper through a narrow local control protocol.
  2. The helper owns exactly one App Server process for the user/app identity, creates its process group, connects newline-delimited App Server stdio, and exposes a mandatory close().
  3. The helper receives the minimum allowlisted environment; it does not inherit the Electron process environment wholesale.
  4. On quit, logout, crash recovery, or upgrade, the helper drains, interrupts active work, terminates the process group by deadline, and verifies that no child or socket remains.
  5. Finder activation of a second GUI attaches to the existing daemon/helper path; it never creates a second App Server.

5. Delegation and authority

5.1 Two delegation classes

chirality-managedA governed child session created by Chirality’s managed delegation mechanism.Existing sealed brief, declared context/tools/writes, parentage, return, and Agent 0→1→2 rules continue unchanged.

5.2 Native delegation rule

Configuration intent: native multi-agent capability is enabled; agents.max_concurrent_threads_per_session is left unset so Codex selects its supported default; Chirality does not register a child-type allowlist or model/reasoning exclusion merely to control topology. Upstream/account/platform limits remain effective and must be displayed honestly.

“Without Chirality restrictions” applies to the inner topology—not to external authority. A descendant cannot receive a broader filesystem root, network allowance, approval grant, consent scope, process lifetime, or protected-path access than its parent session. A custom Codex agent may narrow its posture; it may not expand the enforced ceiling.

5.3 Agent 0/1/2 semantics

  • Untyped, Agent 0, and Agent 1 sessions: may use native Codex delegation when their effective instruction stack permits it.
  • Agent 2/TASK sessions: execute one bounded objective and do not create another orchestration layer.
  • Equivalent evidence: when AGENTS.md requires sealed briefs, scopes, parentage, and returns, the delegated-harness adapter must preserve equivalent observable evidence to the extent exposed by the exact pin. Where an upstream descendant cannot be represented faithfully, it remains upstream-native evidence and is not promoted into a governed Chirality child record.
  • Conformance consequence: violation of semantic posture makes the workflow evidence non-conforming. Hard containment must still hold even if the model violates an instruction.

5.4 Thread-aware approval contract

The current broker’s (sessionId, toolUseId) key is insufficient. The revised correlation key is:

ApprovalKey = {
  sessionId,
  threadId,
  turnId,
  requestId | itemId,
  requestKind
}

The UI must show the requesting primary/descendant thread and action. Concurrent requests may not overwrite or answer each other. Session-scoped approval is granted only when the upstream request offers it and the user chooses it; it remains bounded to the same session authority. Unattributed requests fail closed.

5.5 Upstream evidence used by this plan

Current official documentation says subagents inherit the active sandbox and permission mode, and that live runtime overrides are reapplied on spawn. It also documents collabToolCall items with sender/receiver/new thread IDs, experimental parent/ancestor thread filters, and approval requests containing threadId and turnId. These surfaces make the design testable, but their exact pinned behavior—not prose alone—is the acceptance basis.

6. Process, containment, and failure behavior

6.1 Required layers

  1. Declared policy: one effective runtime profile names sandbox mode, approval policy, writable roots, network posture, protected paths, and relevant feature flags.
  2. Enforcement: the exact packaged App Server must demonstrably enforce the policy for both primary and descendant actions. The macOS mechanism is selected after the App Sandbox × Seatbelt compatibility spike; this plan does not prejudge whether that is upstream Seatbelt alone, a compatible enclosing profile, or another OS boundary.
  3. Positive sentinel: every new thread performs safe canary checks that must be denied outside the declared root and on protected material. A policy that parses but does not enforce is a failure.
  4. Approval boundary: escalation requests surface through the thread-aware broker. No missing UI, disconnected client, or ambiguous request becomes implicit approval.
  5. Process boundary: the helper owns, drains, kills, and scans the process tree. A successful turn cannot hide an orphan.

6.2 Workspace-write enablement

Native delegation remains enabled in all outcomes, but workspace-write is conditional on containment proof. If the exact packaged candidate cannot pass G-SBX, G-SENT, G-APPR, G-ENV, and protected-path tests, the candidate may only expose a read-only Codex Preview if the owner explicitly accepts that reduced capability at G0/G4; otherwise RC publication is blocked. The failure does not justify silently disabling native delegation or silently granting broader access.

6.3 Environment posture

  • Construct the helper/App Server environment from an allowlist; do not clone process.env.
  • Exclude development bypasses, zero-timeout overrides, unrelated API keys, proxy variables, shell startup mutations, and the user’s ambient CODEX_HOME.
  • Use an app-specific CODEX_HOME with documented ownership, permissions, backup, deletion, and upgrade behavior.
  • Treat unavailable keyring access, invalid config, unsupported feature state, or sandbox refusal as typed unavailable; never fall back to plaintext credentials or an uncontained process.

6.4 Terminal and shutdown invariants

  • Exactly one top-level durable terminal per Chirality turn: completed, failed, or interrupted.
  • Descendant activity may finish later internally only if the top-level contract permits it; RC defaults to interrupt-and-drain all descendants before terminal publication.
  • App Server EOF, malformed protocol, crash, or helper loss yields a typed failure and invalidates the instance.
  • Shutdown has measured grace and force deadlines; after force termination, an orphan/socket scan must be clean before a new instance starts.

7. Authentication, data, and privacy

7.1 ChatGPT login for Codex

  1. Before thread/start, explain that selected project context may be sent to OpenAI and record consent in the chosen non-secret store.
  2. Call account/read to display non-secret state.
  3. Default RC flow: account/login/start with type: "chatgptDeviceCode".
  4. Render the verification URL and user code, support cancel, and wait for account/login/completed plus account/updated.
  5. Browser callback login (type: "chatgpt") may be added only as a declared localhost exception with loopback bind, ephemeral port, bounded lifetime, no token logging, and a specific K-NET-1 disposition.
  6. Logout calls account/logout, ends active Codex sessions, clears visible account state, and verifies the adapter-private credential state is no longer usable.

7.2 Credential boundary

Renderer code, project truth, Chirality event logs, support bundles, and ordinary application logs never contain API keys, access/refresh tokens, auth URLs with sensitive parameters, device codes, cookies, or Keychain payloads. The shared account contract exposes state such as signedOut, signingIn, signedIn, expired, and unavailable, not token material.

7.3 Typed event projection

Raw Record<string, unknown> payloads may not flow from App Server to SSE or events.jsonl. The adapter validates each upstream item against generated exact-pin types, converts it into a provider-neutral event union, drops unknown fields by default, and applies structural secret redaction before any renderer or durable sink. Unknown event types are retained only as a bounded, redacted diagnostic code—not raw payload.

7.4 Consent store decision

G1 must choose whether hosted-engine consent is project truth (and therefore participates in re-registration and review) or user-local application state. The selection must be made before thread construction because App Server can read the working directory, AGENTS.md, project .codex configuration, and git metadata at thread/start.

7.5 Claude posture

Claude remains API-key authenticated in RC. Chirality does not advertise, design around, or promise Claude subscription login. Such a capability may enter a future plan only after written Anthropic approval for this third-party product and a new contract/security review. Product copy must follow Anthropic branding requirements.

11.1 Evidence rules

  • Fake-server evidence proves client determinism; it does not substitute for exact-pin or packaged evidence.
  • Live owner-authenticated evidence never records secrets and is not required in ordinary CI.
  • Unsigned/ad-hoc package proof supports G5 only; it does not support G6b, G7, or G8.
  • Notarized evidence applies only to the exact bytes tested. Rebuild, repackage, re-sign, dependency drift, or source change invalidates it.
  • Upstream documentation is a design input. Generated exact-pin schemas and empirical packaged behavior are the executable evidence.

12. Packaging, signing, notarization, and publication

12.1 Preparation lane

  1. Pin and inventory App Server as an extra resource; preserve its nested code identity during ordinary packaging.
  2. Build local/CI arm64 DMGs without production signing/notarization credentials.
  3. Generate checksums, dependency inventory, notices, chosen SBOM format, minimum macOS declaration, and a release manifest.
  4. Run package-level tests and label the result preparation / not for distribution.
  5. Repeat freely during development. None of these builds consumes the owner’s notarization time or claims public-release integrity.

12.2 Actual release lane

  1. Owner release act: select the exact accepted candidate for publication and record source/release identity.
  2. Verify Apple Developer enrollment, Developer ID Application identity, bundle IDs, hardened runtime, entitlements, nested signing order, and local credential custody.
  3. Build once from the frozen source/lock/supply/config identity, or promote the already frozen candidate through a byte-preserving signing procedure. Do not rebuild after final acceptance without restarting the gate.
  4. Sign nested helpers/binaries, then app, then DMG in the proven order.
  5. Submit the exact artifact to Apple’s notary service; staple the accepted ticket.
  6. Verify codesign, spctl, staple, checksums, SBOM/notices, clean-machine install, launch, login, turn, delegation, interrupt, and quit.
  7. Publish as a GitHub prerelease; download through the user-visible path and repeat identity/Gatekeeper/smoke checks.

Credential custody: no Apple signing certificate, App Store Connect key, Apple ID password, or notary credential is placed in GitHub Actions under this plan. The existing unsigned CI posture remains intact. Any future hosted-signing design requires its own explicit owner decision and threat/custody review.

12.3 Publication contents

  • Chirality-3.0.0-rc.1-arm64.dmg (signed, notarized, stapled).
  • SHA-256 checksum and release manifest binding source, lock, App Server, schema, config, notices, SBOM, signature/notary and test snapshot identities.
  • Third-party notices and SBOM (format selected at G1; recommendation: CycloneDX JSON plus human-readable notices).
  • Release notes identifying Codex as Preview, ChatGPT login behavior, data transmission/consent, supported macOS/architecture, known limitations, support route, and rollback instructions.

12.4 Rollback

Withdraw the affected asset and mark the prerelease accordingly; never replace bytes under the same version/tag. Preserve the evidence and incident reason. If safe, point users to the last accepted release and document data compatibility. A fixed candidate receives a new version and repeats the full release lane.
