## Publication subject and basis

Propose a named **Chirality library source edition**, delivered from one exact
Git revision through the existing repository release/archive route, with concise
publication notes. Include the complete tracked source, required resources and
notices; retain historical and Root-only holdings with their existing standing.
Do not describe this as an installed agent product, a new manual edition, or
qualification of every historical tool. No new packaging system is needed.
The owner selects the library version name and authorizes publication under
[PRD R15 and A7](../../docs/PRD.md). A manual's “Consolidated v9” edition name is
not a library version.

## Remaining work, in order

1. **Prepare one publication proposal — Agent 0.** The [publication notes](../PKG-05/DEL-05-01/Work/PublicationNotes.md) now provide the reviewable draft; their content and proposed `library-v1.0.0` label await owner approval. Draft the
   release description under DEL-05-01 Work, using the current source as its
   comparison basis. Explain the library's purpose, obtaining/entry path,
   consequential changes since the preceding development basis, dependencies,
   limitations and recovery. Cover current setup/tool repairs, F-02, retirement,
   reflection and consumer-use guidance; cite existing PRs instead of copying
   their histories. Propose a distinct library version label for the owner to
   choose. Done when the actual proposed notes and affected source edits are
   available together for content review. No release is created by drafting.
2. **Resolve content findings and identify the delivery revision — Agent 0,
   with owner content approval before integration.** Preserve the seven scopes'
   commitments. Update only affected current descriptions and links. Integrate
   approved content under normal exact-head checks, then bind the intended
   publication source. Done when the source, comparison and remaining claims are
   unambiguous; historical candidate identities remain unchanged.
3. **Check the actual delivery form — Agent 0, after step 2.** Build the selected
   source archive, check its revision, bytes/modes, required resources and notices,
   and compute its checksum. Check recipient entry/release links and reuse the
   extracted-source evidence where unchanged sources justify it. Run required
   credential/private-term checks on the actual public changes/artifact, retaining
   the distinction between locally available terms and hosted secret-set coverage.
   Recheck any altered behavior or dependency; otherwise do not repeat suites.
   Done when artifact identity, usable instructions, evidence applicability and
   any remaining findings can be presented for the named publication subject.
4. **Present acceptance and release choices together — Agent 0 prepares;
   owner decides.** Present coverage of the seven contributions/A1–A8, exact
   source/artifact, version, notes, limitations and continuing responsibilities.
   Ask separately whether the agreed product is accepted and whether this named
   edition may be published for the proposed audience. Gate approval and prior
   source-candidate approval supply neither decision. Any unresolved finding
   needs an explicit consequence and disposition, not a passing test count.
5. **Publish the authorized edition and verify access — Agent 0 only within
   the owner's release authorization.** Use the existing repository release
   mechanism at the approved source, retain checksum/source/notices and notes,
   and verify that the advertised download identifies and supplies that result.
   Update a moving discovery pointer only to the actual published edition.
   Consumers choose adoption independently. Retain scratch needed for delivery
   or recovery; clean it once those needs end. Done when the owner-authorized
   edition is obtainable through its stated route.

Steps 1–3 are preparation; the owner decisions in step 4 control step 5. They may
be presented as one coherent publication undertaking rather than seven new PRs.
The public notes belong with DEL-05-01's output; this coordination document owns
only the route and remaining actions. Update it when decisions change that route;
Git retains its history.
