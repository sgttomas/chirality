## Frame kernel and linear algebra

**Element formulation** (`core/solver/frame_kernel/src/lib.rs`): two-node 3D Euler–Bernoulli frame, 6 DOF/node in fixed order `[ux, uy, uz, rx, ry, rz]` (node i = local 0..6, node j = 6..12; `element_dof_map`, lines 79–87). `local_stiffness` (lines 686–731) builds the textbook 12×12 by superposing four uncoupled blocks: axial `EA/L`, torsion `GJ/L`, and the two 4×4 bending blocks with coefficients `12EI/L³, 6EI/L², 4EI/L, 2EI/L` — bending-about-z couples `{uy, rz}` (lines 957–970) and bending-about-y couples `{uz, ry}` with the sign flip on the 6EI/L² terms (lines 972–985). No shear deformation (no Timoshenko φ term anywhere).

**Transforms**: `FrameOrientation` stores rows = local unit axes in global coordinates, constructor-validated for unit length, mutual orthogonality, and right-handedness at `AXIS_TOLERANCE = 1e-12` (lines 480–506). `from_x_axis_and_y_reference` Gram-Schmidts a y-reference against the member axis (508–522). The 12×12 transform is four copies of the 3×3 rotation on translation and rotation blocks (524–534); global stiffness is `TᵀKT` via `multiply_transpose_left` (733–739, 1040–1059).

**Assembly and BC reduction**: dense scatter-add over the DOF map (748–783, includes `UserStiffnessElement` relative-DOF macro-elements at 1000–1022 — the expansion-joint precedent the curved bend reuses). `reduce_system_for_boundary` (815–871) deletes constrained rows/cols and applies the prescribed-displacement force correction `f_free -= K[free][bc] · d_bc` (lines 853–860); duplicate/out-of-range boundary DOFs are hard errors.

**Dense solve**: Gaussian elimination with partial pivoting, zero-pivot guard `1e-12` explicitly documented as *not* tolerance policy (lines 20–21, 895–955). The README (lines 28, 46–48) states the dense path is interim, is the **parity oracle for the sparse path**, and the intended replacement boundary is exactly the reduced-system solve interface.

**sparse_direct** (`core/solver/sparse_direct/`): per DEC-023 (D-03 Option C, `execution/_Decomposition/SOFTWARE_DECOMP.md` §12 line 609) — a hand-rolled in-repo **skyline (profile) LDLᵀ** with **reverse Cuthill–McKee ordering**. The README states the "why" directly: RCM is the classic bandwidth/profile reducer for the *banded/branched frame topologies* piping models produce, and it admits a fully deterministic formulation — symmetrized/sorted/deduped adjacency, components by lowest original index, pseudo-peripheral start, all ties broken by ascending `(degree, original index)` (README lines 14–28; `reverse_cuthill_mckee` at src line 496). The factorization (`factorize_ldlt`, line 377) uses **no pivot reordering** and a fixed single-threaded operation order (rows ascending, inner sums ascending), preserving byte-reproducibility, asserted bitwise in tests (README lines 30–32). LDLᵀ rather than Cholesky matters here [investigator characterization: it avoids square roots so indefiniteness is observable rather than fatal] — the README's record content is that nonpositive pivots are counted and located, never silently absorbed, and `pivot_condition_ratio_estimate = max|d|/min|d|` is an explicitly labeled *proxy*, with thresholds reserved to D-04/DEC-026 (README lines 34–39). Only the lower triangle `dense[max][min]` is read, making the caller responsible for symmetry and shielding against last-ulp transform asymmetry (lines 41–43). Parity: sparse-vs-dense parity tests against `frame_kernel::solve_dense` on invented chain/grid/banded models at the DEC-026 analytic-class relative seed **1.0e-9** (README line 55; `assert_dense_parity`, src line 883). Zero external dependencies; frame_kernel is a dev-dependency only. Live-path adoption is still a separate tranche (README lines 57–59), but the assembled nonlinear loop already defaults to sparse-interactive under DEC-053, dense retained as "scrutiny" mode (`nonlinear_integration/README.md`).

## Curved-bend element (the interesting one)

`core/solver/curved_bend/src/lib.rs`, the P1 sub-tranche of **DEC-070** (D-34 Option O-B: dedicated arc-consistent macro-element, chosen over O-A k-scaled chords; SOFTWARE_DECOMP §12 line 656).

**Construction** (flexibility → stiffness):
1. **Geometry** from end nodes + arc center: radii must match to relative 1e-9, included angle φ strictly in (0, π); bend plane from `(i−center)×(j−center)`; local frame x = radial at node i, z = plane normal, node i at arc angle 0 (lines 149–178).
2. **Energy terms**: with node i clamped, the 6×6 end flexibility at node j is the unit-load (Castigliano) integral over θ ∈ [0, φ] of four strain-energy products: in-plane bending `k_in·Mip_a·Mip_b/EI`, out-of-plane bending `k_out·Mop_a·Mop_b/EI`, torsion `T_a·T_b/GJ`, axial `N_a·N_b/EA`, all × R dθ (README lines 26–31; `end_flexibility` lines 205–238). Shear energy excluded, consistent with the kernel.
3. **Closed-form arc integrals**: every internal action of the six unit tip loads is a linear combination of `{1, cosθ, sinθ}` (`unit_load_actions`, lines 670–719 — e.g. unit z-force gives Mop = R·sin(φ−θ), T = R·(1−cos(φ−θ)), which is where out-of-plane bending–torsion coupling lives). So every F entry is a quadratic form `leftᵀ·G·right` over the exact 3×3 trig Gram matrix (`trig_gram`, lines 901–918: entries φ, sinφ, 1−cosφ, φ/2±sin2φ/4, sin²φ/2). **No numerical quadrature anywhere.**
4. **User factors**: `k_in` scales only the in-plane bending energy term, `k_out` only the out-of-plane bending-curvature term; torsion/axial untouched; the geometric out-of-plane/torsion coupling is carried by the integrals themselves (README lines 43–47). Factors = 1 reproduce the plain Euler–Bernoulli curved beam. Factors are validated finite-positive opaque numbers — no k/SIF formula, catalog, or default ships (the crate's non-compliance fence).
5. **Stiffness assembly**: `K_jj = F⁻¹` (columnwise dense partial-pivot solve then symmetrization, `invert_symmetric6` lines 932–953), then the rigid equilibrium transfer `H = [[I,0],[skew(chord),I]]` gives `K = [[H K_jj Hᵀ, −H K_jj],[−K_jj Hᵀ, K_jj]]` in the bend-plane frame (lines 957–986), rotated to global with the kernel transform.

**How it "softens bends"**: increasing k_in/k_out scales the bending flexibility integrals affinely, so K_jj = F⁻¹ drops, and the macro-element scatter-adds into the global matrix beside frame elements (in the nonlinear loop via `add_curved_bend_stiffness_contributions`, `nonlinear_integration/src/lib.rs` lines 613–629) — the solve is flexibility-correct rather than a post-hoc stress multiplier (the DEC-066 supersession of the DEC-045 multiplier-only realization).

The crate also carries consistent load vectors derived on the same energy basis: uniform distributed load (extended `{1,cos,sin,θ,θcos,θsin}` basis, `trig_extended_gram` lines 826–868), the exactly self-equilibrated radial pressure-thrust wall load (lines 489–555 — notable: statics-only nodal lumping of the complete cap+wall system cancels to zero, so only the work-equivalent vector carries the deformation effect), and closed-form section resultants at arc stations.

**Stated limits**: single `second_moment` about both bending axes; φ ∈ (0, π) open interval; no shear deformation; center-parameterized geometry rejects degenerate/collinear input rather than guessing; straight-limit convergence to the chord element is first-order in φ (documented 1e-3 relative at φ = 1e-3); formulation-only crate — no product-physics integration, schema, or recovery path in this slice (README lines 3–7, 63–87).

## Nonlinear active set as ruled

Ruled semantics: **DEC-067** (D-35 ruling, `execution/_Coordination/_DECISIONS/D-35_RULING_2026-07-09.md`; codified SOFTWARE_DECOMP §12 line 653), building on DEC-044 (D-16, loop ownership) and DEC-046 (D-19, class-tiered convergence-tolerance policy keyed by support class: gap/one-way/lift-off/friction, tighten-only). DEC-066/070 cover bend flexibility (above); DEC-068/069 are adjacent (workflow physics; PRD non-goals); DEC-077 is temperature interpolation of E and α — peripheral to the active set.

**States** (`nonlinear_supports/src/lib.rs`): `Active | Inactive | Sticking | Sliding` for behaviors `OneWay{active_when}`, `Gap{closes_when}` (explicit clearance required, missing gap = blocking model error), `LiftOff{contact_when}`, `Friction`.

**Switching rules — the state-switched complementarity test** (`classify_support_state`, lines 551–635, doc comment 540–550):
- *Engaged* unilateral support (prior = Active, incl. closed gap): classify on **trial reaction sign** — contact persists only while the reaction bears in the supplyable sense; a pulling reaction ⇒ lift-off.
- *Released* support (prior = Inactive or unseeded): classify on **trial displacement penetration** into the bearing side (`state_from_penetration`, 695–705), or on reaching the explicit clearance for gaps (closes when `d ≥ gap` / `d ≤ −gap`, lines 587–595).
- This pairing is exactly D-35 item 1 — replacing the reaction-only/displacement-only tests so re-engagement and lift-off are both observable and the converged state doesn't depend on the seeded state.
- *Friction*: normal ≤ 0 ⇒ Inactive (contact loss); else `|tangential| ≤ μ·|N|` ⇒ Sticking, else Sliding (lines 604–634).

**Sliding force** (D-35 item 2; `nonlinear_integration/src/lib.rs`): a support classified Sliding gets a bounded tangential force `−sign(motion)·μ·|N|` added to the iteration load vector (lines 404–414, 651–704), replacing the previous full-DOF release. N comes from **current-iterate evidence** (explicit input or a caller-named derived-normal DOF), direction from the prior iterate: `signum(prev displacement)`, else `−signum(prev reaction)` (impending motion), else 0 ⇒ no force (lines 710–718). The force is reported back into the support's tangential reaction so it doesn't vanish into the load vector (lines 417–424).

**Convergence acceptance**: the governed residual is the **active-set state-change count** (`residual_norm = changed_supports.len()`, `nonlinear_supports` line 479); converged when `residual ≤ tolerance` AND not blocked AND not sliding-deferred (`nonlinear_integration` line 442). Iteration cap and tolerances are caller-supplied under the DEC-046 governed policy (no defaults). Every non-converged exit must carry a visible `NonConvergence` diagnostic — including the zero-residual capped exit (guard at lines 469–488, closing corner TP-PMM-P2-NONCONVDIAG-001).

**Anti-chatter measures** (all present in code):
1. *Sliding persistence*: a friction support previously Sliding that classifies Sticking with nonzero trial displacement stays Sliding (`classify_iteration_support_state`, lines 524–538; assumption text at `nonlinear_integration` line 511).
2. *Seeded-sliding deferral*: a Sliding seed with no solved iterate defers convergence one iteration so the bound is applied before the loop can converge — seed-independence by construction (lines 397–403, 442).
3. *Zero-direction suppression*: no deterministic direction evidence ⇒ no force applied that iteration (line 678).

## The friction path-history problem, stated precisely

**Record content.** The open item is `_STATUS.md` Remaining line 8 (`execution/PKG-04_.../DEL-04-04_.../_STATUS.md`): "Resolve sliding-direction dependence on the prior iterate (anti-chatter / friction path-history follow-on) (gated: new D-XX ruling per mechanics plan §4)". The mechanics plan (`plans/PLAN_2026-07-09_physical_model_mechanics.md` §4) names "friction path-history" as a follow-on trigger *each requiring a new D-XX*; DEC-067's disposition says "no path/load-step friction history model is adopted (future D-XX if sought)".

**What the implementation does**: within a single quasi-static solve of one load vector, the sliding force applied at iteration n is `−sign(d_{n−1} or −r_{n−1})·μ·|N_{n−1 evidence}|` — direction and magnitude are functions of the *previous linearized iterate*, not of any physical load path (`sliding_direction`, `nonlinear_integration` lines 706–718; limitation text line 524: "a single-iterate Coulomb bound, not a path-dependent or load-step friction history model; its magnitude is not itself a convergence residual axis").

**Why it is path-dependent in a quasi-static solve**: the iteration sequence — the free first solve, the seeded states, and each intermediate active set — plays the role that physical loading history plays in a real Coulomb system. The converged fixed point can therefore depend on the iteration trajectory (which is itself seed- and ordering-determined), even though the load case is a single static vector. [Investigator characterization of the mechanism; the record itself states the dependence and gates it, without this elaboration.]

**Documented failure modes** (all record content):
- *Directional chatter to the cap*: "sliding direction comes from the prior iterate only, so a sliding support whose bound exceeds the actual drive can oscillate direction and reach the visible nonconvergence cap instead of re-sticking; this fails loudly (diagnostic), never silently" (FRICTION-001 run record, §Boundaries And Residuals; same wording in DEL-04-04 `MEMORY.md`, "Residuals").
- *The zero-residual capped corner*: sliding seed at `max_iterations == 1` returns `converged=false` with zero residual; originally silent, closed by the NONCONVDIAG-001 diagnostic guard.
- The DEC-067 seed-independence guarantee holds for the *unilateral* classifiers; the friction slide direction is the one place the prior iterate remains load-bearing — hence the persistence rule (which suppresses Sliding→Sticking, i.e. resolves the tie deterministically rather than physically).

**Candidate formulations**: **NOT FOUND in the records.** DEC-067, the run record, MEMORY.md, _STATUS.md, and the mechanics plan gate the topic on a future D-XX but name no candidate scheme. *Investigator characterization only — not record content*: the structure of the code admits the standard menu: (a) incremental load stepping so iterate history approximates physical load path (a "load-step friction history model" is the phrase the records use for what was *not* adopted, suggesting this is the anticipated shape); (b) return-mapping/radial-return-style regularization — treat the tangential DOF elastically-stick with a penalty stiffness and project onto the Coulomb disk, making direction emerge from the trial state rather than the prior iterate; (c) direction freezing per step with a stick/slip complementarity check only at step boundaries; (d) velocity/increment-based direction (sign of Δd between iterates rather than total d), which would decouple direction from the absolute prior displacement. All four would require the ruled D-XX because each introduces either history state or a new tolerance axis.

## The three questions a numerics reviewer would ask next

1. **Friction fixed-point well-posedness**: the convergence criterion is a state-change count, not a force/energy residual — two active sets can both be self-consistent fixed points of the iteration map (particularly with the sliding-persistence rule suppressing re-sticking while d ≠ 0). What is the uniqueness argument, or the disclosure, for multi-friction-support models where the reached fixed point depends on seeding and iteration order? (The records acknowledge the single-support chatter mode; the multi-support interaction is unexamined in what I read.)
2. **Conditioning of the flexibility inversion for stiff bends**: `invert_symmetric6` inverts F through the dense solver with only the generic 1e-12 pivot guard. For small φ with k = 1, F approaches the rank-deficient-looking flexibility of a nearly straight, nearly rigid short arc (the README's own straight-limit test needs a loosened 1e-3 tolerance at φ = 1e-3). What is the condition growth of F⁻¹ vs φ and section stiffness, and should the macro-element carry its own conditioning report the way `sparse_direct` does?
3. **Sparse path under active-set restraint churn**: each nonlinear iteration re-reduces the system as the active set toggles restrained DOFs, changing the reduced pattern — is the RCM ordering/profile recomputed per iteration (cost and, more importantly, byte-reproducibility of the *sequence*), and is the dense-vs-sparse parity oracle exercised on the *iterated* nonlinear path or only on single linear solves? The parity tests I found (`sparse_direct/src/lib.rs` line 883 ff.) are single-solve; DEC-053 made sparse the default interactive path for the nonlinear loop.
