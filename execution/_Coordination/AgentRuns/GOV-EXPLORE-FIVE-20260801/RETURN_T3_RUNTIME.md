# T3 terminal return — runtime local-model architecture (verbatim)

## Daemon architecture as built

**Package layout.** `runtime/packages/` holds seven packages: `contracts` (types, protocol, engine port, residency contract, harness event schema), `core` (all orchestration logic: `runtime-service.ts`, `session-store.ts`, `turn-coordinator.ts`, `residency-coordinator.ts`, `agent1-run-coordinator.ts`, `auth-registry.ts`, `project-registry.ts`, `engine-registry.ts`), `daemon` (HTTP server only), `client` (Node HTTP-over-UDS client, `runtime/packages/client/src/client.ts` — `httpRequest({ socketPath })`), `cli` (`project register|list|status`, `models list|activate`, `agent1 run`, plus a macOS launchd installer `runtime/packages/cli/src/launch-agent.ts`, label `com.chirality.runtime`, default `KeepAlive` crash-only), and two engine packages (`engine-claude`, `engine-pi-omlx`).

**Transport and auth (K-CONTROL-1).** `runtime/packages/daemon/src/runtime-daemon.ts` listens exclusively on a Unix socket (`server.listen(this.options.socketPath)`, then `chmod 0o600`; `ensurePrivateDirectory` gives 0700 dirs). There is no TCP path in the package. Every route calls `authorize()` → `AuthRegistry.authenticate` (`runtime/packages/core/src/auth-registry.ts`): `Bearer` token, SHA-256 hash compared with `timingSafeEqual`, per-client scope list (`runtime:read`, `sessions:write`, `models:write`, …), and project-scoped tokens — a client with a `projectId` can only touch its own project (403 otherwise). Registration (`RuntimeService.registerProject`) revokes all prior tokens for the project before issuing a new one (tested at `runtime/tests/daemon.test.ts:156`). Stale-socket recovery is fail-closed: an `.owner.json` record (`chirality.daemon-owner/v1`, mode-checked, uid-checked) is required, and the old daemon is replaced only when its PID is *demonstrably* absent (`ESRCH`); live-or-ambiguous → 409, non-socket path or another user's socket → refusal (`recoverStaleSocket`, tested `daemon.test.ts:357`).

**Session store (K-STORE-2).** `runtime/packages/core/src/session-store.ts`: central records are `session.json` (`chirality.session/v2`) + `events.jsonl` per session under `{runtimeDir}/projects/<projectId>/sessions/<sessionId>/`. Legacy project-local sessions are imported lazily and non-destructively — `migrateLegacy` copies into a temp dir and `rename`s, never touching the source (test: "lazily copies a legacy record without modifying the source", `runtime/tests/session-and-residency.test.ts:38`); deletion uses tombstone markers so a deleted legacy session doesn't resurrect. Legacy roots are containment- and symlink-checked against the project root.

**Project registration.** `runtime/packages/core/src/project-registry.ts`: registers a tracked `chirality.project.json`, stores the manifest SHA-256; any byte drift flips `adaptersEnabled=false` and `requireAuthorized` throws `PROJECT_MANIFEST_DRIFT` (409) until explicit re-registration. Manifest paths are realpath'd and containment-checked (tests in `runtime/tests/contracts-and-project.test.ts`).

**Engine composition** happens in the *client host*, not the daemon package: `projects/chirality-app-dev/frontend/electron/runtime-host.ts` `createEngines()` registers four adapters — `stub`, `anthropic-direct` (`@anthropic-ai/sdk`), `claude` (Claude Agent SDK, with legacy in-process coordination tools hard-rejected via `rejectLegacyDelegation`), and `pi` (the app's `PiAgentEngineAdapter`). It wires `OmlxClient` (from `@chirality/engine-pi-omlx`) into `ResidencyCoordinator`, builds `TurnCoordinator`, `GovernedAgent1RunCoordinator`, `RuntimeService`, and starts `RuntimeDaemon` at `{userData}/runtime/control.sock`.

**What runs in CI.** `.github/workflows/harness-premerge.yml`: builds and tests `runtime/`, builds the Electron host, then launches the real packaged entry headless — `xvfb-run electron dist-electron/main.js --runtime-daemon` with a temp user-data dir — polls for the socket + operator token file, registers `projects/chirality-app-dev/chirality.project.json` via `chirality-cli project register` over the socket, exports the issued project token, then starts the Next dev server whose `/api/harness/*` routes (e.g. `frontend/src/app/api/harness/turn/route.ts`) proxy to the daemon through `RuntimeClient` at `CHIRALITY_RUNTIME_SOCKET_PATH`, and runs `validate:release-quality` against that stack. So in CI the daemon really does own project registration, sessions, turns, and permissions for the whole harness validation suite; the local-model engine (Pi/oMLX) is not exercised live there (fake-loopback fixtures only).

## Residency semantics: design and implementation status

The contract is `runtime/packages/contracts/src/residency.ts`; the implementation is `runtime/packages/core/src/residency-coordinator.ts`, and it is real code, not paper:

- **Explicit activation:** `activate(modelId, approvalReference)` — both must be non-empty; every transition appends evidence (`chirality.model-residency/v1`) to `{runtimeDir}/model-residency.jsonl` with `started/completed/aborted/failed` outcomes and the `approvalReference`. Exposed at `POST /v1/models/<id>/activate` (requires `models:write`), and via CLI `models activate`.
- **Drain, never interrupt:** phase goes `DRAINING`; `waitForDrain` blocks on `activeTurns` (turns are admitted through `admitTurn()`, released in `TurnCoordinator`'s `finally`) up to `drainTimeoutMs` (default 10 min). Timeout → `RESIDENCY_DRAIN_TIMEOUT`, transition aborted, previous model stays managed. No force-interrupt path exists.
- **Fail-closed unload:** ownership is cleared and persisted *before* the unload request is transmitted (comment at lines 165–168: an unload response can be lost), so any failure after that point lands in `NO_MODEL` with no fallback (tests: "enters NO_MODEL when an unload outcome is ambiguous", "drains without force and enters NO_MODEL after a post-unload load failure", `runtime/tests/session-and-residency.test.ts:72,115`).
- **Never unloads unknown/helper models:** only the previously *managed* LLM is ever unloaded; the drift-reconciliation path unloads nothing at all — an externally loaded conflicting LLM just demotes the coordinator to `NO_MODEL` with a `"External residency drift introduced another loaded LLM"` evidence line (`reconcile()`, lines 268–300). The test asserts the `embed` model stays loaded.
- **Residency epoch, concretely:** `ResidencyEpoch = { epochId: string (randomUUID), modelId, activatedAt }`. It is **minted** in `completeActivation()` on every successful activation, **persisted** in `{runtimeDir}/model-residency.json` and in the completion evidence line, and **read** by (a) `TurnCoordinator.run`, which stamps `session.residencyEpoch` on the session record at `session:init` for every local turn (`turn-coordinator.ts:236-254`); (b) `GovernedAgent1RunCoordinator`, which refuses to delegate unless phase is `READY` with the exact model and an epoch present, records `child.residencyEpoch` in the AgentRun record, and passes it back into the manager's review prompt (`runtime-host.ts:313`: "Agent 2 return (${child.model}, residency ${child.residencyEpoch})"). Restart re-initializes from the persisted file but demotes to `NO_MODEL` if the model is no longer actually loaded (`initialize()`).
- **Turn admission:** `admitTurn(modelId)` throws `RESIDENCY_TRANSITION_IN_PROGRESS` or `MODEL_NOT_RESIDENT` (409) unless phase is `READY` and the model matches exactly. `TurnCoordinator` calls it only when `providerId === "omlx"`.

Status: fully implemented and unit-proven against a fake; the *live* half of the verification claim is deliberately opt-in (below).

## The Pi/oMLX engine

**What Pi is.** `@earendil-works/pi-coding-agent` v0.82.0 (pinned constant in both `runtime/packages/engine-pi-omlx/src/pi-omlx-engine.ts:10-11` and `projects/chirality-app-dev/frontend/src/lib/harness/pi-agent-engine-adapter.ts:23-24`) — a third-party in-process coding-agent framework. Chirality does not use its ecosystem: `createIsolatedPiResourceLoader` disables extensions, skills, prompt templates, themes, context/AGENTS files and overrides the system prompt (`pi-agent-engine-adapter.ts:492-520`); the session is built with `noTools: 'all'` plus only Chirality-supplied custom tools, in-memory credential/models/session/settings stores, and `allowModelNetwork: false`.

**What oMLX is.** A local OpenAI-compatible model server on literal `http://127.0.0.1:<port>/v1` (default port 8000) with control extensions `GET /models/status`, `POST /models/{id}/load|unload`, bearer-authenticated, redirects forbidden. `runtime/packages/engine-pi-omlx/src/omlx-client.ts:144-147` references "oMLX 0.5.x" field names (`model_type`, `engine_type: batched|simple|vlm|embedding|reranker`) and explicitly *never* infers a model's kind from its name. NOT FOUND: any in-repo expansion of the acronym (the MLX/Apple-silicon association is implied by the app PRD's "without requiring Apple Silicon, oMLX, or a downloaded model in CI", `projects/chirality-app-dev/docs/PRD.md:1338`). The one recorded live model is `Qwen3.6-35B-A3B-8bit` (`docs/harness/reliance_boundary_register.md:41`).

**Turn execution (the 1,010-LOC app adapter).** `preflight`/`startTurn` enforce a bounded-child posture: session must be Agent 2 with a `parentSessionId` and `approvalRef`, zero write targets, exactly one tool, no file attachments (`validateBoundedChildPosture`); the injected tool set must be explicitly marked `readOnly: true` with `evidenceSource: 'chirality-tool-bridge'` and exactly match the turn allowlist (`selectAuthorizedTools`). After constructing the Pi session it re-verifies the in-memory session identity and that Pi's active tool list equals the allowlist byte-for-byte. Streaming is a subscribe→`AsyncEventQueue`→`mapPiSessionEvent` pipeline emitting harness events persisted per-event; a 120 s default hard timeout aborts hung provider streams. Security shims: a process-global fetch guard forcing `redirect: 'manual'` on loopback `/v1` requests (Pi 0.82.0's OpenAI transport exposes no fetch option — comment at lines 206-210), a `console.error` guard redacting raw provider parser payloads, and API-key redaction on every failure string. Interruption (`interrupt()`) sets a flag, persists `interruption.requested`, calls `session.abort()`, and the turn terminates with persisted `interruption.completed` + `turn.interrupted` and `process:exit {exitCode:130, interrupted:true}` — the D-APP-40 taxonomy (`execution/_Coordination/_DECISIONS/D-APP-40_RULING_2026-06-21.md` in app-dev).

**The runtime package split.** `engine-pi-omlx` contributes two things: `OmlxClient` (the control plane — actually used by `runtime-host.ts` for residency) and `createPiOmlxEngineAdapter` (a thin `AgentEnginePort` shell that enforces Agent-2-only + exactly one `read_file`/`read` tool + `isExactlyResident`, then delegates to an injected `PiTurnRuntimePort`). That factory has **no callers** in the repo — the Electron host registers the app-dev `PiAgentEngineAdapter` directly, so the promoted turn engine is currently a contract shell awaiting the runtime port.

**"Fake-oMLX and opt-in live proofs".** Fake-oMLX is (a) the `FakeOmlx implements OmlxControlPort` fixture in `runtime/tests/session-and-residency.test.ts:9-35` driving the residency matrix, (b) a fake loopback OpenAI-compatible SSE server in `projects/chirality-app-dev/frontend/scripts/run-packaged-pi-runtime-proof.mjs` (CI-safe packaged proof, `harness:validate:pi-packaged-proof`), and the `omlx-client.test.ts` protocol fixtures. The live proof is explicitly non-CI, owner-selected evidence — `LIVE_OMLX_PROOF_2026-07-22.json` covering "exact authenticated discovery, governed read, hard denial, interruption, offline provider, and bad authentication" plus an "opt-in live two-model proof" for residency (`docs/harness/reliance_boundary_register.md:41,145`); PRD.md:1338: "a live oMLX proof is opt-in evidence only."

## The three most interesting engineering choices (investigator's view, labeled as such)

1. **Clearing residency ownership *before* transmitting the unload** (`residency-coordinator.ts:163-172`). The coordinator treats a transmitted-but-unconfirmed unload as already lost: ownership and epoch are persisted away first, so a dropped response can only strand the system in honest `NO_MODEL`, never in a false `READY`. This is the fail-closed invariant implemented as write ordering rather than as error handling — the cheapest correct answer to a genuinely ambiguous distributed outcome.

2. **The required-tool receipt as an in-process closure** (`agent1-run-coordinator.ts:readFileTool` + `turn-coordinator.ts:200-211`). Proof that the Agent 2 child actually read the file is a boolean captured by the tool's own `execute` closure in the daemon process — the engine adapter can *say* anything in its event stream, but `turn.completed` is rejected with `REQUIRED_DELEGATION_MISSING` unless the daemon's closure flipped. `turn-hardening.test.ts:314` ("does not accept adapter-forged tool evidence") tests precisely the forgery. It moves trust from the model/adapter to memory the coordinator controls.

3. **Sandboxing an uncooperative third-party agent with global-scope shims** (`pi-agent-engine-adapter.ts:99-264`). Because Pi 0.82.0's OpenAI transport exposes no fetch hook, the adapter installs a Symbol-keyed, idempotent process-global fetch guard that forces `redirect: 'manual'` on loopback `/v1` traffic (so a compromised local model server cannot bounce the bearer key off-host), plus a `console.error` guard that redacts raw provider bytes from Pi's stream parser diagnostics — alongside the fully in-memory resource loader that nulls out Pi's entire extension/skill/prompt ecosystem. It's defense-in-depth applied to a dependency, with each shim commented with the exact upstream limitation that justifies it; the residual smell (patching globals) is acknowledged as version-pinned scaffolding rather than architecture.

One honest gap worth relaying: the D-GOV-20 "promotion" of the Pi engine into `runtime/packages/engine-pi-omlx` is half-finished by design — the control plane (`OmlxClient`) is live in the daemon, but the promoted turn-engine factory `createPiOmlxEngineAdapter` has no caller; real Pi turns still run through the app-dev adapter registered by `electron/runtime-host.ts`. Any DEL-02-06-governed tranche touching runtime semantics will land on exactly that seam.
