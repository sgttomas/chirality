## Question and finding

The owner's proposed mental model puts Root in the control plane and product features in projects. Live accepted governance instead gives Root both operating-system stewardship and product obligations, including generic runtime ownership. Those obligations are real even where ordinary deliverable selection is sparse. The four surfaces below are useful responsibility categories, **not four disjoint filesystem trees**: root `docs/` contains both instruction canon and control-plane decision records, and Root product work can propose changes to the instruction surface through a separate M2 tranche.

I recommend naming control-plane discovery separately now, with exact R17 amendments, while retaining Root's current product identity. I would commission a bounded runtime ownership/packaging assessment before choosing a move. I would not yet commission wholesale Root decomposition retirement: the claimed absence of a runtime path home is false, and the Root product has accepted obligations beyond demonstrations.

## Runtime path-model status — disagreement with the prior reading

The allegation that `runtime/` lies in neither a working root nor the path model is not supported:

1. `docs/SPEC.md` §0.2.2 explicitly says that for the Root product, WORKING_ROOT is REPO_ROOT; §0.2.3 makes allowed write targets contained by that working root. Root `runtime/` is therefore inside the declared working root.
2. D-GOV-20's first architectural statement expressly names a Root-owned `runtime/` workspace. PRD_ROOT O-11, accepted through D-GOV-28 (its row retains a historical PROPOSED-origin label), binds continuing Root generic-runtime stewardship.
3. `execution/_harness/surface_ownership.yaml` declares `runtime/**` for PKG-02 and DEL-02-06. G2 reports that identical target as a static fact and defers serialization to G3. G3 has six nodes, none active; neither result authorizes a concurrent runtime write.
4. `runtime/` is absent from the **instruction surface** enumeration. That is consistent with code being Root product implementation rather than shared agent instructions. G4 even reports a prior runtime path declaration as non-blocking over-declaration. Adding runtime to that enumeration would change governance, not repair an obvious omission.

The unresolved design choice is how to organize the runtime product and its delivery cadence while Root retains accountable generic semantics. It is not where a currently homeless directory belongs. A separate registered runtime workspace would also introduce containment design: SPEC's external v2 registration requires disjoint instruction/working roots, and `runtime/packages/core/src/project-registry.ts` validates real paths, references and `CHIRALITY_INSTRUCTION_ROOT`. An in-tree project is not automatically equivalent to a disjoint external v2 registration. Choose the intended registration shape, manifest dialect, instruction-root deployment and tests before assuming that creating `projects/chirality-runtime/` is sufficient.

App's live `projects/chirality-app-dev/frontend/package.json` uses seven `file:../../../runtime/packages/...` dependencies. Packaging copies `dist-runtime`. Thus a physical code move requires App path/lockfile/build/packaging and test reconciliation through its owning loop, beyond this PR's permitted writes.
