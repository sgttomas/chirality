## Concrete guarded source retirement mechanism

Choose a dedicated `tools/scaffolding/apply_root_retirement.py`, tested by `tools/validation/test_apply_root_retirement.py`, rather than extending ordinary write_status lifecycle. This is a required implementation target, not an existing runnable tool. SCOPE_CHANGE's source writer must invoke the reviewed tool; copying53 status postimages directly is not the execution path.

Proposed command interface: `python3 tools/scaffolding/apply_root_retirement.py --subject-manifest <exact selected application manifest> --effect-record <exact owner-approved application record> --evidence-dir <immutable guard result directory> --dry-run`, then the same reviewed subject with `--apply` only after required authorization. These options are a Gate4 implementation contract; do not call them before the tool exists. The selected manifest resolves each source status path, original hash and approved postimage hash. It must contain exactly the approved53 Root statuses and six parent sets, with canonical path/ancestor containment and no symlink escape. It may not contain project targets, pointer files, authority documents or arbitrary metadata writes. Parent scope/decomposition propagation is a separate exact approved action.

The applicator checks owner acceptance of this exact application subject, accepted successor authority and exactly-one-owner/effect inputs, pinned guard implementation/config and immutable positive/negative evidence before any write. A label saying passing is insufficient: hashes must match the exact tested implementation and config and result identities. Ordinary lifecycle vocabulary remains unchanged. There is no force flag and Gate3 alone cannot bypass application approval. Required owner evidence is published main evidence under the approved gate class.

Avoid a circular G0 precondition by dry-running the exact complete prospective application state in an isolated scratch fixture and running guards there before touching any source status; this is candidate validation, never live acceptance. At apply time verify the accepted successor/config state and unchanged live preimages, block dispatch during the serialized transaction, then apply only the53 exact postimages and immediately run live guards against the completed effective state. A partial mixture is never eligible. Use a durable transaction journal with original/postimage hashes; on interruption or failure restore only bytes that still match this transaction's postimage, otherwise refuse to overwrite concurrent changes and report the exact blocked partial state. Idempotent reruns may only recognize the entire exact previously applied subject; they cannot silently complete an unrelated mixed state. No `_LATEST` write or PR merge occurs in this tool.
