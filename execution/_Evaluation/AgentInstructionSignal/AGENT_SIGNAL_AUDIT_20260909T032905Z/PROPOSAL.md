# Agent instruction audit — proposal

Candidate design proposal prepared by HELPS_HUMANS. Source basis: worktree HEAD `781b478176db46ca66ebd38991607612e0ce9338`, with exact instruction hashes in [SOURCE_MANIFEST.json](SOURCE_MANIFEST.json). This packet is derivative decision support; its recommendations await human selection.

## Direction

Make each retained agent instruction express a recognizable way of attending, judging, acting, and taking responsibility. Express that through **PROTOCOL, SPEC, STRUCTURE, and RATIONALE**. Put recurring methods where they can be loaded for the work, and give deterministic operations explicit tool implementations.

The strongest immediate subtraction is repetition: multiple accounts of the same purpose, naming explanations, revision recitals, repeated output inventories, repeated rules, and advice to component authors embedded in worker instructions. Each cohort report identifies specific passages to delete or compress. The reports separately identify material proposed for relocation, with destinations and caller implications.

The larger architectural proposal is to separate runtime configuration from the role presented to the model. Current code reads type, class, scope, tools, and other fields from the instruction document; the App also inserts its full text into the prompt. A runtime manifest and a smaller role projection are a concrete candidate design. That entails changes to discovery, policy resolution, prompt assembly, validation, and attribution. [Shared findings](SHARED_FINDINGS.md) cite the inspected consumers and explain the implementation boundary.

The current component standard is itself part of this inquiry. Its classification rules describe today's accepted arrangement. Our proposed future classifications also need a positive account of the behavior or method they would make available. A persistent role may be worth having because its orientation proves useful across changing assignments; that proposition can be examined through examples and comparative runs.

## What to change across the collection

| Material | Proposed treatment |
|---|---|
| Repeated purpose, naming conventions, revision recitals, slogans, repeated summaries | Delete the repetition; express the purpose once. |
| Multiple formulations of the same rule or validity condition | Write one clear obligation at the point where it governs judgment; reconcile discrepancies. |
| Characteristic attention, judgment, method, and responsibility | Give these the strongest wording in the four sections. Each role card proposes a compact core. |
| Command sequences, mode recipes, report templates, and recurring checklists | Extract the identified recurring method and its resources; make the caller load them when applicable. |
| Parsing, normalization, enumeration, and reproducible checks | Implement or consolidate the identified tools, with defined inputs and observable failure results. |
| Runtime metadata and duplicated launch mechanics | Move to a shared machine contract and resolved launch context once the actual consumers support it. |
| Long governing-reference lists and compatibility accounts | Keep the effective basis available through shared context and method contracts; shorten the role's treatment to what affects its decisions. |

These treatments are passage-specific. The detailed cards distinguish outright deletion, compression, and relocation so the proposed reduction remains inspectable.

## How the audit was conducted

Two bounded auditors read separate cohorts: 19 Type 0/1 packages and 15 Type 2 packages. Each produced a proposal for every assigned file, section-level changes, source evidence, a proposed core, dependencies, and a behavioral probe. HELPS_HUMANS reviewed both cohorts together and inspected shared standards, runtime consumers, and downstream reference surfaces.

The existing structural validator reported **34 checked, zero errors, zero warnings**. Source hashes and coverage are checked separately in the fan-in record. This audit ran source inspection and structural validation; candidate-agent trials remain proposed work.

The change I would make to the audit method is reflected here: ask what behavior the instruction makes possible, then test the proposed core through a concrete interaction. Conformance supplies the current baseline. Matched current/candidate runs would examine whether a smaller instruction sustains the useful pattern through ordinary work, ambiguity, and recovery. Each card supplies a starting probe; the human conversation that defines a role belongs in those trials too.
